## single-commit-exceptions — relocated verbatim from SKILL.md

**Exception 1 — the handover main-sync merge commit.** Phase 5 re-syncs the branch with `origin/<default>` right before the PR (see Phase 5 "pre-commit main-sync"). When main advanced during the run, `git merge --no-edit origin/<default>` produces a **merge commit** (and, on a resolved conflict, its `git commit --no-edit` finalize) on top of the single authored commit. That merge commit is **integration, not authored work** — it carries no new logic of this run — so it does not violate this rule. A clean auto-merge commits via `git merge` (no `git commit` verb) and never reaches `enforce-gates.sh`; a conflict finalize (`git commit --no-edit`) does reach it, and `enforce-gates.sh` enforces the review-staleness hash during the merge — so the merge commit is admitted only once the resolved tree has been re-reviewed and `reviewed_diff_sha` refreshed to match it (Phase 5 step 7). This means a conflict resolution cannot smuggle in an un-reviewed authored edit; the hook mechanically requires the re-review rather than trusting the skill to remember it.

**Exception 2 — Phase 6 bot-fix commits (opt-in).** When `bot_review_autofix` is on, Phase 6 (post-PR bot-comment review) may apply fixes for actionable bot comments and commit + push them to the open PR — additional *authored* commits after the Phase-5 one. This is permitted BECAUSE each bot-fix passes the FULL gate machinery before it can be committed: re-run `/auto-task-verify`, re-invoke the `auto-task-code-review` skill to a clean pass and refresh `gates.code_review.reviewed_diff_sha` + `clean_pass_after_last_fix`, AND — on STANDARD/HEAVY tier — re-run **Gate B** against the bot-fix diff after resetting `gates.gate_b.passed = false` (see Phase 6 step 3). The Gate-B refresh is load-bearing: `enforce-gates.sh` binds a freshness sha only to `code_review`, and its `gate_b` check (`gate_b.passed === true` or `skipped_reason` set) would otherwise accept the *stale* Gate B earned against the pre-bot-fix diff — so without the reset+re-run, a bot-fix would ship code-reviewed but NOT adversarially re-reviewed on the tiers that require Gate B. With the reset+re-run, the pre-commit hook gates the bot-fix commit exactly as it gates the Phase-5 commit (it already enforces gates for **every** non-`done`-phase commit, so no hook change was needed). The invariant therefore holds in its true form: *every authored commit in the run is individually gate-reviewed* — code-review always, and Gate B on the tiers that mandate it (LIGHT runs Gate B too, at one pass, for the bot-fix commit exactly as for the Phase-5 commit). The only NON-authored extra is the main-sync merge (Exception 1).

**Exception 3 — the Phase 9 release commit (opt-in).** When `release_mode` is `always`/`ask`, Phase 9 cuts one additional authored commit — `chore(release): vX.Y.Z` — plus an annotated tag. It is permitted on exactly the same terms as Exception 2, and for the same mechanical reason: the bump + changelog are new authored bytes added *after* the review went clean, so `enforce-gates.sh`'s staleness check (`hash(git diff <base>)` vs `gates.code_review.reviewed_diff_sha`) would block the commit outright. Phase 9 therefore re-passes the FULL gate machinery before committing — re-run `/auto-task-verify`, drive the `auto-task-code-review` skill to a clean pass, refresh `reviewed_diff_sha` + `clean_pass_after_last_fix`, AND on STANDARD/HEAVY reset `gates.gate_b.passed = false` and re-run **Gate B** against the release diff (see Phase 9 step 6). No hook change is required or permitted: the pre-commit hook already gates every non-`done`-phase commit, which is precisely why Phase 9 must run *before* `phase: "done"` rather than after it (after `done` the hook exits 0, and the release would be both ungated and invisible to `record-outcome.sh`). So the invariant holds unchanged across all three: *every authored commit in the run is individually gate-reviewed* — code-review always, Gate B on the tiers that mandate it. This commit is deliberately **separable and unwindable**: it contains the version bump and the changelog entry and nothing else, and because Phase 9 never pushes, `git tag -d` + `git reset --hard HEAD~1` fully reverse it.

The gate-enforcement hook (`enforce-gates.sh`, a PreToolUse/Bash hook registered via the plugin's `hooks/hooks.json`; the `settings-fragment.json` fallback wires it for `install.sh`/manual installs) enforces this mechanically by reading `gates.*.passed` (plus the fix-loop budget) from the state file before every commit. Attempts to commit before the gates pass will be blocked. Do not try to work around the hook — fix what the hook is telling you and try again. If the hook is wrong (e.g., resuming a run where gates legitimately already passed in a prior session), that is a bug in this skill or the state file, not license to bypass; surface to the user.


## phase5-steps — relocated verbatim from SKILL.md


**On entry, set `phase: "handover"`** (`expected_next_action: "auto-continue"`).

This is the **only phase that commits**. By the time you reach it, the working tree contains the entire accumulated diff (initial implementation + all fixes from self-verify, Gate A, code-review, Gate B) and the state file records that all required gates passed.

1. **Verify gates** before doing anything else:
   - `gates.code_review.passed === true` — required.
   - For STANDARD/HEAVY tier: `gates.gate_b.passed === true` (or `gates.gate_b.skipped_reason` set with a valid reason).
   If either is missing, STOP and surface — something went wrong in the pipeline and you should not be in Phase 5. Do NOT manually set the flags to escape this. **One recovery exception:** if **either** `gates.code_review.passed` or `gates.gate_b.passed` is `false` AND the newest `handover-docs` history entry is `result: "re-gating"` or `result: "applied-pending-authorization"`, this is not a pipeline bug — the step-1b docs re-gate was interrupted mid-flight (that step clears the flag before re-running Gate B). Do NOT surface: re-enter step 1b, whose **sub-step 0 resume guard** picks the correct restart point (authorization if the edits are on disk but unauthorized, otherwise the re-gate) and runs 5 → 6 → 7 → 8 — re-running `/auto-task-verify`, driving `auto-task-code-review` to a clean pass, refreshing `reviewed_diff_sha`, and re-running Gate B, setting each flag `true` only on its own clean pass. Both flags are in scope because the docs re-review's own fix loop can clear `code_review.passed` too. Without this clause the correct recovery is indistinguishable from the pipeline-bug case, and a resumed run dead-ends on a stop it cannot legitimately clear.
   - **Requirements completion check.** Set each satisfied `state.requirements[].status` to `done` (based on its `covered_by_acs` ACs having passed), then run `hooks/requirements-coverage.sh <STATE.json>` and require `all_complete == true`. Any requirement still `pending` means an obligation of the original task is unverified — do NOT commit; feed it back as a fix (or, only with the user's standing approval, mark it `dropped` with a reason). This is the "check every requirement on completion" contract: the task is done only when every dissected requirement is individually verified.
1b. **Docs update (optional — `docs_update_mode`).** After a run, the repo's user-facing docs may describe behavior the run just changed. This sub-step refreshes them **before staging**, so the docs land in the SAME single handover commit and pass the same gates as the code — no second commit, no new carve-out to the Single-commit rule. It runs here, ahead of the change diagram / artifacts / CONTEXT.md, precisely because those three are derived from the diff: docs edits must already be in the tree when they are generated.

   0. **Resume guard (check FIRST, before resolving the mode).** Read the newest `handover-docs` entry in `state.history` and branch on it. **In the three in-flight cases below** — `applying`, `applied-pending-authorization`, `re-gating` — do **not** re-invoke `auto-task-docs` in `report-only` first: its report would come back EMPTY (the edits are already on disk), sub-step 3 would exit the step, and the applied edits would be silently dropped from the commit. **The fourth branch is the opposite case and the normal one:** a fresh Phase-5 entry has no `handover-docs` entry at all, so it falls through to sub-step 1 and the `report-only` pass in sub-step 2 runs exactly as specified. Do not let the in-flight prohibition leak onto that path — skipping the report there would leave `apply` with no finding set, so it would re-derive its own superset with no report ever shown to the user, disobeying `ask` mode on the most-travelled path.
      - **`applying`** — the apply call was in flight when the session died, so the edits may be fully landed, partially landed, or not started. **Do not try to tell which from the tree** — `git diff --name-only <base>` cannot distinguish "edited by the apply" from "edited by this run's own code change", and a docs target like `README.md` is routinely in both, so any such test reads "never started" as "already applied" (or the reverse) and silently drops the approved edits. Instead, make the resume **idempotent**: re-invoke `apply` with the marker's persisted `findings` set, whose contract already requires re-confirming that each `file:line` still reads as described before editing — so a finding that already landed is skipped, a partially-landed set completes, and an unstarted set applies in full. Then continue at sub-step 5. (This mirrors how Phase 8 resolves the structurally identical resume problem: it consults a durable per-action record rather than inferring from live state.)
      - **`applied-pending-authorization`** — edits are on disk and unauthorized. Continue at sub-step 5 using that entry's `files` list.
      - **`re-gating`** — sub-step 5 already ran (it precedes 6), so the paths are already in PLAN.md's Blast Radius and any created file is already intent-to-added. Resume at sub-step **6** (the re-gate), not 5; this branch carries no `files` list and needs none.
      - **Anything else** (no `handover-docs` entry, or the newest is `applied` / `no-op` / `skipped-*`) — nothing is in flight; fall through to sub-step 1 normally.
   1. **Resolve the mode (live read, fail-open).** **Locate `settings.sh` via the three-probe pattern first** (`CLAUDE_PLUGIN_ROOT` is empty in the Bash-tool env, and each Bash call is a FRESH shell — the `settings_sh` variable bound during the Phase-1 pre-run cluster is long gone by Phase 5, so re-resolve it here rather than reusing it). Then `mode="$(bash "$settings_sh" get docs_update_mode)"`. Read it live rather than trusting the Phase-1 snapshot. **Then honour the preflight degrade — checked LIVE, not from history:** if `auto-task-docs` does not appear in **this session's** available-skills list (the same authoritative signal the component preflight reads), then force `mode="skip"`, log `result: "skipped-skill-absent"`, and do NOT improvise the docs work yourself, which would escape the skill's `README.md`/`docs/**` scope contract entirely. **Match EITHER registration form when you run that probe**, per the Invocation-name note in the preflight: `auto-task:auto-task-docs` under a marketplace install (the default), or the bare `auto-task-docs` under the `install.sh` symlink fallback. Testing only the bare name would force `skip` on every marketplace install, silently ignoring a configured `always`/`ask` while logging a reason that looks deliberate. **Do NOT key this on a `define-preflight` history entry:** `state.history` is append-only and persists across sessions, so a `docs-skill-absent` entry from an earlier session would still be present after the user ran `install.sh` to fix exactly that — silently disabling the docs step for the rest of the run while the skill sits registered and `docs_update_mode` says `always`. The history entry is a *record* of a past decision; the available-skills list is the current state. (Contrast the interrupt-recovery read in step 1, which is correctly keyed on the **newest** `handover-docs` entry, because sub-step 8 writes a later entry that supersedes it.) `skip` → no-op: log `{ phase: "handover-docs", result: "skipped-disabled", at }` and **skip the rest of step 1b — go to Phase 5 step 2 ("Build the change diagram")**, NOT to the numbered sub-step 2 below. **Any unrecognized value — the reader validates key *presence*, not value domains, so a hand-edited `"yes"` arrives verbatim — is read as `skip`**, logged once as `result: "skipped-invalid-value", value: "<what was found>"`. Settings unavailable → `skip`. The step never errors a run.
   2. **Resolve staleness FIRST, before any prompt — in `report-only` mode.** Invoke the **`auto-task-docs`** skill **explicitly in `report-only` mode** (its step-0 contract) so it returns a `file:line`-cited staleness report and edits **nothing**. Hand it: (a) `git diff <base>` — the run's accumulated work; (b) **the untracked set** `git status --porcelain --untracked-files=all | grep '^??'`, because a plain diff shows nothing for a new file and net-new user-facing surface is the most doc-worthy change there is; and (c) `.auto-task/<branch>/PLAN.md` for the Requirements + Acceptance Criteria. Its scope is `README.md` + `docs/**` (never `CHANGELOG.md`, `CLAUDE.md`, or code comments — see its Scope table). **Do NOT let it apply anything on this call:** in `ask` mode the user must be able to answer "no", which is impossible if the edits are already on disk, and stray unstaged edits would trip the review-staleness gate and dead-end the run.
   3. **Nothing stale → a real no-op, with NO yield.** If the report is empty — the docs are already current, or the repo has no `README.md` and no `docs/` directory — log `{ phase: "handover-docs", result: "no-op", reason: "docs already current|no in-scope targets", at }` and **leave step 1b — go to Phase 5 step 2 ("Build the change diagram")**. **This holds in `ask` mode too:** because staleness is resolved before the prompt, `ask` never interrupts the user about a change that does not exist. A docs-current run is silent regardless of mode.
   4. **Decide whether to apply.**
      - `always` → re-invoke the skill in **`apply`** mode, passing the report verbatim as the finding set, no prompt.
      - `ask` → **degrade to `always`, without yielding, when the run cannot legitimately stop**: `state.autonomy == "autonomous"` (autonomy silences the procedural gates), or `AskUserQuestion` is unavailable (headless). In that case re-invoke in **`apply`** mode and append a `state.assumptions[]` entry `{ kind: "auto-approved-ambiguity", note: "docs_update_mode=ask degraded to always (<autonomous|headless>); applied <n> docs edit(s) unattended", at }` so the merge gate (or the PR body) surfaces the call. Otherwise set `expected_next_action: "user-approval"`, present the staleness report prefixed with the run banner, and ask once: apply the docs edits, or skip them this run. Write back `expected_next_action: "auto-continue"` and honor the answer — **yes** → re-invoke the skill in **`apply`** mode, passing the approved report **verbatim as the finding set** so it applies exactly what the user saw and re-derives nothing (its `apply` row treats a handed-over set as authoritative AND complete); **no** → the declined branch below (nothing was ever edited, so there is genuinely nothing to revert). **This is the ONLY `ask`-mode yield, it is bounded to one prompt per run, and it happens only when there is a concrete proposed change** — see the yield-point contract.
      - **Bracket every apply with two markers — the first BEFORE the call.** (i) *Before* invoking the skill in `apply` mode, log `{ phase: "handover-docs", result: "applying", files: [<the report's paths>], findings: [<the approved report VERBATIM — each `file:line`, what it says now, and the proposed edit>], at }`. **The `findings` payload is load-bearing, not decoration:** it is the only durable copy of what the user approved. A resumed session cannot see the dead session's conversation, so without it the resume has nothing to hand `apply`, the skill re-derives its own superset (its `apply` row: "Only when no set was handed over do you run steps 1-3 yourself first"), and un-consented lines ride into the commit — re-opening the exact `ask`-mode consent hole the "ceiling, not a starting point" rule closed. (ii) *After* the edits land, log `{ phase: "handover-docs", result: "applied-pending-authorization", files: [...], at }`. The pre-call marker is the one that matters: an interrupt across the sub-agent return boundary — a likely interrupt point, not a micro-window — would otherwise leave edits on disk with NO marker, so a resumed run falls through to sub-step 2, gets an EMPTY report (the edits are already applied), exits at sub-step 3, and the docs work is silently dropped from the commit while the run reports success (and, worse, the working-tree diff no longer matches `reviewed_diff_sha`, so the commit hard-blocks until someone re-reviews and unwittingly drops the edit).
      - **Outcome — declined** (the `ask` branch only; `always` and the degrade paths never reach it) → log `{ phase: "handover-docs", result: "declined", findings: <n>, at }`, park the findings in `state.followups` (`source: "docs"`), and **leave step 1b — go to Phase 5 step 2 ("Build the change diagram")**. Nothing was edited, so no re-gate is needed.
   5. **Authorize the edited paths for staging — BEFORE the re-gate (REQUIRED; ordering is load-bearing).** Step 5's Stage rule admits only "the planned files" and rejects anything outside PLAN.md's Blast Radius. `README.md` / `docs/**` are normally NOT in a Blast Radius authored in Phase 1 for the *code* change, so without this step the docs edits either stay unstaged (the commit, change diagram, and CONTEXT.md silently omit them while the run reports success — and the staleness hash still matches, since it is computed over the working tree, so nothing blocks) or trip a fabricated out-of-blast-radius blocker at handover. So: append the edited docs paths to PLAN.md's **Blast radius** list with a one-line note that step 1b added them. **If the step CREATED a doc file, `git add -N <path>` it (intent-to-add) NOW, before sub-step 6 pins the sha** — an untracked file is invisible to `git diff <base>`, so without this it is also invisible to `gates.code_review.reviewed_diff_sha` and would reach the commit un-reviewed with the staleness hook unable to see it. Intent-to-add stages no content, so the "planned files only" staging in step 5 still governs what actually lands, and log `{ phase: "execute-checkpoint", result: "adjacent", files: [<docs paths>], summary: "docs-update step 1b — README/docs paths authorized for staging", at }`. Step 5 then stages them as planned files. **Why this precedes the re-gate:** `reviewed_diff_sha` is computed from `git diff <base>`, which shows nothing for an untracked path — so intent-to-adding *after* the pin would either be decorative (if the skill already did it) or, worse, make the new file enter the diff only after the sha was fixed, so `current_sha != reviewed_diff_sha` and `enforce-gates.sh` hard-blocks the handover commit. Doing it here means the created file is inside the diff that sub-step 6 reviews AND pins, so its content is genuinely reviewed and the hash covers it. This is a *recorded* authorization, not a bypass — the paths are still restricted to the `auto-task-docs` scope contract.
   6. **Re-pass the gates (MANDATORY) — now that every docs path is visible to `git diff`.** The edits are new authored bytes added *after* the review went clean, so the review is now stale by exactly the mechanism `enforce-gates.sh` blocks on. Re-run `/auto-task-verify` (current tier scope), re-invoke the **`auto-task-code-review`** skill on the new diff and drive it to a clean pass, then refresh `gates.code_review.reviewed_diff_sha` (Phase 4's pinned-flags formula) and `clean_pass_after_last_fix`. On **STANDARD/HEAVY** tier also set `gates.gate_b.passed = false` and **re-run Gate B** against the docs diff, setting it back to `true` **only when that pass clears Gate B's own resolution ladder** — i.e. no finding met the AC-impact test of `references/phase-3-gates.md` Step 2 (breaks an approved AC / runtime-reachable regression or bypass / security or data-loss path). A finding that DOES meet it loops back to fixing; one that does not is **parked whatever its severity label**, exactly as in the main pipeline — the hook binds a freshness sha only to `code_review`, so without the reset it would accept the Gate B earned against the pre-docs diff (the identical reasoning as the Phase-6 bot-fix carve-out). Leaving it `false` would block the handover commit. **Interrupt safety (REQUIRED):** log `{ phase: "handover-docs", result: "re-gating", files: [<the authorized docs paths>], at }` to `state.history` BEFORE clearing **either** flag, so a session that dies mid-re-gate is recoverable — see the recovery clause in step 1. Note this window can leave `gates.code_review.passed` false as well (a Blocker/Required in the docs re-review loops back to fixing, which clears it), so the marker covers both flags, not just `gate_b`. LIGHT runs Gate B too, at one pass.
      - **This re-gate has its own Gate B allowance for this run** — `scope: "regate:docs"`, sized by `lb_gate_b_regate_cap` (one pass plus one fix-and-re-pass), counted separately from the main loop's `lb_gate_b_cap` and **not renewed if the docs step runs again**. This separation is load-bearing rather than tidy: were the re-gate to draw on the main-loop cap, a run that spent its passes in the main loop could never re-earn `gates.gate_b.passed`, and — since "Leaving it `false` would block the handover commit" — the run would deadlock at handover with no route forward. With `docs_update_mode: always` that would be every run on the tiers that require Gate B. If the allowance is exhausted and findings remain, **surface** with the per-pass severity table and the three recorded grants (one more pass / park-and-advance / descope) per `references/phase-3-gates.md` Step 4 — never leave the flag `false` and never self-grant.
   7. **Loop-counter accounting (do NOT silently spend the fix-loop budget).** A **clean** docs re-review pass does **not** increment `iteration.review`: no finding drove it, it is a gate refresh, and `enforce-gates.sh` measures the budget against `max(iteration.fix, iteration.review)` — charging a docs refresh to that budget would consume rounds meant for real fixes and could block the commit on a run that never iterated. If the docs re-review **does** produce a Blocker/Required, that is a genuine fix round: increment the counters and loop exactly like any other, subject to the tier cap.
   8. **Record.** Log `{ phase: "handover-docs", result: "applied", mode: "<mode>", files: [...], findings: <n>, at }` and append a TRACE entry (`operation: auto-task:phase-5-docs`) naming the files edited and any parked out-of-scope staleness. The docs edits are now part of the diff that steps 2-4 describe and step 5 stages.

2. **Build the change diagram.** Produce a human-readable Mermaid diagram that the reviewer can scan in ~10 seconds to understand what the run did and (where applicable) what the prior state looked like. Embed it in the PR body under `## Change diagram` so GitHub renders it inline. This is a MANDATORY step — every auto-task PR must carry a diagram or a one-line documented skip.

   **Pick the diagram type that matches the change.** Use ONE diagram unless the task spans multiple concerns and a second adds clear value:

   | Task shape | Mermaid diagram type | What to show |
   |---|---|---|
   | Module / architecture change, refactor, new component wiring | `flowchart` with `subgraph Before` and `subgraph After` | Boxes for modules/files; arrows for calls/imports/data flow. Highlight added/removed/changed nodes (see styling below). |
   | New user flow, request lifecycle, API call sequence | `sequenceDiagram` | Actors as lanes; messages in order. If pre-existing flow exists, show it once with `Note over X: before` annotations on the steps that changed. |
   | State-machine or status change | `stateDiagram-v2` | All states + transitions. Mark new transitions with a comment. |
   | Schema / data-model change | `erDiagram` | Entities + relationships. Annotate new fields/tables in a `Note:` line below the diagram. |
   | File-tree reorganization, large rename/move | `flowchart` tree (top-down) | Before tree on the left, After on the right via two `subgraph`s. |
   | Bug fix in an existing flow | `sequenceDiagram` or `flowchart` | Show the flow once; annotate the broken step (`Note over X: was: <bad>`) next to the fixed step. |
   | **Visual / UI / CSS change** (layout, spacing, size, color, component appearance, a visible flow) | **— (no Mermaid; before/after screenshots when `visual_assets_enabled`, else a local-artifact note)** | The rendered before/after pair carries the delta a box diagram cannot. See "Visual changes" below (embedding is opt-in; when off, a note points at the local artifacts instead — either way, no Mermaid box for the visual concern, which is noise). |
   | Pure config / docs / dep bump / typo / formatting-only | — (skip) | Write a single bullet under `## Change diagram` instead: `Skipped — <type>-only change, no flow/structure shift.` Log to state. |

   **Before/After convention.** When the prior state matters, show it. Two patterns are acceptable:
   - **Two subgraphs in one diagram** (preferred for compactness): `subgraph Before` / `subgraph After`. Use the same node IDs across subgraphs only if they refer to the same artifact.
   - **Two separate fenced diagrams** under sub-headings `### Before` and `### After` — use this when the diagrams are too dense to share a single canvas.

   For greenfield additions where there is no meaningful "before" (e.g., a brand-new module): show only `## After` and add a one-line note: `No prior state — this is a net-new <thing>.` Don't fabricate a "before" just to fill the slot.

   **Highlight what changed.** Within the diagram, mark new/changed/removed elements so the reviewer's eye lands on the delta:
   - Mermaid `classDef` styling — define `added`, `removed`, `changed` classes and apply with `class NodeId added`. Example:
     ```
     classDef added fill:#dcfce7,stroke:#16a34a,stroke-width:2px
     classDef changed fill:#fef9c3,stroke:#ca8a04,stroke-width:2px
     classDef removed fill:#fee2e2,stroke:#dc2626,stroke-dasharray:4 2
     ```
   - For sequence/state diagrams where classDef doesn't apply, use `Note over X: NEW` / `Note over X: CHANGED` / strike-through prose in a `Note`.

   **Source of truth.** Derive the diagram from the actual staged diff plus PLAN.md's Blast Radius — not from the original task description. The diagram must reflect what was *built*, not what was *planned* (the two can diverge legitimately via drift events; the diagram tracks the final state).

   **Length budget.** Aim for ≤ 25 nodes / ≤ 15 sequence messages / ≤ 8 entities. If the diagram would exceed that, abstract: collapse a cluster of small files into one node labeled with the cluster name, or split the diagram into ≤ 2 focused views (one per concern). A bloated diagram is worse than no diagram.

   **Render check.** Mermaid syntax errors break the PR-body render. Sanity-check the diagram for unmatched brackets, unquoted node labels that contain spaces, reserved words, and trailing semicolons (Mermaid is whitespace-sensitive). If unsure, simplify rather than ship a broken render. If a richer canvas is genuinely needed (multi-page architecture, design-system diagram), use the `figma-generate-diagram` skill — load it first per its own MANDATORY-prerequisite rule — to produce a FigJam diagram and link the resulting URL under `## Change diagram` instead of embedding Mermaid.

   **Visual changes (embedded before/after — OPT-IN, replaces Mermaid for visual concerns when enabled).** When the change is visual (the diagram-type table's "Visual / UI / CSS change" row) AND visual embedding is enabled, the PR carries a rendered **before/after pair** under a `## Visual changes` section instead of a Mermaid diagram for that concern. (A PR with an additional structural concern still gets that concern's Mermaid diagram; the two coexist. A *pure* visual change gets screenshots and no Mermaid.) **Embedding is best-effort presentation, NOT verification** — the "does it work" judgment already happened in Phase 3 / Gate A on local dev (INCONCLUSIVE if it couldn't). So **nothing in this step ever blocks the run**: every failure path falls back to a note + local artifacts and the run continues.

   0. **Opt-in gate.** Read `visual_assets_enabled` (`settings.sh get visual_assets_enabled`). If it is not `true`, **skip embedding entirely** — upload nothing. Instead, under `## Visual changes` write a one-line note pointing at the local proof and (if any) the preview: `Screenshots captured locally (see artifacts/screenshot-*.png); visual embedding is off — enable visual_assets_enabled to embed before/after in the PR.` Log `{ phase: "handover-visual", result: "skipped-disabled", at }` and go to "Persist the source". (This is the default state.)

   - **If the scanner cannot inspect the diff, the commit is blocked too** (all-`skip`, a missing `checks.sh`, unusable output) — "could not look" is not "nothing to find". The block message carries the scanner's own reason; the common real cause is a `state.base` that no longer resolves (a rebased or pruned ref), whose fix is to make the base resolvable again rather than to override.
   - **Three ordinary diffs trip `test-integrity` without weakening anything**, because the scan is per-file and rename-blind: renaming a test file, deleting an obsolete one, and moving assertions out of one file into another. The block message names all three; for those the ack IS the intended answer, and "restore the tests" is the wrong instinct. Read the named path before editing anything.
   - **The scan covers the index as well as the worktree.** `git commit` commits the index, so a credential staged and then edited out of the working file is invisible to `git diff <base>` — the gate therefore also runs `checks.sh --base <base> --cached`, and tags any index-only finding in the message. If a block names a finding you cannot see in your editor, that is why: check `git diff --cached`.

   Because `warn` never blocks, a fake credential or a quoted marker inside a test/fixture path still commits exactly as before — the scanner demotes those by path, and this gate honors the demotion.
   - **Then release the intent-adds — UNCONDITIONALLY, right here (REQUIRED).** Run `hooks/intent-add-untracked.sh --undo`. Phase 3 intent-added the files this run created so they would reach the gates; whatever the staging above did **not** stage — a scratch file, an artifact outside the Blast Radius — still carries an index entry, and git treats such a path as *not uptodate*, so a later **`git merge` refuses outright**: `error: Entry 'X' not uptodate. Cannot merge.` (exit 128; the same merge succeeds once released). **It belongs to step 6, not step 7, for two reasons.** First, `--undo`'s precondition is "after the authored commit" — before it, a new empty file staged deliberately is byte-identical in the index to an intent-add and would be wrongly released; the commit above removes that ambiguity, since anything meant to land is now in HEAD and is skipped. Second, step 7 is guarded by *"Unless the sync was skipped-offline in step 5"*, and an offline run must release its index entries too — a run that ends holding them leaves the user a tree where an ordinary `git merge` refuses. `--undo` runs `git rm --cached` on exactly the paths whose index blob is empty AND that are absent from HEAD: never a genuinely-empty file the run committed, never staged content, and never a file's bytes on disk — each returns to plain untracked. Idempotent and fail-open, so running it with nothing to release is a no-op. Log `{ phase: "handover-release", result: "intent-adds-released", count: <n>, at: "ISO-8601" }`.
7. **Integrate main (merge), then verify no leak.** Unless the sync was skipped-offline in step 5, bring the branch up to date with main so the PR merges cleanly:
   - **Merge:** `git merge --no-edit origin/<default>`.
     - **Already up to date / main did not advance** → no-op, no new commit; skip to the leak check.
     - **Clean auto-merge (main advanced, no conflicts)** → git auto-commits the merge (no `git commit` verb, so `enforce-gates.sh` is not involved). Upstream main may have changed behavior this branch relies on, so **re-run `/auto-task-verify` (current tier scope) after the merge** and confirm green before continuing; a regression routes back through the fix/review loop. Upstream's own code is trusted as already-reviewed on main.
     - **Conflict → hybrid resolution policy:**
       - **Auto-resolve** *mechanical / non-overlapping* conflicts only: disjoint hunks in the same file, pure additions on both sides in different regions, generated-file / lockfile regeneration, import ordering. Resolution **reconciles the two sides only** — do NOT author new feature logic while resolving, and **when in doubt, surface** rather than guess. Then `git add` the resolved paths — but **do NOT commit yet** (the re-check below is a hard prerequisite of the merge commit).
       - **Mandatory re-check BEFORE finalizing the merge commit:** the conflict resolution edited the run's own reviewed code, so re-run `/auto-task-verify` **AND** re-invoke the `auto-task-code-review` skill on the post-merge diff, drive it to a clean pass, **refresh `gates.code_review.reviewed_diff_sha`** to `hash(git diff <base>)` of the resolved tree (per Phase 4's pinned-flags formula) — **and if the resolution CREATED a file (a split-out module, a regenerated artifact written to a new path), run `hooks/intent-add-untracked.sh` before that refresh**, since an untracked path is invisible to `git diff <base>` and would otherwise enter the diff only at the finalize commit, moving the hash after it was pinned and hard-blocking the very `git commit --no-edit` below (the Phase-3 contract in `references/phase-3-gates.md` states this rule for every re-pin; this is its merge-finalize instance, and note there is no MERGE_HEAD exemption) — and — on **STANDARD/HEAVY** tier — **reset `gates.gate_b.passed = false` and re-run Gate B** against the merged diff (mirroring the Phase-6 bot-fix carve-out; LIGHT runs Gate B too, at one pass). `/auto-task-verify` alone is not enough — it runs tests/types/lint, not the review loop, so authored resolution logic would otherwise never be re-reviewed. **Only after that clean re-review**, finalize with **`git commit --no-edit`** — and because that re-sweep re-created index entries for anything the finalize does not take, **run `hooks/intent-add-untracked.sh --undo` again immediately after it**, exactly as step 6 does after the authored commit (same precondition: the commit has just landed, so what remains is by definition not part of it). Without that second release the run ends holding entries the step-6 release had already cleared. Note also that the finalize below is itself a `git commit` — this literal `git commit` re-enters `enforce-gates.sh`, whose staleness check **now applies during a merge too** (there is no MERGE_HEAD exemption): the refreshed `reviewed_diff_sha` is precisely what admits the merge commit, and a skipped re-review leaves a stale sha that is **mechanically BLOCKED**. Do NOT lean on `git merge --continue` slipping past the hook's commit regex.
       - **This re-gate has its own Gate B allowance for this run** — `scope: "regate:merge"`, sized by `lb_gate_b_regate_cap`, counted separately from the main loop and not renewed per conflict. Exhausted with findings remaining → **surface** per `references/phase-3-gates.md` Step 4 (per-pass severity table + the three recorded grants). A merge whose Gate B cannot be re-earned must not sit with `gates.gate_b.passed = false`: the staleness check would block the finalize commit and the run would have no route forward.
       - **STOP and surface** (Surfacing protocol, Loop-rule clause 3 "external blocker", `expected_next_action: "user-approval"`) for conflicts needing judgment: overlapping edits to the same logical lines, or any semantic conflict where either side's intent could be lost. On resume, finish the merge and continue.
     - **Re-check scope.** Any post-merge verify/review covers only **this run's own delta over the new main** (review `git diff origin/<default>...HEAD` plus the resolved-conflict files), NOT the entire upstream churn the merge pulled in — otherwise the loop wastes effort re-reviewing unrelated upstream commits. The staleness hook fingerprints the full `git diff <base>` and **now enforces that hash during the merge as well** (the refreshed `reviewed_diff_sha` must match before the merge commit); the review *scope* is still the run's own contribution.
     - Log `{ phase: "handover-sync", result: "up-to-date|clean-merge|auto-resolved|surfaced", at: "ISO-8601" }` to `state.history`.
   - **Verify `.auto-task/` did not leak into history** (after the merge): `git log <base>..HEAD --name-only -- .auto-task/` MUST be empty.
7b. **Merge gate (autonomy — see "Autonomy modes & the merge gate").** Determine whether this run's land requires the mandatory merge-gate ack, and set it **HERE — AFTER the step-7 main-sync merge, before any push/land** (ordering is load-bearing: `enforce-gates.sh` blocks *any* `git merge`/`git push` while `gates.merge.required && !acked`, so setting `required` earlier would block the step-7 integration merge; set it only now).
