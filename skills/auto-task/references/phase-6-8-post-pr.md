## phase6-body — relocated verbatim from SKILL.md


After the PR is opened, review bots (Cursor, CodeRabbit, Sourcery, GitHub Copilot review, …) often post comments a minute or two later. This phase **collects those bot comments, triages them conservatively, and auto-applies only the high-confidence, in-scope fixes** — each routed through the same verify → `auto-task-code-review` → gate → commit → push loop as any other change. It runs when a push happened in Phase 5, a PR was opened (`pr_url` set), AND `bot_review_autofix === true` (opt-in; **default `false`**) — otherwise Phase 5 step 12 already routed past it (to Phase 7 or `done`).

**This phase MAY make additional authored commits — one of the two opt-in exceptions to "only Phase 5 commits" beyond the main-sync merge (the other is the Phase-9 release commit).** Each bot-fix commit is permitted BECAUSE it passes the FULL gate machinery (re-verify + re-`auto-task-code-review` to a clean pass + refreshed `reviewed_diff_sha`) before `enforce-gates.sh` will allow it — exactly like the Phase-5 conflict-resolution re-review carve-out. The invariant "every authored commit is gate-reviewed" is preserved; the mechanical hook is unchanged (it already gates every non-`done`-phase commit). See the Single-commit rule's bot-fix carve-out.

Read the live settings: `autofix = settings.get bot_review_autofix`, `timeout_min = bot_review_timeout_min` (default 10), `interval_sec = bot_review_poll_interval_sec` (default 30), `extra_bots = bot_review_bots`. If `autofix !== true`, set `bot_review = { status: "skipped-disabled", at }` and go straight to the Phase-7 gate (or terminal `done`) — this phase does nothing.

**1. Collect bot comments (bounded poll, ONE round).** Use `hooks/pr-bot-comments.sh --ref "<branch>" [--bots "<extra_bots>"]` (locate via the three-probe pattern; `CLAUDE_PLUGIN_ROOT` is empty in the Bash-tool env). It returns a de-duplicated JSON array `[{author,path,line,body,url,created_at}]` of bot-authored comments across the PR's issue comments, inline review threads, and review summaries (fail-open `[]`). Poll bounded by `timeout_min`: each cycle that returns `[]` — bump `bot_review.polls` + refresh `bot_review.at` in STATE (REQUIRED, same anti-stall reason as Phase-7 `preview.polls`), wait `interval_sec` via a bounded mechanism (the **Monitor** tool — foreground `sleep` may be blocked), then re-poll — until the array is non-empty OR `timeout_min` elapses. This is **exactly ONE collection round**: do NOT re-poll for comments that a later fix-push itself re-triggers (that would be an unbounded re-comment→re-fix loop).
   - **No comments by `timeout_min`** → `bot_review = { status: "skipped-no-comments", polls, at }`; proceed to the terminal handoff (step 6). A slow review bot that posts after the window is deferred (recorded as a parked follow-up), not chased.

**2. Triage each comment (conservative).** Read `.auto-task/<branch>/CONTEXT.md` + PLAN.md first (Read-before-review contract) so you never re-litigate a decision the user already made (e.g. a bot flags something the user explicitly accepted at the risk disclaimer → **park**, do not "fix"). Classify each bot comment:
   - **Actionable** — a concrete, in-scope, high-confidence fix that maps to this run's files / Acceptance Criteria, does not contradict a Human choice, and does not expand scope. (Conservative bar: when unsure, PARK.)
   - **Park** — vague, speculative, style-preference, out-of-scope, or contradicts an approved decision.

**3. Apply the actionable fixes (ONE bounded round).** For each actionable finding: apply via `auto-task-fix` (working-tree edit), re-run `/auto-task-verify` (current tier scope) + any affected AC bound-checks, then re-invoke the `auto-task-code-review` skill on the new diff and drive it to a clean pass, and **refresh `gates.code_review.reviewed_diff_sha` + `clean_pass_after_last_fix`**. **If a bot-fix CREATED a file, run `hooks/intent-add-untracked.sh` before that refresh** — an untracked path is invisible to `git diff <base>`, so it would enter the diff only when the commit stages it, moving the hash after it was pinned and hard-blocking the commit (the Phase-3 contract in `references/phase-3-gates.md` states this rule for every re-pin; this is its Phase-6 instance). **Then re-run the gate the tier requires so the bot-fix diff is gate-reviewed exactly like the Phase-5 commit was — this is what makes the Exception-2 invariant true rather than aspirational:** because a bot-fix is *new authored code landing after Phase-5's Gate B*, and `enforce-gates.sh` binds a freshness sha only to `code_review` (not to `gate_b`), you MUST NOT let the commit ride the stale `gates.gate_b.passed` earned against the pre-bot-fix diff. On **STANDARD/HEAVY** tier: set `gates.gate_b.passed = false`, re-run **Gate B** (the adversarial `task-execution-verifier`) on the bot-fix diff, and set it back to `true` only when that pass clears Gate B's own resolution ladder — no finding met the Step-2 AC-impact test (see `references/phase-3-gates.md`); a finding that meets it loops back to fixing, one that does not is parked whatever its label, exactly as in the main pipeline. On **LIGHT** tier Gate B is skipped by design, so leave `gates.gate_b.skipped_reason` set and re-run only verify + code-review. Then commit the accumulated bot-fixes via the `auto-task-commit` skill (defensive `git restore --staged .auto-task/` first) and `git push`. The pre-commit hook gates the commit via the refreshed flags/sha — do not bypass it; if it blocks, fix what it reports.

**This re-gate has its own Gate B allowance for this run** — `scope: "regate:bot-fix"`, sized by `lb_gate_b_regate_cap` (one pass plus one fix-and-re-pass), counted separately from the main loop's `lb_gate_b_cap` and **not renewed per bot-fix round**. Two reasons it must be separate and must not renew. Separate, because a run that spent its main-loop passes could otherwise never re-earn `gates.gate_b.passed`, and the bot-fix commit would deadlock on the very gate that authorizes it. Non-renewing, because this phase can execute more than once in a run, and a fresh allowance each round would rebuild the unbounded loop inside Phase 6 — the same shape that produced 4-11 adversarial passes in the main loop. Exhausted with findings remaining → **surface** per `references/phase-3-gates.md` Step 4 (the per-pass severity table plus the three recorded grants), which pairs naturally with this phase's existing "when unsure, PARK" bias.
   - **No push authority (fork PR / protected branch / permission denied):** if `git push` fails for lack of authority, FAIL-OPEN — leave the fix committed locally, park the finding(s) with the reason ("could not push bot-fix — no authority on this PR branch"), and continue. It is NOT a hard blocker: the PR is already open and the core work shipped.

**4. Park the rest.** Add every non-applied bot comment to `state.followups` (`source: "bot-review"`, note = author + one-line gist + `url`). Record `bot_review.applied[]` (each with `{url, path, line, summary, at}`) and `bot_review.parked[]`.

**5. Record + report.** Write `bot_review` to state. Append a `## Bot-comment review` section to `.auto-task/<branch>/CONTEXT.md` (comments found, applied, parked, with urls). Append a TRACE entry: `operation: auto-task:phase-6-bot-review`, `outcome: <applied|no-action|surfaced|skipped>`, summary covers counts + what changed.

**6. Terminal handoff.** After bot-review completes, decide the next transition. The `done` branch is subject to the **run-metrics terminal guard** (Phase 5 step 4) — confirm the `handover-metrics` history entry exists before writing `phase: "done"`, and run the metrics step first if it does not:
   - **Preview verification applicable** (per the Phase-7 gate below) → set `phase: "preview"`, `expected_next_action: "auto-continue"`, advance to **Phase 7**. Do NOT report a final summary yet.
   - **Else external actions declared** (no preview) → set `phase: "external"`, `expected_next_action: "auto-continue"`, advance to **Phase 8**. Do NOT report a final summary yet.
   - **Else release applicable** (`release_mode` is `always`/`ask`) → set `phase: "release"`, `expected_next_action: "auto-continue"`, advance to **Phase 9**. Do NOT report a final summary yet — this is the **release terminal guard** (Phase 5 step 4).
   - **Else** → set `phase: "done"`, `expected_next_action: null`, and report the final summary (PR URL + what bot-fixes were applied/parked + a one-line diagram note + local-artifacts pointer).

`expected_next_action` during Phase 6: poll cycles → `"auto-continue"` (the `bot_review.polls` bump advances the anti-stall signature); applying fixes / re-review / committing → `"auto-continue"`; a genuinely ambiguous blocker a bot surfaced that needs user judgment → `"user-approval"` per the Surfacing protocol; terminal → `null` (done) or `"auto-continue"` (advancing to Phase 7 or Phase 8).


## phase7-body — relocated verbatim from SKILL.md


The last verification rung: after the change has been pushed (and after any Phase-6 bot-fixes have landed), confirm it actually works on the **deployed preview**, then record a final judgment. This phase runs when a push happened in Phase 5 (the user did not "hold") AND one of the following applies — otherwise Phase 5 step 12 (or Phase 6's handoff) already routed to `done`:

- **Explicit opt-in:** `has_preview_deployment === true` (explicitly set). Runs every time; no re-learn, no persist.
- **Auto-learn (each undecided run):** `has_preview_deployment` is **unset** (never explicitly decided — `settings.sh present has_preview_deployment` is `false`) AND `preview_autodetect !== false` (built-in default `true`) AND a PR was opened (`pr_url` set). This eligibility is re-evaluated every post-PR run and stays true until a positive is learned or an explicit value is set. In this path the pipeline detects whether a preview deployment exists (step 1) and then **persists only a positive answer** to `has_preview_deployment` (step 1.5) so a found deployment becomes deterministic: `true` if a deployment is found (checked every time thereafter). If none is found, **nothing is persisted** — the project stays unset and re-learns on the next post-PR run (set an explicit `false` to stop the re-check).
- **Explicitly disabled** (`has_preview_deployment === false`, explicitly set) or **auto-learn opted out** (`preview_autodetect: false` with no explicit `has_preview_deployment`) → this phase does not run; Phase 5 step 12 recorded `skipped-disabled`.

**This phase makes NO new authored commit.** The reviewed commit(s) already shipped in Phase 5 (and any bot-fixes in Phase 6); Phase 7 only observes the deployed result. A FAIL here is surfaced as a finding, not auto-fixed (see below) — fixing it is a follow-up run. Because it never commits, `enforce-gates.sh` is not involved; the only mechanical contract is the Stop hook, satisfied by keeping polling on `auto-continue` and every human surface on `user-approval`.

Read the live settings again (do not trust only the Phase-1 snapshot — the user may have edited them). Resolve: `wait_mode = settings.get preview_wait_mode` (default `poll`), `timeout_min = preview_timeout_min` (default 30), `interval_sec = preview_poll_interval_sec` (default 60), `url_template = preview_url`, `bypass = preview_bypass_header`.

**Wait mode:**

- **`handoff`** — do NOT wait in-session. Set `preview = { status: "awaiting", wait_mode: "handoff", ... }`, `phase: "preview"`, `expected_next_action: "user-approval"`, append a TRACE entry, and surface to the user: "Pushed. Preview verification deferred — re-run `/auto-task` once the deploy lands and I'll verify + verdict." On the later resume, the pipeline re-enters Phase 7 and runs the `poll`-style detection immediately (the deploy should be ready by then). (When auto-learn is eligible, defer it too — on the resume the run persists only a positive detection; a non-detection persists nothing and simply re-learns on a later run.)
- **`poll`** (default) — poll for readiness in-session, bounded by `timeout_min`. Keep polling until a ready, SHA-matched preview URL resolves OR the timeout elapses. Each poll cycle that does NOT yet resolve a URL: (a) **increment `preview.polls` and refresh `preview.at` in STATE** — this is REQUIRED, not optional; (b) wait `interval_sec` before the next cycle using a bounded mechanism (e.g. the **Monitor** tool — foreground `sleep` may be blocked in this environment); (c) re-poll. **Why the `preview.polls` bump matters:** the anti-stall Stop hook (`prevent-mid-protocol-stall.sh`) blocks turn-ends whose run-state signature is unchanged for ~25 turn-ends in a row (a frozen-run backstop). A poll holds `phase`/`expected_next_action`/iterations constant, so without a changing field it would trip that backstop and abandon the wait with a false "frozen" warning. `preview.polls` is part of that signature — bumping it each cycle marks the poll as *progressing*, so the wait survives to `timeout_min`; if you ever stop bumping it, the backstop correctly reclaims the session. The turn stays alive on `auto-continue` between cycles; if it ends, the Stop hook re-invokes you and polling continues.

**1. Resolve the preview URL (bound to the pushed commit).** `HEAD_SHA = git rev-parse HEAD`.
   1. **`gh` auto-detect first.** If `gh` is available and authenticated, read deployment status for the pushed ref — e.g. `gh api "repos/{owner}/{repo}/deployments?sha=$HEAD_SHA"` and the deployment's statuses (`state == "success"`, `environment_url`), and/or `gh pr checks` for a preview/deploy check that exposes a URL. **Bind to the SHA:** accept a deployment only when its `sha`/`ref` matches `HEAD_SHA`. A `success` deployment for an *older* SHA is NOT ready for us — keep polling (a newer deploy for our SHA is still building). Record the matched `deployment_sha`.
   2. **Configured fallback.** If `gh` deployment auto-detect exposed no URL: fall back to `url_template` (`preview_url`) with `{branch}` substituted (skip if empty). Not SHA-verifiable via the provider, so best-effort confirm it reflects the change (asset hash, version string, or simply reachable + recently deployed).
   3. **PR-comment auto-detect (the DEFAULT, zero-config source).** When `preview_autodetect !== false` and a PR exists, **poll the PR's comments/body for a deployment URL** via the sibling `hooks/pr-deploy-url.sh` (locate with the three-probe pattern): `url="$(bash "$pr_deploy_url_sh" --ref "$branch")"`. It returns the first URL from a deploy-bot comment (Vercel/Netlify/Cloudflare Pages/Render/Fly/Railway/Firebase/… host suffixes; extend with `preview_url`'s host or a custom list). This is the same bounded `poll` loop as above — the comment appears a minute or two after the push, so keep polling (bumping `preview.polls`) until it resolves or `timeout_min` elapses. The URL is not SHA-bound (the bot posts per-push), so best-effort confirm reachability before trusting it. This is the source that makes auto-learn work by default when a PR is opened: most projects reveal their preview URL this way with zero settings.
   4. **No URL by `timeout_min`.** If NONE of the sources yields a reachable URL in the bound: in the **explicit** case (`has_preview_deployment` true) record `preview.status = "pending"` and surface (`user-approval`) to resume later. In the **auto-learn** case (`has_preview_deployment` was unset), do NOT nag and do NOT persist a negative: leave `has_preview_deployment` unset, record `preview = { status: "skipped-learned-none", learned: null, verdict: null, at }`, log `{ phase: "phase-7-preview-autolearn", learned: null, at }` to `state.history`, and then **apply ALL THREE terminal guards below** (external-actions, run-metrics AND release) (a declared external action still gates completion even though the preview was skipped, and a configured release step still owes work) — only if there are no declared external actions AND `release_mode` is `skip` do you set `phase: "done"`, `expected_next_action: null` and finish with the normal final summary. Because nothing is persisted, a later post-PR run re-attempts detection — a slow deploy bot or a degraded check (no `gh`/auth/PR) is thus a transient miss, never a permanent `false`; the user sets an explicit `false` to stop the per-run re-check. A repo without a deploy comment must feel exactly like a repo with preview disabled — no failure, no stall, no extra prompt. Never emit FAIL for a missing preview (no preview ≠ a regression).

   **Terminal guards — the external-actions terminal guard, the run-metrics terminal guard AND the release terminal guard (ALL THREE apply to EVERY Phase-7 exit that would otherwise set `phase: "done"` — the `skipped-learned-none` auto-learn case above, and the PASS/FAIL/INCONCLUSIVE verdict terminal in step 4).** Before writing `phase: "done"`, check the run's declared external actions: if any is not yet `applied-verified` / accepted `applied-unverified` / descoped, do NOT go to `done` — set `phase: "external"`, `expected_next_action: "auto-continue"`, and advance to **Phase 8** (the preview outcome is still recorded + reported; Phase 8 owns the terminal state). Only when there are no un-applied external actions does a Phase-7 exit reach `done`. This is the same "external actions gate completion" rule step-12 enforces at the Phase-5 → post-PR fork; it MUST be re-checked at every Phase-7 done-writer so a no-preview / skipped-learned-none run can never short-circuit past a declared external change (the "shipping the script ≠ done" invariant). The **run-metrics terminal guard** (Phase 5 step 4) applies at the same points and for the same structural reason: before any Phase-7 exit writes `phase: "done"`, confirm a `handover-metrics` entry exists in `state.history` and run the metrics step if it does not. A run that reached Phase 7 by resuming a `handoff`/`pending` preview is exactly the path that can arrive here without Phase 5's metrics step having run in this session. The **release terminal guard** (Phase 5 step 4) applies at the same points, and is checked LAST of the three because Phase 9 is the last phase: once external actions are settled and the metrics entry exists, a `release_mode` of `always`/`ask` routes to `phase: "release"` (Phase 9) instead of `done`, and Phase 9 owns the terminal state and the final summary.
   5. **Persist ONLY a positive auto-learn result (only when `has_preview_deployment` was unset).** Auto-learn remembers a *found* deployment; it never records the absence of one — a failure to detect is not proof of absence (a slow deploy bot, or a degraded check with no `gh`/auth/PR, looks identical to a genuine no-preview repo), so persisting a negative would wrongly and permanently disable preview verification on a project that does have one.
      - **A deployment/URL WAS resolved** (steps 1.1-1.3) → `settings.sh set has_preview_deployment true` and record `preview.learned = { value: true, at }` before proceeding to verification (step 2). Future runs then hit the explicit-`true` branch and check every time.
      - **NO deployment found** by `timeout_min` (step 1.4) → do **NOT** persist anything: leave `has_preview_deployment` unset and record `preview.learned = null` (with `preview.status = "skipped-learned-none"`, per step 1.4). A later post-PR run simply re-attempts auto-learn, so a transient miss self-corrects. To stop the per-run re-check on a genuine no-preview repo, the user sets an explicit `false` (honored below, never written by auto-learn).
      - Locate `settings.sh` via the three-probe pattern; write the **project** scope (default). **Fail-open:** the only persist is the positive one — if that `set` errors, log `{ phase: "phase-7-preview-autolearn", learned: true, result: "persist-failed", at }` to `state.history` and continue (next run simply re-learns). Log the success case as `{ phase: "phase-7-preview-autolearn", learned: true, at }` (the non-detection case is terminal in step 1.4, which writes its own `learned: null` history entry). In the **explicit** cases (`has_preview_deployment` was set), skip this step entirely — never overwrite a user's explicit choice.

**2. Verify the change on the preview.** MCP allowance is the same as Phase 3 (read-only by default; `playwright` for browser checks; auth prompts are not verifiers you invoke interactively). Send `bypass` as a request header when set (for deployment-protection tokens).
   - **Reachability / auth.** Fetch the preview URL. **A 401/403 is deployment protection, NOT a genuine failure** — if `bypass` is unset, do not treat it as a pass or a FAIL; record `preview.status = "inconclusive"`, verdict `INCONCLUSIVE`, with the explicit note "preview is auth-protected — set `preview_bypass_header` to a bypass token", and surface. Never silently mask a possible regression behind a 401.
   - **URL-checkable ACs.** For each AC row whose `Verification method` is a URL / `playwright` / `curl` check, re-run it against the **preview URL** (substitute the base). Record each as a `preview.checks[]` entry `{ ac, result, evidence, at }`.
   - **Smoke.** Navigate the preview URL and the routes the change touched; assert they load (HTTP 200 / rendered) and the browser console shows no new errors on the affected pages.

**3. Final verdict.** Compute and record `preview.verdict`:
   - **PASS** — every URL-checkable AC passed against the preview AND the smoke check is clean. `preview.status = "verified"`.
   - **FAIL** — the preview was reachable but a URL-AC or the smoke check regressed. `preview.status = "failed"`. The commit already shipped, so do **NOT** auto-loop back into Phase 4/2 — the preview verdict is negative and fixing the regression is a separate `/auto-task "fix <the preview regression>"` run. Report the verdict prominently with evidence (which AC, observed vs. expected, `preview.checks[]`). Then apply **all three terminal guards** (the paragraph under step 1.4): the **run-metrics terminal guard** first — no `phase: "done"` without a `handover-metrics` history entry, so run the metrics step if this branch was reached by resuming a preview and Phase 5's step never ran in this session — and then the **external-actions terminal guard**: with no declared external action this is terminal — `phase: "done"`, `expected_next_action: null`, so `record-outcome.sh` captures the completed run rather than leaving it to linger as an in-flight "stall"; with a declared external action still un-applied, route to Phase 8 instead (carry the preview FAIL into Phase 8 so its apply confirm-gate shows the failing verdict and the user decides whether to apply on a regressed build); and finally the **release terminal guard** — a configured `release_mode` routes to Phase 9 rather than `done`, carrying the FAIL verdict into the release plan so the user sees they would be tagging a build whose preview regressed. Either way, do not dress a FAIL up as success.
   - **INCONCLUSIVE** — could not reach the preview, auth-protected without a bypass, or the resolved URL could not be SHA-bound. `preview.status = "inconclusive"`. Surface with the reason; do not claim success.

**4. Record + report.**
   - Write `preview` to state with the verdict, url, `deployment_sha`, and `checks[]`. Append the checks to `state.checks[]` (tagged `gate: "preview"`) so the manifest stays complete.
   - Append a `## Preview verification` section to `.auto-task/<branch>/CONTEXT.md` (URL, deployment SHA, verdict, per-check results, any INCONCLUSIVE reason). Save any screenshots under `artifacts/preview-*.png` and a transcript under `artifacts/preview-verdict.txt`.
   - Append a TRACE entry: `operation: auto-task:phase-7-preview`, `outcome: <pass|fail|inconclusive|pending>`, summary covers the URL, verdict, any surfaced reason, and (when auto-learn persisted a positive) the `has_preview_deployment: true` it wrote — a non-detection persists nothing.
   - **Optional PR comment.** Only if `preview_post_verdict_comment === true`: post the verdict as a PR comment via `gh pr comment` (an external write — off by default). Write the comment's prose in the resolved **Comment voice** (see the `## Comment voice` section); the verdict itself (PASS/FAIL/INCONCLUSIVE) and any evidence links stay factual. Otherwise report the verdict only to the user + CONTEXT.md.
   - **Terminal state (or handoff to Phase 8).** A **completed** verification is terminal UNLESS the run has declared external actions — in which case route to **Phase 8** instead of `done` (set `phase: "external"`, `expected_next_action: "auto-continue"`; the preview verdict is still reported). With no external actions: subject to the **run-metrics terminal guard** (confirm the `handover-metrics` entry exists first) and the **release terminal guard** (`release_mode` is `always`/`ask` → route to `phase: "release"` / Phase 9 instead, which then owns the terminal state; the preview verdict is still reported), on PASS, FAIL, or INCONCLUSIVE set `phase: "done"`, `expected_next_action: null`, and give the user the final summary (PR URL + the preview verdict + where artifacts live) — so `record-outcome.sh` records the run and telemetry never misclassifies a decided verdict as a perpetual stall. An **incomplete** verification stays in-flight: on `pending` (timeout) or `awaiting` (handoff), leave `phase: "preview"` with `expected_next_action: "user-approval"` (surfaced) — the run is not `done` until a resume finishes the check (re-check once the deploy lands). The distinction is completion, not success: a FAIL is done (nothing more to do automatically; the fix is a new run), whereas a `pending`/`awaiting` genuinely has verification still owed.

**No preview infra?** With `preview_autodetect` at its `true` default, Phase 7 auto-learn is *attempted* on each undecided post-PR run, but a repo whose PRs get no deploy comment resolves no URL, so Phase 7 records `skipped-learned-none`, **persists nothing**, and ends exactly as if preview were off — no failure, no stall, no extra prompt. (Exception: if the run *also* declared an external action, the external-actions terminal guard routes it into Phase 8 rather than `done` — a skipped preview never lets a declared external change slip past unapplied.) Auto-learn never writes a negative, so the setting stays unset and the run re-attempts detection next time (a slow or one-off-degraded check can never leave a permanent wrong `false`). The cost of that safety is a bounded re-check each post-PR run on a genuine no-preview repo — **set `has_preview_deployment: false` explicitly to skip instantly with no polling from then on** (an explicit value is honored and never overwritten). A repo that opens no PR (e.g. this plugin lands directly on `main`) never enters Phase 6 or Phase 7 at all. To opt out of auto-learn entirely, set `preview_autodetect: false` (or set `has_preview_deployment` explicitly either way).


## phase8-body — relocated verbatim from SKILL.md


The honesty rung for tasks whose real-world outcome needs a change in an **external system** — a CMS, a feature-flag service, a data migration applied to live, a third-party API config — beyond shipping code. **Shipping the script is not the task being done**: this phase actually applies the change and verifies nothing broke, and — until it does — the run is explicitly NOT `done`. It runs LAST, after Phase 7, whenever the run has **declared external actions** (Phase 1, see the AC contract's external-action rule). A run with no declared external actions skips it entirely (`external: null`, behaves as v0.17.1).

This phase makes **NO new authored commit** — the code shipped in Phase 5 (and any bot-fixes in Phase 6). It applies a change to a system *outside* the repo, then observes. So `enforce-gates.sh` is not involved; the only mechanical contract is the Stop hook, satisfied by keeping apply/poll waits on `auto-continue` and every human surface on `user-approval`.

Read the live settings (do not trust only the Phase-1 snapshot): `mode = settings.get external_actions_mode` (default `ask`), `timeout_min = external_actions_timeout_min` (30), `interval_sec = external_actions_poll_interval_sec` (60).

**1. Gate + push-held branch.** If no external actions were declared → `external = { status: "none", at }`, terminal per step 12's ladder (nothing to do). If the Phase-5 push was **HELD** (code not shipped) → do NOT attempt to apply (external changes usually depend on the shipped code) and do NOT emit the step-3 human runbook (that is the `awaiting-external` handoff, where the human is the applier — the wrong owner here): record `external.status: "declared"` (auto-task remains the applier; it is only deferring until the code ships), mark not-done, hold `phase: "external"`, `expected_next_action: "user-approval"`, and surface a **push-held-specific** message — "The external change is NOT applied: the code hasn't shipped yet. Push the code (or resume `/auto-task` once it's pushed) and I'll apply + verify it. I have **not** handed this to you to apply manually." Applying happens on a later resume once the code ships, via step 6's `declared` path (auto-task applies, skipping `external.applied[]`). Do NOT flip to `awaiting-external` here — that status means a human was handed the apply, which is not the case for a push-held deferral, and conflating the two reopens the double-apply hazard (a human who applied a `declared` action manually would not be in `external.applied[]`).

**2. Apply the external action(s) (code shipped).** Load the external-action manifest (the `external.actions[]` produced during implement + Phase-1 declaration).
   - **Irreversibility-aware consent (safety-critical).** Any action with `reversible: false` ALWAYS requires an explicit per-run confirmation that NAMES it as irreversible/un-undoable — regardless of `mode`. The `ask` prompt must list which actions are irreversible (not a generic "permission + credentials").
   - **`ask` (default):** one `AskUserQuestion` for permission + credentials (set `expected_next_action: "user-push-prompt"` — this is the single allowed Phase-8 prompt, like the Phase-5 push). Word it plainly per the `user-facing-voice` rule in `references/phase-1-preamble.md`: *"This change needs <n> thing(s) done outside the codebase before it works. Want me to run them?"* (header chip: `Run steps`), listing each action in one line of ordinary language — what it does to what system — and marking any that **cannot be undone** with those words, in the option description as well as the list. Options: **"Yes, run them"** / **"No, give me the steps to run myself"**. On yes → run. On decline → fall to the runbook (step 3).
   - **`auto`:** run without the prompt — but ONLY for `reversible: true` actions AND only if creds/target are reachable. Any `reversible: false` action still prompts; if creds/target are unreachable, **degrade to `runbook`** (never silently fail an un-runnable auto).
   - **Running.** Apply actions **in order**, each bounded (Monitor / bounded `curl`), recording each success to `external.applied[]` with evidence. On resume of THIS auto-run path (status `declared` → applying), the apply loop MUST consult `external.applied[]` and **SKIP already-applied actions** — never re-run a non-idempotent/irreversible action (e.g. a migration) a second time. (This guard is sound only because on the auto-run path auto-task is the applier and records every apply itself; a human-applied `awaiting-external` action is handled by step 6's verify-only resume, never this loop.) Set `external.status: "applying"`. If an applied action's external effect is asynchronous (a reindex, a deploy-triggered migration, an eventually-consistent write), auto-task MAY poll the external system in-session until it settles before verifying — each poll cycle bumps `external.polls` and waits `interval_sec` via a bounded mechanism (the **Monitor** tool; foreground `sleep` may be blocked), bounded by `timeout_min`; this is the one Phase-8 state that advances `external.polls` in the anti-stall signature. Capture output to `artifacts/external-<id>.txt`.
   - **Credential hygiene.** Prefer creds supplied via an environment variable / secret-file *reference* the script reads — NOT pasted inline — and say so in the prompt. The declared `actions[].script` MUST carry a credential *reference* (an env-var name / secret-file path), never an inline secret; if a raw secret ever appears in it, redact it before persisting the manifest. Creds are NEVER written to STATE, TRACE, CONTEXT, `artifacts/`, or the PR. **Redaction applies to EVERY recorded sink, not just artifacts** — before writing `external.applied[].evidence` / `external.verify[].evidence` (→ STATE.json + `state.checks[]`), the CONTEXT `## External actions` section, any transcript under `artifacts/`, or a PR body/comment, redact secret-shaped tokens (bearer/API-key/password-shaped strings) from the command + output first. Record the *shape* of the evidence (command with the secret masked, exit status, confirmation), never the secret itself. Residual caveat: an inline-pasted secret can still land in the raw session transcript, so the reference-not-paste path is the documented default.
   - **Partial-failure recovery.** If an action fails mid-sequence → STOP, do NOT auto-continue; record the partial state, set `external.status: "failed"`, surface which actions applied and each's `rollback` steps (flagging any `reversible: false` as un-undoable), and hand to the user. Never leave a partial state unreported.

**3. Runbook (mode `runbook`, user-declined, or creds/target absent).** Emit a **paste-ready runbook**: per-action system, the exact command/steps, how to verify it took, and a **Rollback / recovery** subsection (per action: its `rollback`, or "IRREVERSIBLE — cannot be undone"). Set `external.status: "awaiting-external"`, `phase: "external"`, `expected_next_action: "user-approval"`, and surface: "Code shipped; the external change is NOT applied yet — apply it via the runbook, then resume `/auto-task` and I'll **verify it took (I will not re-apply)**." Then **STOP and wait for the resume** — this is a human handoff, so auto-task does NOT poll in-session (it cannot detect when a person finishes a runbook; polling would only burn turns). `external.polls` is NOT bumped here; the run yields on `user-approval` and step 6's resume path resolves it by verifying. (Contrast the in-session `auto`-run settle-poll in step 2, which is the only Phase-8 state that bumps `external.polls`.)

**4. Post-apply verification.** After applying (set `external.status: "verifying"` for this step), re-run each external-action AC's verification method + a smoke check against the affected system. Record each to `external.verify[]` and append to `state.checks[]` (tagged `gate: "external"`). `applied-verified` if all pass; `applied-unverified` if applied but a check could not confirm (surface — never fake a pass). MCP allowance is the same as Phase 3/7 (read-only by default).

**5. Clear the not-done marking on success + record.** The Phase-5 "⚠ NOT DONE until applied" banner was written pre-application. On `applied-verified` (and on an accepted `applied-unverified`/descope that reaches `done`), Phase 8 MUST **update the already-published PR** (via `gh pr edit` / `gh pr comment`) + CONTEXT.md + append a TRACE entry to REPLACE the not-done banner with an "external changes applied + verified" confirmation. Leaving a completed run showing a stale NOT-DONE PR is a bug. Append a `## External actions` section to CONTEXT.md (systems, what was applied, verify results, any rollback notes). Save transcripts under `artifacts/external-*.txt`.

**6. Terminal state.** Subject to the **run-metrics terminal guard** (Phase 5 step 4) — confirm the `handover-metrics` history entry exists before writing `phase: "done"`, and run the metrics step first if it does not; a run resumed straight into Phase 8 from `awaiting-external` is a path that can reach `done` without Phase 5's metrics step having run in this session. `applied-verified`, accepted `applied-unverified`, `none`, or an explicit user descope → **the release step is applicable? → set `phase: "release"`, `expected_next_action: "auto-continue"` and advance to Phase 9** (which then owns the terminal state; do NOT report a final summary yet). Otherwise → `phase: "done"`, `expected_next_action: null`, final summary (PR URL + external-actions applied/verified + artifacts). `declared`/`awaiting-external` (in-flight) or `failed` (surfaced) → `phase: "external"`, `expected_next_action: "user-approval"` — the run is NOT `done`. **Resume re-entry — who is the applier decides re-apply vs verify (double-write guard):**
   - **`declared`** — auto-task is the applier (it deferred only because the push was held). Resume APPLIES once code ships, via step 2's apply loop, which SKIPs any action already in `external.applied[]`. Because auto-task performed (and recorded) every apply on this path, `external.applied[]` is authoritative and the skip guard is sound.
   - **`awaiting-external`** — auto-task HANDED the apply to a human (runbook / declined / creds absent). The human is the applier, so `external.applied[]` does NOT track it and can NEVER be trusted to gate a re-apply. Resume therefore goes **straight to post-apply verification (step 4) — auto-task MUST NOT re-run the script**. If verification confirms the change took → `applied-verified`. If it cannot confirm (not applied yet, or unverifiable) → stay `awaiting-external` and re-surface the runbook; never auto-apply a handed-off action. This is the fix for the double-apply hazard: an action auto-task did not itself apply is never auto-applied on resume.
   - **`applied-unverified`** — re-run post-apply verification ONLY; do NOT re-apply.
   - **`failed`** — surfaced for the user (partial state + rollback); auto-task does not auto-retry an external write.
   Mirror the Phase-7 `handoff` resume anchor. The invariant: **auto-task auto-applies an external action at most once, and only on a path where it is itself the applier (`declared`/in-session auto-run); a human-owned (`awaiting-external`) apply is only ever verified, never repeated.**

**No external actions?** The default. A task that touches only code declares none, `external` stays `null`, Phase 8 is a no-op, and the run reaches `done` exactly as before. Detection + the not-done marking are always-on honesty; only *live auto-execution* is gated by `external_actions_mode`.
