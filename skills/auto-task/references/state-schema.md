## state-object-notes — relocated verbatim from SKILL.md

**`gates.gate_b` pass-accounting fields (`passes[]`, `verified_diff_sha`, `allowance_acked`) and `gates.loop_budget.park_non_blocking`.** All additive and backward-compatible: **absent `passes[]` counts as zero passes**, an absent or empty `allowance_acked` object as no grant for any scope, absent `verified_diff_sha` as "pass 1 of this scope", and absent `park_non_blocking` as `false` — so an in-flight run that predates these fields behaves exactly as it did, mirroring the legacy tolerance the loop-budget gate already applies to a missing `effort.tier` or `iteration` object. Read by **no hook**: a Gate B pass is an `Agent` spawn, and `hooks/hooks.json` registers `PreToolUse` only for the `Bash` matcher, so no hook can observe one — identifying a spawn by its `label` is forbidden besides, since the run label is cosmetic and "never changes control flow". The cap is therefore a model-honored contract whose mechanical backstop stays where it already works: `enforce-gates.sh`'s commit-time block (`gate_b.passed` or `skipped_reason`, plus the fix-loop budget) and `prevent-mid-protocol-stall.sh`'s turn-end release. `ARCHITECTURE.md`'s gate table — the authoritative enumeration of what the hook reads — is unchanged by these fields.

Per-field semantics:

- **`passes[]`** — one entry per adversarial pass, `{ n, scope, blockers, required, followups, reopened, self_inflicted, fixed_lines, diff_sha, at }`. `reopened` is the count of findings that met the Step-2 reopen test — **the convergence test's basis, and the only count it compares across passes**; `blockers`/`required` are the raw label counts, which that test deliberately does not use. `scope` is `main` for the ordinary Phase-4 → Gate-B loop, or `regate:docs` / `regate:merge` / `regate:bot-fix` / `regate:release` for the four sites that reset the gate after the main loop. **Counting is per scope**, which is the whole point: the main loop's cap (`lb_gate_b_cap`) and each re-gate's allowance (`lb_gate_b_regate_cap`) are separate budgets, because a shared one would let a run that spent its main-loop passes never re-earn `gates.gate_b.passed` and deadlock the handover commit. A re-gate allowance is **per site per run and is not renewed** when a site executes again.
- **`fixed_lines`** — `[{ path, hashes: [...] }]`, one hash per line a pass's fixes **added**. It exists so `self_inflicted` attribution is mechanical rather than a judgment: a later finding is self-inflicted when the current content at its cited `file:line` hashes to one of these. **Content-addressed on purpose — never line numbers.** A subsequent fix that edits the same file above the hunk shifts every line below it, so stored coordinates would both miss real self-inflicted findings and invent false ones.
- **`self_inflicted`** — true when this pass found a defect inside a previous pass's fix. The **second** such pass (not necessarily consecutive) surfaces to the user. It is a distinct signal from "the loop is long": it says the fixes have become the defect source, which is what the measured runs showed when blockers first appeared at passes 3 and 5 rather than pass 1.
- **`verified_diff_sha`** — the diff boundary a pass covered, computed with the **byte-identical** pinned-flag formula `gates.code_review.reviewed_diff_sha` uses, so pass N+1 reviews only the delta. **Set it when a pass SPAWNS, from the same diff handed to that pass, and leave it untouched until the next pass spawns** — a boundary refreshed at the *end* of a reopening pass is taken from the post-fix tree, so the next pass's delta comes back empty and the self-inflicted defects it exists to catch are the one thing it never sees (`references/phase-3-gates.md` Step 1). Unlike `reviewed_diff_sha` it is **not** bound by a hook — no staleness check reads it — so it is a scoping input, not a commit gate.
- **`allowance_acked`** — extra passes the **user** granted at an over-cap surface, as an **object keyed by `scope`** (`{"main": 1}`), never a bare integer. The key is load-bearing: a scalar would be added to whichever scope was being evaluated, so a `+1` granted at the main-loop surface would silently raise **every** re-gate site's allowance from 2 to 3 — handing out four grants the user never gave, and breaking the "its own allowance, one per site per run" property the re-gate design depends on. An absent key counts as 0. Like `park_non_blocking` and every other gate flag it is a checkable artifact, **never self-granted**; writing either without asking is the same contract violation as flipping `gates.code_review.passed` without running the review, and it would convert the one mechanism that lets a user end the loop into a self-authorized bypass.

**`gates.code_review` round-accounting fields (`rounds[]`, `deferred[]`) — the Phase-4 sibling of `gate_b.passes[]`.** Additive and backward-compatible on the identical terms: **an absent or empty `rounds[]` counts as zero rows** and an absent `deferred[]` as nothing deferred, so an in-flight run predating these fields behaves exactly as it did. Both defaults err toward doing the work rather than skipping it — zero rows means the convergence test cannot fire (no prior round to compare) and the deferred batch has not been spent. Contract: `references/phase-3-gates.md` ("phase-4-round-mechanics").

Why they exist: Gate B was bounded in 0.29.0 and the churn moved to Phase 4, which had no grading, no record and no in-loop bound. In the two runs in the clone-wide outcomes ledger, `iteration.review` reached **9** and **5** against a STANDARD cap of 4, while the nine-round run's `gate_b.passes[]` holds exactly two rows, both `reopened: 0`.

- **`rounds[]`** — one entry per Phase-4 review round, `{ n, blockers, required, reopened, deferred, followups, batch, diff_sha, at }`, appended on **every** exit including a reopen. `n` is `1 +` the prior row count. `reopened` is the count of findings that met the Step-A reopen test — **the convergence test's declared basis, and the only count it compares across rounds**; `blockers`/`required` are the raw label counts, which that test deliberately does not use, because a deferred `blocker` cost no round. `deferred` is the count this round added to `deferred[]`. `batch: true` marks the single round that applied the deferred batch.
- **`deferred[]`** — `blocker`/`required`-labelled findings that failed the reachability test: `{ label, location, note, at }`. **Deferred is not parked** — Gate B parks such a finding permanently, Phase 4 still fixes it, in one batch once a round comes back with zero reopening findings **and the batch is still unspent**. The batch is **spent once per run**, and its spent-marker is the existence of a `rounds[]` row with `batch: true` rather than a separate boolean, which could disagree with the record. Nothing clears `deferred[]`, so the unspent condition is what bounds batch entry — an entry test without it re-fires on every later zero-reopening round.
- **`reviewed_diff_sha`** (pre-existing field; the pinned-flag formula lives here so both the spine and Gate B's `verified_diff_sha` above can cite one copy) — pins the exact diff a clean round covered: `git diff --no-color --no-ext-diff --no-textconv --no-renames --diff-algorithm=myers --src-prefix=a/ --dst-prefix=b/ <base> | git hash-object --stdin`, where `<base>` is `state.base`. The flags MUST match `enforce-gates.sh`'s verbatim — they pin the diff text against git-config drift so an unchanged tree always hashes the same, and omitting them risks a spurious staleness block. The hook recomputes the same hash at commit time and **blocks the commit if it differs**, i.e. if any tracked code changed after the review went clean. Recompute and overwrite it on every subsequent clean round (e.g. after a Gate B fix or the deferred batch forces a re-review). Never copy a stale value forward; set it from a freshly-computed hash only when the round is genuinely clean, exactly like the boolean flags.

**Read by one hook, and only for movement.** `enforce-gates.sh` reads none of these — a review round is a `Skill` invocation and `hooks/hooks.json` registers `PreToolUse` for `Bash` only, the same observability limit `gate_b.passes[]` has. `prevent-mid-protocol-stall.sh` reads **`rounds | length`** as one field of its no-progress fingerprint, for the reason its own comment already gives for the poll counters and `loop_budget.acked_through`: a round that defers everything writes a row, applies no fix and bumps no counter, so every other signature field stays constant and the round would be miscounted as a frozen turn-end. It reads the length only — never the contents, never a magnitude judgment. `ARCHITECTURE.md`'s gate table (the authoritative enumeration of what `enforce-gates.sh` reads) is unchanged by these fields.

**`gates.hygiene` object (the diff-hygiene gate's false-positive override).** Additive and backward-compatible: an absent `gates.hygiene`, an absent or empty `acked[]`, a non-array `acked`, or an entry missing either key all count as **no grant**, so the block they would clear stays in force. That direction is deliberate — every unreadable shape must preserve a block, never lift one.

`enforce-gates.sh` **does** read this object (unlike `gate_b.passes[]` above, which no hook can observe): it is the only thing that clears a `fail` row from `hooks/checks.sh` at commit time. See `ARCHITECTURE.md`'s gate table for the authoritative row.

- **`acked[]`** — `[{ check, diff_sha, reason, at }]`. `check` is the **row name** the grant covers, drawn from `checks.sh`'s vocabulary (`secret-scan` / `conflict-markers` / `test-integrity`), plus the sentinel **`scanner-unavailable`** for a block raised because the scanner could not inspect the diff at all (all-`skip`, a missing `checks.sh`, unusable output). A grant is **per check**: an ack naming `conflict-markers` does nothing for a `secret-scan` finding, so one false positive cannot silently wave through a different, real one.
- **`diff_sha`** — the hash the grant is pinned to. An entry counts only while it equals the *current* hash, so a grant for one tree cannot cover a later one — the `reviewed_diff_sha` lesson applied to acks. **Any subsequent edit therefore invalidates the ack and re-blocks, and that is intended**, exactly as a post-review edit forces a re-review.
  - **It is deliberately NOT the `reviewed_diff_sha` formula** (`git diff <base>`), even though that is the obvious choice. That formula sees neither untracked nor index-only content, so a grant survived edits the scanner could plainly see: measured, an ack for a documented docs placeholder still cleared a **new untracked file carrying a real credential** — the hash did not move and the commit was allowed while the scanner reported two matches. A path staged and then deleted from the worktree is invisible to it for the same reason.
  - **The pin therefore covers exactly the scanner's field of view**, hashed from four parts: `git rev-parse HEAD` (moves on any commit), `git diff <pinned-flags> HEAD` (tracked worktree content), `git diff --cached <pinned-flags> HEAD` (index content, including a staged-then-deleted path that the previous part cannot see at all), and one `<path>\t<blob-hash>` line per untracked file (the untracked path set *and* its content). `git status --porcelain` is not a substitute for the content-bearing parts: it emits status codes and paths but never content, so rewriting the bytes of an already-listed (` M …` / `?? …`) file would leave a porcelain-only pin identical.
  - Being **base-independent** is also what makes the override reachable when `state.base` does not resolve — the headline reason to need one. An earlier version pinned to `git diff <base>` with a fallback, which needed a ref-resolvability probe because `git diff <unresolvable-ref>` prints nothing yet the pipe still hashes *empty input*, yielding the empty-blob hash rather than an empty string. One formula removes that trap along with the branch. **Do not "simplify" the hook's resolvability probe to a non-empty test on the hash:** `git diff <unresolvable-ref>` prints nothing but the pipe still hashes empty input, yielding the empty-blob hash rather than an empty string, so a non-empty test reads total failure as a successful hash of an empty diff.
- **`reason`** — free text: why this row is a false positive. Not machine-read; it exists so the grant is *reviewable* after the fact, which is the entire value of the mechanism.

**Trust model — identical to `gates.loop_budget.acked_through` and `gate_b.allowance_acked`, and the same warning applies with the same force.** The *block* is mechanical; the *ack* is prose-trusted, so a model that self-grants one defeats the gate. Writing it without asking is the same contract violation as flipping `gates.code_review.passed` without running the review. What the mechanism buys unconditionally is narrower but real: a **silent** secret-leak or test-gutting becomes impossible, because clearing one requires leaving a durable, diff-pinned, reviewable record that says so. Hardening acks generally is a separate problem (observed tool evidence), not something this object solves.

**`clarify_forward_pending` object.** Additive and backward-compatible (absent on pre-existing runs → treated as `{ pending: false }`). Written only by the Phase-1 clarify **Step 4b-forward** (`kind: "clarify"`) and the approach-fold forward branch (`kind: "approach"`) to mark that the user chose to forward the open questions/decision as a comment and the run is paused for the owner's answers; the `kind` discriminator routes the resumed answer to the correct record (Clarifications vs `## Approach`); cleared on resume once the answers are recorded (see Phase 1 clarify "Resume detection"). Read by **no hook** — it neither gates a commit (`enforce-gates.sh`'s gate-deciding reads are `gates.*`, `effort.tier`/`iteration.fix`/`iteration.review`, and `base`) nor participates in the anti-stall signature; the Stop hook already allows the pause because `approved:false` during Phase 1.

**Run-metrics objects (`estimate`, `actuals`, `quality`, `checks`).** These are additive and populated by the run-metrics helpers + orchestrator (see "Run metrics" wiring in Phases 1, 3, and 5). They never gate a commit — `enforce-gates.sh`'s gate-deciding reads are `gates.*`, `effort.tier`/`iteration.fix`/`iteration.review` (the loop-budget gate) and `base` (the staleness check), and none of the run-metrics objects (see the gate table in ARCHITECTURE.md for the authoritative list of what it reads). **`actuals` does carry a Phase-5 obligation** — the **run-metrics terminal guard** (see Phase 5 step 4) — but it is enforced by the phase contract, not by a hook: no writer of `phase: "done"`, in any phase, may write it without a `handover-metrics` entry in `state.history` showing the metrics step ran. `estimate`/`actuals` token+time fields are `null` (never `0`) when a measurement could not be taken — or, for the duration, when one **was** taken and **rejected** — so the telemetry reader (`auto-task-stats`) EXCLUDES them from the actual/estimate ratio instead of dividing by zero. **`actuals.duration_min` is measured, not narrated:** it comes from the hook-stamped run clock (`.auto-task/<branch>/.run-clock.json`, written from `date -u` by `hooks/stamp-run-clock.sh`; the derivation and its bounds live in `hooks/lib/run-clock.sh`), and a span that is negative or exceeds 12h is rejected to `null` rather than recorded. Two consequences worth stating because they change existing contracts: the ledger/telemetry `duration_min` used to be a number on every row (it fell back to `0`) and is now **nullable**; and a rejection must never be expressed as a bare nullable value in the row builders, because jq's `//` treats `null` identically to absent and would silently substitute the history-derived number the rejection exists to suppress — hence the three-state (`ok`/`rejected`/`absent`) verdict those builders branch on. `quality` is a **signals panel, not a composite score** (the maintainability read is reused verbatim from the code-review verdict; per-run business impact / collaboration / long-term maintainability are explicitly out of reach and listed under `not_measured`). `checks[]` is the comprehensive checks manifest surfaced in the final summary. `quality.satisfaction`/`quality.correctness`/`quality.comment` are the user's answers to the Phase-5 satisfaction ask (see "Remote telemetry" below and Phase 5 step 8); they are `null` on every run where telemetry is off (the ask is skipped) and are the ONLY `quality` fields sourced from a human, not derived. `quality.comment` is free text — sent verbatim (capped 500 chars) and thus the one potentially-identifying field, so it is consent-gated behind the same prompt.

**Settings + preview + bot_review + external objects (`settings`, `preview`, `bot_review`, `external`).** All additive. `settings` is the Phase-1 snapshot of the resolved project settings (see "User settings" below) — a record of what the run read, not a live source; it is invisible to every hook. `preview` is populated only by Phase 7 (preview verification); `bot_review` only by Phase 6 (bot-comment review); `external` is **seeded at Phase-1 declaration** (its `actions[]` manifest + `status: "declared"`, per AC-contract rule 11, refined during Phase-2 implement) and its runtime fields (`applied[]`, `verify[]`, terminal `status`, `polls`) are written by **Phase 8** (external-change application). All three are `null` on every run where their phase does not execute (the default, since `has_preview_deployment` defaults to `false`, `bot_review_autofix` defaults to `false`, and a run has no declared external actions). `enforce-gates.sh` reads none of them (its gate-deciding reads are `gates.*`, `effort.tier`/`iteration.fix`/`iteration.review` for the loop-budget gate, and `base` for the staleness check — see the gate table in ARCHITECTURE.md for the authoritative list of what it reads — and it handles any phase string generically). Two Stop hooks read these objects. `prevent-mid-protocol-stall.sh`: its soft-lock signature includes `preview.polls`, `bot_review.polls`, AND `external.polls` so the long-lived `auto-continue` poll waits of Phases 7, 6, and 8 (for Phase 8, the step-2 `auto`-run settle-poll — NOT the `awaiting-external` human handoff, which yields on `user-approval` and does not poll) are recognized as *progressing* each time the respective poll counter bumps, instead of being misread as a frozen run. And `send-telemetry.sh`: at `phase==done` it reads `.preview.verdict` AND `.external.status` into the anonymized payload (see "Remote telemetry" below); `record-outcome.sh` mirrors `.external.status` onto its local row. No other hook reads these objects — `enforce-gates.sh` and the rest are phase-agnostic; the anti-stall signature line + those two payload fields are the only edits the external object required.

**`external` object (Phase 8 — external-change application).** Additive; absent on every run with no declared external actions (treated identically to v0.17.1 — Phase 8 is a no-op). Its `actions[]` manifest is **seeded at Phase-1 declaration** (AC-contract rule 11) and refined during Phase-2 implement; **Phase 8** then applies those actions and writes the runtime fields (`applied[]`, `verify[]`, terminal `status`, `polls`). It tracks external-system changes a task requires beyond shipping code (CMS edits, feature-flag toggles, a data migration applied to live, third-party API config). `status` uses the canonical enum in the schema above — `skipped-disabled | none | declared | awaiting-external | applying | verifying | applied-verified | applied-unverified | failed` — and every other site that names an external state MUST draw from exactly this set. Each `actions[]` entry carries `reversible` (`true|false`) and `rollback` (undo steps, or the literal `"IRREVERSIBLE — cannot be undone"` when `reversible:false`) so an un-undoable live mutation is representable and the runbook / partial-failure path can warn about it. **Credentials are NEVER written here** (nor to TRACE/CONTEXT/artifacts) — see the Phase-8 credential-hygiene rule.

**`release` object (Phase 9 — release step).** Additive; `null` on every run that never enters Phase 9 — which is every run where `release_mode` is `skip` (the default), since the release terminal guard is a no-op there and no earlier phase routes in. So a default run behaves exactly as it did before this object existed. (The one way a `skip` run can still populate the object is entering Phase 9 on an `always`/`ask` reading and then resolving `skip` from a live re-read — settings changed mid-run, or a resume — which is what step 2's `skipped-disabled` write records.) Written only by **Phase 9**. `status` uses the canonical enum in the schema above — `skipped-disabled | skipped-invalid-value | skipped-skill-absent | deferred-pr | nothing-to-release | runbook | in-progress | resolved-re-derive | applied | partial-failure | failed | declined` — and every other site that names a release state MUST draw from exactly this set. Five of those are the distinct **degrade** paths (`skipped-disabled` for `skip`, `skipped-invalid-value` for a hand-edited value, `skipped-skill-absent` for a missing skill, `runbook` for an unset `release_command`, `failed` for a non-zero release command), each recorded separately so a skipped release is never indistinguishable from a failed one. `bump` + `bump_signal` record the derived level **and its evidence**, so a reviewer can see why `minor` rather than `major`. `unwind` persists the exact undo commands (with the `reset` precondition) that were handed to the user, so a resumed session can re-surface them without re-deriving. **No hook reads this object** — `enforce-gates.sh` keys on `gates.*` and handles any phase string generically, and Phase 9 never polls, so it contributes no field to the anti-stall signature (unlike `preview.polls` / `bot_review.polls` / `external.polls`).

**Terminal vs in-flight for `phase: "release"`.** Same honesty rule as Phases 6-8. **Completed** and therefore TERMINAL (`phase: "done"`, so `record-outcome.sh` records it): `applied`, `nothing-to-release`, `declined`, `runbook`, `deferred-pr`, and every `skipped-*`. A `runbook` / `deferred-pr` outcome is genuinely *finished* from auto-task's side — it handed over paste-ready steps and owes no further work — which is why, unlike Phase 8's `awaiting-external`, it does not linger as in-flight. **SURFACED** (stays `phase: "release"`, NOT `done`, NOT recorded): `in-progress` (a mutating action was interrupted), `partial-failure` (a commit with no tag — the state most likely to be misread as success), and `failed`. **None of the three is auto-resumed, auto-retried, or auto-reverted** — Phase 9 hands the recorded state and the undo commands to the user and waits (step 1). That is the deliberate scope choice: the phase guarantees it never silently re-cuts and never reports success, and leaves the judgement call to a human. Once the user resolves it and says so, auto-task verifies the observable state itself and records the honest outcome via step 1's **resolution rule** — `applied` (the release is complete), `declined` (it was cut and then unwound, and the user does not want it re-cut), or (when nothing was cut and a release is still warranted) a re-entry into step 2. **Note `declined`, not `nothing-to-release`:** the latter is routed to a live re-read on the premise that nothing was ever cut, which is false on the undone path — see step 1's resolution rule, which is the single authority for this vocabulary. All three surfaced states share that one rule, so none of them can strand the run permanently non-terminal.

**Terminal vs in-flight for `phase: "bot-review"` / `phase: "preview"`.** The hooks treat any non-`"done"` phase as an active run, and `record-outcome.sh` fires only at `phase: "done"`. Phases 6 and 7 therefore map their outcomes so the ledger/telemetry stay honest. **Phase 7:** a **completed** verification — verdict `PASS`, `FAIL`, or `INCONCLUSIVE` — is TERMINAL (`phase: "done"`), so it is recorded and never lingers as "stalled"; an **incomplete** verification — `awaiting` (handoff, deferred) or `pending` (deploy not ready by timeout) — stays `phase: "preview"` and is correctly counted as in-flight until a resume finishes it. A `FAIL` is done-with-a-negative-verdict (fixing the regression is a *new* run), not an open loop. **Phase 6:** a completed bot-review (`applied` / `no-action` / `skipped-*`) hands off to Phase 7 or to terminal `done`; it only stays `phase: "bot-review"` while genuinely in-flight (polling, or a surfaced blocker awaiting the user). **Phase 8:** a **completed** external-change application — `applied-verified`, an accepted `applied-unverified`, `none`, `skipped-disabled`, or an explicit user descope — is TERMINAL (`phase: "done"`), so it is recorded. An **un-applied** external action — `declared` (code not yet shipped, e.g. push held) or `awaiting-external` (shipped, handed to a human to apply) — stays `phase: "external"` and is correctly in-flight (NOT `done`, NOT recorded) until a resume resolves it (`declared` → auto-task applies + verifies; `awaiting-external` → auto-task verifies the human's apply, never re-applies — see Phase 8 step 6). `failed` (apply or post-apply verify failed) is surfaced for the user, not auto-looped. This is the exact honesty rule that makes "shipping the script ≠ done" mechanical: a task with an unapplied external change never reaches `done`.

**Autonomy + merge-gate objects (`autonomy`, `landing`, `gates.merge`, `assumptions`).** All additive and backward-compatible (absent on pre-existing runs → today's behavior). `autonomy` (`supervised`|`autonomous`) and `landing` (`pr`|`direct`) are a Phase-1 snapshot of the resolved policy for the run (from `settings.sh`), recorded so the pipeline and telemetry read a stable value even if settings change mid-run; defaults (`supervised`/`pr`) reproduce the pre-feature behavior exactly. `gates.merge` is the **one mandatory gate**, and — alongside `gates.loop_budget` (the loop-budget gate, added later) — one of only two objects from this family that a hook reads: `enforce-gates.sh` blocks a land action (`git push` / direct-to-main `git merge`) when `gates.merge.required == true` and `gates.merge.acked != true` (absent object → skipped, exactly like the legacy `base`/`reviewed_sha` skip). `assumptions[]` is an append-only ledger of decisions the run made to stay unattended (auto-approved ambiguities, thinly-cited calls, drift auto-continues, accepted risks); it is read by NO hook — it is surfaced to the human at the merge gate (or the PR body) so optional plan-approval never means "silently decided." See "Autonomy modes & the merge gate" below.
