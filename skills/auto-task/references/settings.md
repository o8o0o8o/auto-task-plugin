## settings-table — relocated verbatim from SKILL.md

Per-project, per-user configuration for the pipeline. **Optional and fully defaulted** — a project with no settings file behaves exactly as before. Settings are read (never written) by the orchestrator via the `hooks/settings.sh` helper.

- **Where they live (deliberately OUTSIDE the user's repo).** `${AUTO_TASK_HOME:-$HOME/.claude}/auto-task/<project-key>/settings.json` (i.e. under `~/.claude/auto-task/` by default), where `<project-key>` is `<repo-basename>-<12-char-hash>` derived from the git **common dir** (`git rev-parse --git-common-dir`) — which every linked worktree of one clone shares. So settings are **project-specific and per-clone** (all worktrees of a repo resolve to the same file), and a setting **never alters the tracked repo** (nothing is written inside the working tree; it never shows in `git status`). This satisfies the "keep them elsewhere, don't touch my repo" contract.
- **Format: JSON.** A flat object of `key: value`. Any key the user omits **falls back to the built-in default** (the single source of truth is the `default_for` table in `hooks/settings.sh`). A missing file, malformed JSON, or an absent key all resolve to defaults — the helper is fail-open and never errors a run. Note `false`/`0`/`""` file values are honored (the helper tests key *presence*, not jq's `//`).
- **Reading them.** Locate `hooks/settings.sh` via the same three-probe pattern used for `check-version.sh`/`estimate.sh` (`CLAUDE_PLUGIN_ROOT` is empty in the Bash-tool env), substituting `hooks/settings.sh`. Then:
  - `bash "$settings_sh" get <key>` → the value (file override, else default).
  - `bash "$settings_sh" all` → the merged (defaults ⊔ file) JSON.
  - `bash "$settings_sh" path` → the resolved file path (for surfacing to the user).
  - `bash "$settings_sh" init` → seed a documented template if none exists (only when the user asks to configure).

> **Not shown above:** the remaining recognized keys — `history_reminder_enabled` and the `worktree_*` cleanup/retention family — are documented in README → "Project settings" and the `auto-task-gc` skill.

**Two scopes.** `settings.sh` merges a GLOBAL file (`${AUTO_TASK_HOME:-$HOME/.claude}/auto-task/settings.json`, applies to every project) UNDER the per-project file (`.../auto-task/<project-key>/settings.json`). Resolution is `defaults ⊔ global ⊔ project` — the project file wins, so you can opt telemetry in globally and disable it for one project with `{"telemetry_enabled": false}` in that project's file (or vice-versa). Seed either with `settings.sh init` (project) / `settings.sh init --global` (global).

**Remote telemetry (opt-in, off by default).** The endpoint + ingest token default to the project's **bundled central collector** (shipped in `hooks/settings.sh`), so a user opts in by setting only `telemetry_enabled: true`. When it is `true` and `telemetry_endpoint` is a valid `https://` URL, the `send-telemetry.sh` Stop hook fires at `phase==done` and POSTs an ANONYMIZED quality/performance row (`schema_version: 6` — v4 as of v0.23.0, bumped to 5 when `est_tokens` changed from a cache-inclusive total to predicted OUTPUT tokens, and to 6 when `duration_min` / `act_duration_min` changed from model-narrated history timestamps to a hook-measured run clock AND became nullable for a rejected span; a consumer pooling rows across either boundary must branch on `schema_version`). The payload EXCLUDES every identifying field the local `record-outcome.sh` row carries (task text, branch, base SHA, completion timestamp) and is otherwise a SUPERSET of that row's metrics: it adds a random resettable install id (`${AUTO_TASK_HOME:-$HOME/.claude}/auto-task/client-id`), the OS, a schema version, the Phase-5 satisfaction/correctness answers (incl. the optional free-text `comment`), and derived metrics not in the local row — `difficulty`, `risk`, `task_type`, `requirements_count`, `drift_events`, `tokens_input`/`tokens_output`/`tokens_by_skill`, `files_changed`, `preview_verdict`, `model`, `claude_code_version`. (`plugin_version` is now on the LOCAL row too — added for the stats version-over-version regression guard — so it is shared, not sender-only.) **Repo-shape fields are FROZEN as of schema_version 4 (and still not emitted at v5 or v6):** the speculative per-segment fields (`repo_files_bucket`, `primary_language`, `is_monorepo`, `churn_ratio`, `hotspot_concentration`, `dirs_touched`, `max_depth`) are **no longer emitted** — at the current install base they cannot reach statistical power as reporting dimensions and slicing a small ledger by them courts winner's-curse false discoveries. `hooks/repo-metrics.sh` is retained (still unit-tested) but no longer merged into the payload; the server columns are kept as legacy nullable (v4 rows store NULL) per the schema's never-drop rule. It is fail-open, bounded (`--connect-timeout 2 -m 5`), and write-once per run. This is independent of the local `outcomes.jsonl` opt-in. A reference ingest server + Turso schema live (undeployed) under `server/`.

Unknown keys present in the file are preserved by `all` (forward-compatible) and returned verbatim by `get`, so the schema can grow without a helper change.


## autonomy-subcontracts — relocated verbatim from SKILL.md

### First-run setup (one-time, per project)

On a NEW run, after the version check and BEFORE branch setup, resolve `settings.sh schema-status`. If it returns `unconfigured` or `stale`, run the one-time setup (skipped on resume; fail-open — any error/headless → keep safe defaults and proceed):

1. If `stale`, first `bash "$settings_sh" reset --backup` (see "Settings reset").
2. Ask the user **five policy questions** in one pass (each recorded immediately via `settings.sh set`, project scope):
   - **Telemetry** — share anonymous metrics? (`telemetry_enabled`) — asked at project scope; a global opt-in is *surfaced*, not silently inherited (`present --scope project`).
   - **Autonomy** — `supervised` vs `autonomous` (`autonomy`).
   - **Landing model** — `pr` vs `direct` (`landing_model`).
   - **Unattended external** — may the run run deploy/migration/side-effect commands on its own? (`unattended_external`, default no).
   - **Docs update** — after a run, should the optional docs-update step refresh user-facing docs? (`docs_update_mode`) — three answers: **skip and never ask again** (`skip`, the default), **update every run and never ask again** (`always`), or **ask each run** (`ask`).
3. Stamp `settings_schema_version` to the current value (via the first `set`, which also seeds it) so the setup does not re-fire next run.

`bot_review_autofix` stays a quiet default-off opt-in (edited in the settings file), not a setup question. The five questions are the whole policy surface; every other key has a safe default.

### Autonomy modes

`supervised` (default) is today's behavior unchanged. `autonomous` silences the *procedural* gates (Phase-1 plan approval, Phase-5 push prompt) and runs unattended; the plan/AC/critique/disclaimer are still generated and recorded, just not waited on. The merge gate and the interrupt-now gates below are the safety net that makes that safe. The gate that fires is a function of `autonomy` × `landing_model`:

| autonomy | landing | Phase-1 plan gate | Handover / land |
|---|---|---|---|
| supervised | pr | STOP for approval | push/PR prompt (today) |
| supervised | direct | STOP for approval | prompt before landing on the default branch |
| autonomous | pr | auto-approve (unless ambiguity/inconclusive) | push + open PR unattended; red disclaimer goes in the PR body; the human merges the PR. **Exception:** `risk >= risk_gate_threshold` forces one pre-push merge-gate ack anyway. |
| autonomous | direct | auto-approve (unless ambiguity/inconclusive) | **merge gate**: stop once, show the red disclaimer + assumptions ledger, land on the default branch on ack |

Even a fully autonomous run therefore gives the human exactly one meaningful review moment (the merge, or the PR) with everything consolidated.

### Merge gate

The merge gate is the single mandatory human stop — the point where work becomes shared/irreversible. It is **mechanical**: the skill sets `gates.merge.required = true` at handover when the matrix (or `risk >= risk_gate_threshold`) demands it, surfaces the red disclaimer + assumptions ledger, and sets `gates.merge.acked = true` only on the user's explicit go-ahead. **The high-risk half does not depend on the skill remembering.** `enforce-gates.sh` recomputes `effort.risk >= risk_gate_threshold` itself at the land action and blocks when the gate was never armed — because a step-7b that does not run leaves the land unguarded on exactly the runs the gate exists for, and that was observed on a real run that reached `done` at `risk: 6` with `required: false`. The skill still owns arming the flag and surfacing the disclaimer; the hook is the backstop, not a replacement. `enforce-gates.sh` blocks the land action — `git push`, a direct-to-main `git merge`, **or `gh pr merge`** (the `landing_model=pr` land) — resolved via its cross-branch active-run scan so an on-main land is not fail-open, whenever `required && !acked`. In `pr` mode the gated `git push` is the *pre-push ack* for a high-risk run (the run stops once before pushing/opening the PR); it is only ever gated when `required` is set, so ordinary supervised and low-risk `pr` pushes are never blocked. In `supervised` mode the gate is satisfied by the existing push prompt; in `autonomous`+`pr` low-risk it is not required (push proceeds, disclaimer in the PR body); in `autonomous`+`direct` or any high-risk run it is required and blocks until acked. Set `expected_next_action: "user-approval"` while it waits.

### Interrupt-now gates

Distinct from the merge gate (which defers to the end), these stop the run *mid-flight* because proceeding would waste work or do damage:

- **Ambiguity** — a genuine decision the run cannot resolve with evidence. At Phase 1 a non-empty Asked bucket hard-stops even in `autonomous` mode (autonomy never auto-approves through real ambiguity — this is the safety net for optional plan approval). Mid-run, it is a Loop-rule clause-3 surface.
- **Destructive / out-of-envelope op** — `guard-dangerous-ops.sh` (PreToolUse/Bash, fail-closed on a matched dangerous pattern, run-scoped) blocks a command outside the safe envelope (`rm -rf` on a dangerous target, force-push to a protected branch, `DROP`/`TRUNCATE`, `kubectl/terraform/aws … delete`, migration-apply, deploy/publish) unless `unattended_external=true`. The model must surface it for approval instead of running it unattended.
- **Test integrity** — a `checks.sh` `test-integrity` fail (added skip/focus markers or removed assertions) routes into the fix loop / surfaces, when `test_integrity_guard` is on. The classic "gutted the test to go green" failure.
- **Budget blowout (cost)** — a *soft* interrupt (loop-rule-family, model-driven; there is no token-usage hook): when measured cost exceeds the estimate by `budget_blowout_factor`, check in with the user. This *cost* interrupt is deliberately not hook-enforced and is labeled as such rather than overclaimed.
- **Fix-loop budget (iteration count)** — hook-enforced, and the one exception to the sentence above, but be precise about *where* it bites: the mechanical stop is **at commit time** (`enforce-gates.sh` refuses the commit while `max(iteration.fix, iteration.review)` exceeds the tier budget un-acked), not at an arbitrary point mid-phase. The Stop-hook half *releases* a turn-end and warns; it never halts. So this bounds what can **land**, and notifies during the loop — it does not abort a phase the way the ambiguity or destructive-op interrupts do. See "Fix-loop budget" under Effort tiers.

### Assumptions ledger

Because `autonomous` mode removes the plan-approval gate, every decision the run makes on the user's behalf is appended to `state.assumptions[]` — auto-approved ambiguities, thinly-cited resolutions, drift auto-continues, and accepted risks. The ledger is surfaced at the merge gate (or in the PR body for `autonomous`+`pr`) so the human's one review moment shows exactly what was decided without them. No hook reads it; it is the honesty mechanism that makes optional plan-approval safe rather than silent.

### Settings reset

The settings model is version-stamped (`settings_schema_version`). When the plugin updates and the stamp is behind the current `SETTINGS_SCHEMA_VERSION`, the settings are reset from scratch rather than migrated: `settings.sh reset --backup` copies the PROJECT file to `settings.json.pre-<oldstamp>` (restore = copy it back) and clears the project file so First-run setup re-asks the five questions and re-stamps it. Reset touches ONLY the project file — the shared GLOBAL file (cross-project settings like a global telemetry opt-in) is never clobbered. It is new-run-only (a resume keeps its STATE snapshot, so the rules never change under an in-flight run), and telemetry is re-consented at project scope because the payload changes across schema versions. A plugin downgrade re-reads the old file harmlessly (unknown newer keys are preserved).

### Stop-hook registration (the yield-point contract's mechanical half)

_Relocated byte-exact from the spine's "Yield-point contract". The contract itself — the value table and the hook's decision procedure — stays in `SKILL.md`; only the registration mechanics live here, with the other install-time settings._

The hook is registered via the plugin's `hooks/hooks.json` (marketplace install) or the `settings-fragment.json` fallback (`install.sh`/manual). Without it, the field is informational; with it, the field is enforced. Both must be aligned — never set `"user-approval"` speculatively to "escape" the hook, because that defeats the entire mechanism. The pre-commit hook for gates is the analogous precedent: don't flip flags speculatively.
