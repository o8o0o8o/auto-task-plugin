## phase3-body — relocated verbatim from SKILL.md


**On entry, set `phase: "self-verify"`** (`expected_next_action: "auto-continue"`).

**Make created files visible to the diff FIRST (NON-NEGOTIABLE — run this before invoking `auto-task-verify`).** Run `hooks/intent-add-untracked.sh` (locate it with the three-probe pattern). It intent-to-adds (`git add -N`) every untracked, non-ignored path in the repo, which is what puts a file *created during the run* into `git diff <base>`.

Why it must happen here, and why here is enough for the common case: **every** verification input downstream is specified against `git diff <base>`, and nothing is staged or committed until Phase 5 — so a created file is otherwise invisible to Phase 4 review, to Gate A, to Gate B, and to the `gates.code_review.reviewed_diff_sha` pin. Phase 3 is the single choke point that precedes all four, and the fix loop re-enters Phase 3 from the top, so a file created by a *fix* is caught on the next pass exactly like one created in Phase 2. Phase 2 needs no call of its own: its drift check reads `git status --short`, which already lists `??` entries.

**Run it again before EVERY (re-)computation of a diff-pinned gate hash** — `gates.code_review.reviewed_diff_sha` at each clean review pass, and `gates.gate_b.verified_diff_sha` at each Gate-B pass. A file created by a Phase-4 or Gate-B fix that lands *after* the pin would otherwise enter the diff only once Phase 5 stages it, moving the hash after it was fixed. That is not a review blind spot but a **hard stop**: `enforce-gates.sh` compares the two and blocks the handover commit, so the run deadlocks with no path forward except an intent-add nobody instructed.

**It sweeps repo-wide but touches ONLY files this run created.** The helper skips every path listed in `.auto-task/<branch>/untracked-baseline`, pinned at branch setup (see `references/phase-1-preamble.md`) — the set of paths already untracked before the run began. That baseline is empty on the normal fresh-worktree path, and load-bearing on the two paths that carry a user's pre-existing WIP into the run's tree, where the "Pre-existing staged/unstaged changes" rule forbids `git add` on that WIP. **The exclusion is what makes the sweep safe, and it is not merely tidiness:** intent-adding a file the user owns makes an ordinary `git restore .` / `git checkout -- .` truncate it to zero bytes, and a hard reset remove it outright — where the same commands leave a plainly-untracked file untouched. A missing baseline fails open to sweeping everything, so do not let branch setup skip writing it.

For the run's **own** created files one consequence still applies: while an intent-added entry exists, `git merge` refuses that path as *not uptodate* (`error: Entry 'X' not uptodate. Cannot merge.`). **Phase 5 releases them with `hooks/intent-add-untracked.sh --undo` immediately after the authored commit**, before the main-sync merge — see `references/phase-5-handover.md` step 6.

The call is safe to repeat: `git add -N` stages **no content** (`git diff --cached` stays empty and `git commit` finds nothing staged), so Phase 5's "planned files only" staging still decides what actually lands, and the helper is idempotent — a second run reports `count: 0`. It never touches ignored paths (`--exclude-standard` covers `.auto-task/` and `.claude/worktrees/`). **Fail-open:** it always exits 0; on a non-repo, absent git, or a path git refuses it reports the fact in its JSON (`{added, count, failed, note}`) and the run proceeds. Log the result to `state.history` as `{ phase: "self-verify-intent-add", count: <n>, failed: [...], at: "ISO-8601" }`.

Invoke the `auto-task-verify` skill on the **uncommitted working-tree diff** (`git diff <base>` — no `..HEAD`, the changes are not yet committed). Parse its report.

**MCP usage in verification is open.** Any MCP available to the session may be used during self-verify and the gates if it's the most direct way to execute a Verification method or confirm an observation. Common picks:

- **playwright** — live UI / browser-driven AC checks (selector present, no console errors, screenshot diff, network call returns expected payload). **Local dev first** (rule 9): resolve a local UI via the recon reuse-or-improvise ladder (running server → disposable render → mock/seed to reach the *real* UI) and run the check there; the preview (Phase 7) is the second rung. If the UI can't be reached even after improvising, record the AC **INCONCLUSIVE** (never a proxied pass, never a hard STOP) per the floor. **For any visual AC (rule 8), the screenshot you take to verify the criterion IS the "after" image** — drive the app to the same state the Phase 1 baseline captured, `browser_take_screenshot`, save as `.auto-task/<branch>/recon/screenshot-after.png` (same crop/viewport as `screenshot-before.png`). One shot serves both the assertion and the PR. **Close every Playwright session when the check is done** (`browser_close`), and shut down any disposable render harness you started — don't leave browsers or servers running across phases.
- **ide** — `getDiagnostics` to assert no new type/lint errors in the touched files.
- **claude_ai_Context7** — confirm an external library API the code now calls actually behaves the way the plan assumed.
- **plugin_figma_figma** — visual reference comparison for design-driven ACs.
- Others (Notion, Drive, Slack, etc.) only when the AC explicitly references content in that system.

Same rules as Phase 1 recon apply: **read-only by default** (writes to external systems are forbidden during verification without explicit user authorization in this run); auth prompts are not blockers — log `result: "ac-blocked"` for that AC and treat it as fail, since an AC that can't be executed can't pass; mandatory prerequisite skills (`figma-use` before `use_figma`) still load. If the AC's `Verification method` literally names an MCP call, run that call; otherwise, prefer the cheapest tool that produces the evidence.

**AC execution contract (NON-NEGOTIABLE).** In addition to whatever the `auto-task-verify` skill runs by default, you MUST execute every row in PLAN.md's Acceptance Criteria table whose `Gate` column contains `self-verify`. For each such row:

1. Run the `Verification method` literally as written (the command, assertion, or MCP call).
2. Capture stdout/stderr/exit code (or MCP response payload) and compare against `Expected result`.
3. Record the run in `state.history` as `{ phase: "self-verify-ac", ac: <#>, result: "pass|fail|inconclusive", evidence: "<command or MCP call + result snippet>", mcps: ["..."] (if any), at: "ISO-8601" }`.

**Do not substitute a weaker method (verification-method binding, AC contract rule 6).** Run the AC's *declared* `Verification method`. If it is live/manual/real-data and you cannot execute it here (dev server user-run, preview unreachable, data not configured), do NOT green it with a `grep`/unit/code-reading proxy — record `result: "inconclusive"` per the INCONCLUSIVE floor and let it route to the human surface (verify-now, or explicit descope). A `self-verify`-gated AC should never *be* live-only in the first place (rule 4/6 routes those to `gate-a`); if you find one that is, that is a plan defect — fix it, don't proxy it.

`gates.self_verify.passed` cannot be set to `true` unless EVERY `self-verify`-gated AC row has a recorded `result: "pass"` entry from the current iteration. An AC recorded `inconclusive` is NOT a pass and blocks the gate exactly like a fail (it resolves only through the INCONCLUSIVE floor's human decision, never by inventing a proxy pass). If the `auto-task-verify` skill's report says "all quality checks PASS" but an AC's bound check was never executed (e.g., the test file the AC names doesn't exist yet), that is a FAIL — surface it as a missing test, not a pass. Do not treat AC coverage as optional just because the generic checks were green.

**Checks-manifest capture (NON-NEGOTIABLE — builds the "comprehensive checks" the summary enumerates).** Every verification run in this phase MUST be recorded to `state.checks[]` so the final summary can list them all. A check row is `{ name, category, command, gate, result: "pass|fail|warn|info|skip", evidence, at }`. Populate it from two sources:

1. **Each `auto-task-verify` check** (typecheck, lint, build, unit, e2e/playwright) and **each `self-verify` AC bound-check** — one row per check, `gate: "self-verify"`, `result` from its exit code / comparison, `evidence` a short snippet.
2. **Universal hygiene/defect checks** via `hooks/checks.sh` (locate with the three-probe pattern). Run `checks.sh --base <base>` — it returns rows shaped `{name, category, result, detail}` (secret-scan, conflict-markers, debug-artifacts, large-files, diff-size, tests-added). Map each into a `state.checks[]` entry by renaming `detail`→`evidence` and adding `gate: "self-verify"` (plus `command`/`at` where known) so the appended rows match the `state.checks[]` schema. **A `result: "fail"` row (a real secret or a leftover conflict marker outside test/fixture paths) FAILS self-verify** — route it into the fix loop exactly like a failing quality check. `warn`/`info` rows are recorded but do not block.

Gate A and Gate B likewise append their findings to `state.checks[]` (tagged with the appropriate `gate`), so the manifest is complete by Phase 5. This is additive to the `self-verify-ac` / `gate-a-ac` history entries — reuse their evidence rather than re-running. Fail-open: if `checks.sh` cannot be located, record a single `metric-unavailable` note and proceed (never a silent skip that reads as "all clean").

- All `auto-task-verify`-skill tasks COMPLETE + all quality checks PASS + every `self-verify` AC executed with `result: "pass"` + no `checks.sh` `fail` row → set `gates.self_verify = { passed: true, at: <ISO>, evidence: "<short summary of checks that passed, including which AC rows ran>" }` and advance to Gate A.
- Any task PARTIAL/NOT FOUND, or any quality check FAIL → diagnose:
  - If the failure indicates flakiness (intermittent test, retry-passes-without-change) → STOP and surface per Loop rule.
  - Otherwise → invoke `/auto-task-fix` against the failing item (which modifies the working tree, no commit), then return to start of Phase 3. Increment `iteration.fix`.
- **Re-score hook.** Before incrementing `iteration.fix`, check whether the failure exposes anything outside PLAN.md's Blast Radius / Unknowns. If so, re-run the rubric, update `effort`, log to `effort.history`, and apply the new tier's caps and `/auto-task-verify` scope to the next iteration.
- Apply the Loop rule between iterations to detect "no progress". If `iteration.fix` has reached the current tier's fix-loop cap, do a forced re-score before STOPPING; if the tier escalates, the new (higher) cap applies, which raises the budget. Two independent mechanisms are in play and neither silently undoes the other: a **tier escalation** raises the cap itself, whereas a **user ack** (`gates.loop_budget.acked_through`) raises the budget to the next cap rung that clears the current loop count, without changing the tier — the effective budget is `max(cap, acked_through)`, so both are honoured. Note the budget is measured against `max(iteration.fix, iteration.review)`, so review rounds consume it too.


## gate-a-body — relocated verbatim from SKILL.md


**On entry, set `phase: "gate-a"`** (`expected_next_action: "auto-continue"`).

**Before spawning the agent**, execute every AC row whose `Gate` column contains `gate-a`. Run the `Verification method` **as declared** (verification-method binding, AC contract rule 6) and compare exit code / output (or MCP response) against `Expected result`. The MCP allowance from Phase 3 applies here too — any available MCP may be used to execute a bound check, read-only by default. Record each as `{ phase: "gate-a-ac", ac: <#>, result: "pass|fail|inconclusive", evidence: "<command or MCP call + result snippet>", mcps: ["..."] (if any), at: "ISO-8601" }` in `state.history`. Any `gate-a` AC with `result: "fail"` short-circuits Gate A immediately — treat as an unsatisfied criterion and feed back to Phase 2 without running the agent (the agent's judgment is moot if a bound check already failed).

**A live/manual/real-data AC whose declared method you cannot run here is `inconclusive`, NOT a proxied pass (the INCONCLUSIVE floor).** Do not substitute a `grep`/unit/code-reading check for a declared live method to clear the gate. An `inconclusive` `gate-a` AC does not pass the gate; it routes to the human surface (verify-now, or explicit descope) exactly as the floor specifies — and until the user resolves it (re-verified to `pass`, or descoped so its requirement is `dropped`), `gates.gate_a.passed` stays `false`. Surface it (`expected_next_action: "user-approval"`); do not spin Phase 2 trying to "fix" an AC whose only blocker is that the verification target is unreachable.

### Spawning a verifier — synchronous, and what to do if it is not

**Spawn SYNCHRONOUSLY: pass `run_in_background: false`.** This applies at every Agent spawn site in the pipeline — Gate A, Gate B, and the Phase-1 critique. The whole gate contract rests on it: the reminder closing this section ("the verifier's report is INPUT") is only true if the spawn *returns* a report. A backgrounded spawn returns launch metadata instead, and the report arrives later as a task notification — which this pipeline has no synchronous way to collect.

**If a spawn returns launch metadata anyway, wait by YIELDING — never by polling.** Write `expected_next_action: "awaiting-agent"` and end the turn. That is the one mid-pipeline turn-end the Stop hook releases on purpose (capped — see the yield-point contract in `SKILL.md`), precisely so the harness can deliver the report and re-invoke you with it. On the next turn, act on the report and set `expected_next_action: "auto-continue"`. This is a fallback for a harness that backgrounds the spawn regardless, not a spawn mode to choose.

**Two things are forbidden while waiting. Both are observed failures, not hypotheticals.**

1. **A subagent's transcript file is not a completion signal.** Do not `stat` it, do not compare its size or mtime between turns, and do not `sleep` against it in a loop. The file grows and then goes quiet while the agent is merely thinking, so the heuristic reports "done" and "hung" at random. In the observed run it produced eight blocked turn-ends in five minutes, each answered with a longer `sleep`, while the verifier's 380 KB of genuine investigation was never collected at all.
2. **A timeout is not a result.** Never record a gate verdict, a critique round, or a review round from the *absence* of a report. A run that had begun writing "round 2 has gone quiet — recording it honestly" was handed five substantive findings moments later. If the wait exhausts its cap, re-spawn synchronously and say so in `state.history`; do not write down an outcome you never received.

If every `gate-a` AC passed (or there are none), spawn the `task-execution-verifier` Agent (prefix its `label` with `state.title` per the "Run label" convention, and pass `run_in_background: false` per the synchronous-spawn rule above) with a fresh-context prompt containing:
- The Acceptance Criteria table from `.auto-task/<branch>/PLAN.md`, **with any user-descoped rows removed** (a row whose requirement the user marked `dropped` via the INCONCLUSIVE floor is no longer a criterion of this run — do not hand it to the verifier, or it will correctly flag the very row the user already descoped and bounce the run). Tell the agent, in one line, which rows (if any) were descoped and why, so it does not treat their absence as missing coverage.
- The current working-tree diff (`git diff <base>` — uncommitted).
- The list of `state.history` entries with `phase: "gate-a-ac"` (so the agent sees which checks already ran and what they returned).
- Explicit ask: "For each row in the Acceptance Criteria table, confirm the diff satisfies the `Criterion` AND that the listed `Verification method` would actually produce the `Expected result` if re-run now. For rows already executed above, validate the evidence is real (not fabricated) and that 'pass' actually maps to the criterion's intent (not a superficial match). **Reject any 'pass' where a weaker proxy (a `grep`, a unit test, code-reading, or a local fixture) was used to satisfy a criterion whose declared `Verification method` is live / manual / Playwright / real-data — that is not a pass, it is INCONCLUSIVE.** Likewise flag any criterion whose real-world outcome depends on external/runtime data but was only checked against fixtures. Flag any criterion that is unsatisfied, weakly satisfied, or whose bound check doesn't truly test it. Do not propose new work — only judge completeness."

If any AC row failed its bound check OR the agent reports any criterion unsatisfied / weakly satisfied / proxied-when-live: feed findings back as a fix list, return to Phase 2 (append each unsatisfied criterion as a new implement task under a "Gate A findings" section in PLAN.md). After fixing, return to Phase 3. **Do not commit between iterations.** (A criterion the agent flags as proxied-for-live is re-classed `inconclusive` and routes to the human surface, not the Phase-2 fix loop — its blocker is an unreachable target, not missing code.)

If every `gate-a` AC passed its bound check (none left `inconclusive`) AND the agent confirms all criteria satisfied: set `gates.gate_a = { passed: true, at: <ISO>, evidence: "<agent summary + which AC rows were executed with pass results>" }` and advance to Phase 4. An `inconclusive` gate-a AC must first be *resolved* through the INCONCLUSIVE floor before the gate can pass — either re-verified to `pass` (target made reachable) or descoped (its requirement marked `dropped`, and the row removed from the gate-a set, per the floor). The gate never passes while any AC is still recorded `inconclusive`; there is no "deferred-but-passing" state.

**Reminder (see top-of-file NON-YIELDING CONTRACT):** the verifier's report is INPUT. Set the gate, update state, write the next phase header, and immediately call the next tool — do not write a recap to the user.


## gate-b-body — relocated verbatim from SKILL.md


**On entry, set `phase: "gate-b"`** (`expected_next_action: "auto-continue"`).

Second `task-execution-verifier` pass with an **adversarial** stance — flip the prompt from "is this complete?" to "find what's wrong." Pass only if the agent genuinely tries and fails to find issues.

### Why this gate is bounded (read before changing any rule below)

Left unbounded, this gate does not converge. Measured across seven completed runs: Gate B ran **4 to 11 passes** each, required-finding counts **never decayed** (one HEAVY run went `3,2,3,3,3,2,3,4,0` over nine passes), blockers arrived at passes **3 and 5** rather than pass 1, and **three of the seven runs ended by human fiat** rather than by a clean pass. The mechanism is self-feeding: each pass's fixes are new, un-adversarially-reviewed code that the next pass legitimately finds fault with, so a determined verifier always has something to report. Two properties made it unbounded — a finding's *self-assigned severity* drove control flow regardless of whether it touched an Acceptance Criterion, and nothing counted the passes. Every rule below exists to close one of those. Do not relax one without re-reading this paragraph.

### Step 0 — pass accounting and the entry budget check (BEFORE spawning anything)

1. **Determine this pass's `scope`.** `main` for the ordinary Phase-4 → Gate-B loop; `regate:docs`, `regate:merge`, `regate:bot-fix` or `regate:release` when Gate B is being re-run by one of the four post-main-loop sites that reset `gates.gate_b.passed = false`.
2. **Read the applicable cap from the single executable definition** — source `hooks/lib/loop-budget.sh` (locate it with the three-probe pattern) and call `lb_gate_b_cap <tier>` for `scope: "main"`, or `lb_gate_b_regate_cap` for any `regate:*` scope. **Never hardcode the numbers here**; the helper is the definition and this prose documents it. The two are deliberately separate functions: a re-gate allowance that drew on the main-loop count would let a run that spent its passes in the main loop never re-earn the gate, deadlocking the handover commit.
3. **Count the passes already recorded for this scope** — `state.gates.gate_b.passes[]` filtered to the same `scope` — and compare it against `cap + gates.gate_b.allowance_acked[<scope>]`. **A granted allowance raises the CAP; it never adds to the spent count** — adding it to the passes already spent would leave a granted pass still at the cap and re-surface the same check-in the grant was given to end. The grant is per-scope and recorded as an object keyed by scope, never a bare integer — a scalar would let one grant raise every other scope's allowance too. **An absent `passes[]` counts as 0**, so a run that started before this contract existed is never blocked by it (the same legacy tolerance the loop-budget gate applies to a missing `effort.tier`).
4. **Check the fix-loop budget HERE, not only at commit time.** Compute the loop count `max(iteration.fix, iteration.review)` and the effective budget `lb_effective_budget <cap> <acked_through>` (with `<cap>` from `lb_cap_for_tier`). If the loop count exceeds the budget, run the ack ritual **now** rather than discovering it at the Phase-5 commit — `enforce-gates.sh` only sees `git commit`, and this loop never commits, which is precisely why an unbounded run could spend 28 review rounds without the budget ever being consulted.
5. **If this scope is already at its cap, do NOT spawn the agent.** Go straight to "Over-cap surface" below.

### Step 1 — delta-scope the pass

Pass 1 of a scope reads the whole `git diff <base>`. **Every later pass reads only what changed since the previous pass of that scope**, plus the findings that pass claimed fixed. Record the boundary in `gates.gate_b.verified_diff_sha`, computed with the **byte-identical** pinned-flag formula `reviewed_diff_sha` uses:

```
git diff --no-color --no-ext-diff --no-textconv --no-renames --diff-algorithm=myers --src-prefix=a/ --dst-prefix=b/ <base> | git hash-object --stdin
```

**`verified_diff_sha` is an equality token, not a revision** — it is a blob hash of diff *text*, so `git diff <that sha> …` is not a runnable command (the blob is not a commit-ish, and per the single-commit rule there is no commit to diff against yet). To make the delta executable, write the pass's diff bytes — **the same bytes the formula hashes** — to `.auto-task/<branch>/artifacts/gate-b-<scope>-<n>.diff`, and hand the next pass `diff -u <that file> <(the current diff)` plus the previous pass's findings named explicitly. Rationale: re-reading the full accumulated diff every pass means pass N searches all N−1 rounds of fixes again, so the search surface grows monotonically while the budget does not. Delta-scoping bounds the surface to the work actually at risk. **Snapshot the boundary when the pass STARTS — of the bytes that pass actually read — never after its fix round lands.** A boundary captured at the *end* of a reopening pass is taken from the post-fix tree, so the next pass's delta comes back empty and the fixes that pass triggered — the self-inflicted defects this whole ladder exists to catch — are the one thing it never sees. So: write the file and set `verified_diff_sha` from the same diff you hand the agent, at spawn time, and leave both untouched until the next pass spawns.

Spawn with a fresh-context prompt (prefix the Agent's `label` with `state.title` per the "Run label" convention, and pass `run_in_background: false` per the synchronous-spawn rule at Gate A — including its two prohibitions, transcript-polling and recording an outcome from a timeout) containing:
- The Acceptance Criteria from `.auto-task/<branch>/PLAN.md`.
- **On pass 1 of the scope**, the full diff vs. base (`git diff <base>` — the uncommitted working-tree diff; **every later pass gets the Step-1 delta instead, never this full diff** — handing it the whole diff again is the unbounded search surface Step 1 exists to close. Per the single-commit rule nothing is committed until Phase 5, so `<base>..HEAD` / `<base>...HEAD` would be empty here and the adversarial verifier would see no code).
- The list of review findings that were addressed in Phase 4.
- Explicit ask: "Adversarially review this diff. Your job is to find what's wrong, not confirm what's right. Hunt for:
  - An acceptance criterion only superficially satisfied (the test exists but doesn't exercise the AC's intent).
  - A regression — any existing behavior this diff could break.
  - A bypass — input or sequence that reaches the new code with protections circumvented.
  - An edge case the diff doesn't handle (empty / null / concurrent / large / malformed input).
  - A Phase 4 review finding 'addressed' in name but not in behavior.
  Return up to 6 specific findings. For each: cite `file:line`, describe how to reproduce or trigger it, rate severity (blocker / required / follow-up). If you genuinely cannot find any after thorough search, return exactly `No adversarial findings.` — but the bar is 'you tried and failed,' not 'you didn't try.'"
- Additionally: "For each finding also state `ac:` — the number of the Acceptance Criterion it breaks, or `none` — and `reachable:` — one of `runtime` (a real input or sequence reaches the failure at run time), `spec-only` (it is a contradiction or gap in specification text), or `docs-only` (it is prose, a comment, a changelog or a README claim). These two are **facts for the orchestrator to act on, not your severity judgment** — report them even when you rate the finding a blocker."

### Step 2 — resolve by AC impact, not by label

**A finding's severity label does not decide control flow.** The verifier assigns it under a definition ("correctness issue the project conventions require") that is unbounded in a docs-heavy repo, and in the measured runs it duly labelled README wording and stale code comments `required`, each of which reopened the whole loop. What decides is whether the finding touches this run's contract.

**Reopen Phase 4 for a finding if and only if AT LEAST ONE holds:**

- **(a) It breaks an approved Acceptance Criterion** — its `ac:` names a row in PLAN.md's AC table that is not user-descoped.
- **(b) It is a runtime-reachable regression or bypass in the diff** — `reachable: runtime`, with a named input or sequence.
- **(c) It is a security or data-loss path** — credential exposure, injection, corruption, silent data loss.

**Every other finding parks in `state.followups`, whatever its label** — including one the verifier called `blocker` or `required`. Park it with its original severity and the reason it parked, so the record shows what was set aside rather than hiding it.

**Fail closed on a missing fact.** If a finding's `ac:` field is absent, unparseable, or names a row that does not exist, treat it as **AC-breaking** and reopen. The safe direction is to do the extra work, never to park something that might be a real breach. (The one exception is `park_non_blocking`, below, whose whole purpose is to override this — and which only the user can set.)

**Record the pass FIRST (Step 3), on every exit — reopen included.** The steps are numbered for reading order, not control flow: a reopen that leaves the gate at Step 2 without appending to `passes[]` leaves the array empty, and since **an absent `passes[]` counts as 0** the cap, the `self_inflicted` signal and the convergence test all silently disarm on the very path they exist to bound. **Append the row with the fields knowable now** — `n`, `scope`, `blockers`, `required`, `followups`, **`reopened` (the count of findings that met (a)/(b)/(c) — the convergence test's declared basis, and the one field it compares across passes; `blockers`/`required` are the raw LABEL counts, which that test explicitly does not use)**, `diff_sha` (the boundary this pass read, per Step 1) and `at`. The two that depend on later work are filled in later, on the same row: `fixed_lines` when Phase 4's fixes land, and `self_inflicted` by the pass that cites them. Waiting for those before recording anything is what leaves `passes[]` empty.

On a reopen: feed the finding back to Phase 4 as a new fix task; **increment `iteration.review`** (this also keeps the anti-stall hook's freeze signature advancing, since it hashes `iteration.review`); do NOT set `gates.gate_b.passed`; and reset `gates.code_review.passed` to `false`, because an addressed-in-name-only failure means the review did not really hold up.

- Only **follow-up** findings → park in `state.followups`, set `gates.gate_b = { passed: true, at: <ISO>, evidence: "<adversarial summary; only follow-ups>" }`, advance to Phase 5.
- `No adversarial findings.` → set `gates.gate_b = { passed: true, at: <ISO>, evidence: "No adversarial findings" }`, advance to Phase 5.
- **No finding met (a)/(b)/(c)** → the gate passes exactly as if only follow-ups were returned; record the parked findings and their labels in the evidence.


**Why a single non-decreasing pass, and not two consecutive clean ones (the rule this replaced).** The earlier "two consecutive rounds with zero blockers and zero required" test could not fire where the churn actually happens: Gate B exits on the *first* clean pass, so a second consecutive clean round is never observed, and any non-clean round resets the streak. Across seven measured runs it fired **once**, in a docs re-gate. Worse, a two-round test is arithmetically unreachable under a Gate B cap of 2 (STANDARD), reproducing the same dead clause one layer down. A non-decrease test is observable in-loop on both tiers: on the measured HEAVY sequence `3,2,3,3,3,2,3,4` it fires at **pass 3** rather than never, while a genuinely improving `3,2,1` does not fire at all.

### Step 3 — record the pass, then test for convergence

Append to `gates.gate_b.passes[]`: `{ n, scope, blockers, required, followups, reopened, self_inflicted, fixed_lines, diff_sha, at }`.

**`self_inflicted` — is this pass finding defects in the previous pass's fixes?** When a pass triggers fixes, record `fixed_lines: [{ path, hashes: [...] }]` — one hash per line the fix **added**. A later finding is `self_inflicted` when the current content of its cited `file:line` hashes to one of those recorded lines. **Hash the content; never store line numbers.** Two rules keep content hashing from over-matching, because identical lines hash identically and fixes add non-unique lines constantly: **(i) skip lines that are blank, whitespace-only, or pure structure** (`}`, `fi`, `else`, `done`, a lone bracket) when recording `hashes[]` — they carry no attribution signal; **(ii) a match counts only if that content occurs exactly once in the file now** — if it occurs more than once, the citation cannot be attributed to the fix and the finding is NOT `self_inflicted`. Without these, a fix that adds one `  fi` marks every other `  fi` in the file as self-inflicted, and the flag's whole purpose is to give the user a trustworthy "the fixes are the defect source" signal. A subsequent fix that edits the same file above the hunk shifts every line below it, so a coordinate-based range would both miss real self-inflicted findings and manufacture false ones. **The second pass with `self_inflicted: true` — not necessarily consecutive — surfaces to the user.** ("Two consecutive" would be unfirable under a cap of 2, which is the dead-clause defect the convergence test below exists to fix; do not reintroduce it here.) The surface is worth making because "the fixes are now the defect source" is a different problem from "the code is wrong", and the user's answer is usually to park and land.

**Convergence test (Loop-rule clause 5, applied here).** Compare this pass's **reopening-finding count** — the findings that met (a)/(b)/(c), i.e. exactly the ones that cost a round — against the previous pass of the same scope, reading both from the rows' `reopened` field (never from `blockers`/`required`, which are label counts). **This is the counting basis in both places the test is stated:** the spine's clause 5 says "blocker+required count", which under this ladder means *the blockers and required findings that reopen*, not every finding so labelled. A parked `blocker` consumed no round, so counting it would let a run that parked everything look like it was still churning and never converge. When the two readings could differ, this one governs. **If it did not DECREASE, the loop has converged.** One pass is enough to fire; do not wait for two consecutive non-decreasing passes, which under a cap of 2 can never happen. **Surfacing (Step 4) is the only outcome this test has**, and the reason is structural: it is reached only when Step 2 found at least one reopening finding — a zero-reopening pass has already passed the gate at Step 2 — so a fired convergence test always has a live AC breach, runtime-reachable regression, or security/data-loss path still on the table. Convergence means the *count* stopped falling, not that the findings stopped mattering, so parking them would ship exactly what this ladder exists to catch, on a laxer test than the cap path applies to the same evidence. **This matches clause 5 as the spine states it** — a fired convergence surfaces there too, and the only autonomous advance is the one with nothing left to fix: at Gate B that outcome is Step 2's zero-reopening exit, which is where a pass with nothing left to fix already advances. On the measured `3,2,3,3,3,2,3,4` sequence this fires at **pass 3** instead of never. A still-decreasing sequence (`3,2,1`) does not fire — the test bounds churn, it does not short-circuit genuine progress.

### Step 4 — over-cap surface, and what the user's answer grants

**Three triggers reach this surface:** the scope is **at its cap**, a **second `self_inflicted` pass** landed, or **a fired convergence test** (Step 3). None of the three contradicts loop-rule clause 5, which resolves a fired convergence to a surface in every loop: at Gate B the clause's autonomous advance is Step 2's zero-reopening exit, and a pass reaching any trigger here still has AC breaches, runtime-reachable regressions or security paths on the table — parking those unseen would be laxer than what the cap path does on the same evidence. So: nothing meeting (a)/(b)/(c) ever leaves this gate without either a fix or a recorded human grant that names it — and the grants themselves carve (a)/(b)/(c) out, so "park the non-blocking ones" can never be stretched to cover them.

On any of those triggers, **surface — do not auto-continue.** Set `expected_next_action: "user-approval"` and show the **per-pass severity table** (`n`, `scope`, blockers, required, follow-ups, `self_inflicted`) so the user can see for themselves whether returns diminished. That evidence is the point; "we have done N passes" alone does not tell them anything.

Then name the three things their answer can grant, and **record whichever they choose** — none of these may be self-granted:

1. **One more pass** → set `gates.gate_b.allowance_acked[<scope>]` `+1` — that scope only — and re-enter Step 0.
2. **Park and advance** → set `gates.loop_budget.park_non_blocking = true` (see below) and pass the gate **only once nothing on the table meets (a)/(b)/(c)** — **applying the same carve-out to the findings already on the table, not only to later passes.** The surface was reached *because* something met (a)/(b)/(c), so a grant that passed the gate over those very findings would ship the breach it was called to adjudicate. If any current finding meets (a)/(b)/(c), this grant does not cover it: it needs a fix, or grant (iii).
3. **Descope the residual** → set `gates.gate_b.skipped_reason` naming what was set aside and why, and pass the gate. This is a recorded human descope, not a silent skip — the same shape a real run already used (`user-descope-at-loop-budget-ceiling`).

**On resume, read the recorded grant and act on it — do not re-surface the same check-in.** A run that surfaces, gets an answer, and then asks again on the next session has not bounded anything.

**`gates.loop_budget.park_non_blocking` (user-set only).** When set, it resolves **both the findings on the table when it was granted and those of every subsequent pass**, by parking every finding that is neither literally `severity: blocker` **nor a finding meeting the Step-2 reopen test — (a) an AC breach, (b) a runtime-reachable regression or bypass, or (c) a security/data-loss path** — and advances instead of surfacing again. **The (a)/(b)/(c) carve-out is not optional, and it is deliberately the same set the convergence test uses.** Carving out only (a) would leave this flag routing (b) and (c) on the *severity label* — the basis Step 2 opens by declaring untrustworthy — so a grant worded "park non-blocking findings" would silently ship a runtime regression or a security path that the verifier happened to rate `required`. Gate A has already passed and does not re-run, and Phase 5's completion check reads only `state.requirements[].status` — so a parked AC breach leaves `all_complete == true` and the run commits with that criterion broken and no record saying so. The user's grant was "park non-blocking findings", which is not authorization to ship a broken criterion. An AC breach leaves the run exactly one legitimate way: grant (iii), the recorded descope, which marks the covered requirement `dropped` so the completion check can see it. **Its precedence is explicit: it is evaluated BEFORE Step 2's fail-closed rule**, so a finding with a missing `ac:` is parked rather than forced AC-breaking — otherwise the fail-closed default would defeat the flag entirely and the run would keep surfacing. It carries the identical trust model as every other gate flag: **a checkable artifact, never set speculatively.** Writing it without asking is the same contract violation as flipping `gates.code_review.passed` without running the review, and it converts the one mechanism that lets a user end the loop into a self-authorized bypass.

**Trip-wire test (same shape as Phase 4's):** after the Gate B agent returns, before ending the turn — did you (a) write the gate-b resolution to state AND (b) make the next tool call (a Phase 4 fix Edit if blockers, or the Phase 5 git-stage command if clean)? If not, you're about to stall. Don't end the message. Call the next tool.

## phase-4-round-mechanics — the graded round contract for the Phase 4 fix loop

_New in this section, not relocated. It lives here rather than in the spine because it is the Phase-4 sibling of the Gate B ladder above and reuses that ladder's reopen test by reference — two copies of a reachability test would drift, which is the whole failure this section exists to prevent. The spine keeps Phase 4's anti-stall body inline (it is the anti-stall keystone) plus the graded non-negotiables, and points here._

**Why Phase 4 needs this at all.** Gate B was bounded in 0.29.0 because measured runs went 4-11 passes. Phase 4 was not, and the churn simply moved: in the two runs recorded in the clone-wide outcomes ledger, `iteration.review` reached **9** and **5** against a STANDARD cap of 4, while `gates.gate_b.passes[]` for the nine-round run holds exactly **two** rows, both `reopened: 0`. Gate B's bound worked perfectly; every one of those nine rounds was a Phase-4 `auto-task-code-review` round. The measured per-round finding counts were `6, 7, 2, 3, 1, 3, …` — a sequence that reads as non-convergence — while the *reachable* findings were decaying, because README figures and missing test assertions were labelled at the same severity as security holes. Phase 4 was missing all three of Gate B's bounds: no reachability grading, no per-round record, and no in-loop bound (`enforce-gates.sh` sees only `git commit`, and this loop never reaches one).

### Step 0 — where the review RUNS (`review_in_subagent`, default `true`)

**Default: spawn a fresh-context agent that INVOKES the skill. Set `review_in_subagent: false` to invoke it inline instead.** Both modes run the same skill on the same diff and record the same `gates.code_review.tool` value; the only difference is whose context reads the code.

**The spawn decision reads TWO things, every round, and this is the whole rule:** spawn only when `review_in_subagent` is on **AND `gates.code_review.subagent_disabled` is not `true`** (absent counts as `false`); otherwise invoke the skill inline. The second condition is not a footnote — the degradation ladder below sets that flag when the reviewer edits the tree, and a run **resumes from `STATE.json`**, so a resumed orchestrator that consulted only the setting would re-read `review_in_subagent: true` and re-spawn the very agent that was disabled. A flag written but never read closes nothing.

**Why the default moved.** Phases 2, 3 and 4 all ran in the main loop, so the model that wrote the diff also self-verified and code-reviewed it — independence entered only at Gate A and Gate B. An author reviewing their own work reads it charitably, because they know what they *meant*; that is the whole reason a second pair of eyes exists in human review too.

**The skill is still the reviewer, and that is not negotiable.** The agent's prompt MUST tell it to invoke the `auto-task-code-review` skill via the Skill tool. A hand-rolled review prompt in an agent is the substitution the spine forbids and `enforce-gates.sh` blocks — and the block still works here, because the hook reads `gates.code_review.tool` from state and cannot see *where* the skill ran. Moving the call site does not loosen the gate by one byte; writing `skill:auto-task-code-review` for a review the skill did not perform is the same lie it always was.

**So REQUIRE EVIDENCE that it ran, and treat its absence as a failed round.** This is the one integrity check the move actually costs you, and it is easy to leave out because the other rungs below all catch *loud* failures. Inline, the orchestrator knows the skill ran because the `Skill` call is in its own tool log — first-hand knowledge. **In a subagent that evidence is gone**, and a `general-purpose` agent handed the diff, the plan, TRACE.md and the prior rounds' findings has everything it needs to write a *plausible* review without ever calling the Skill tool. Such a report is not empty, not malformed, not truncated, and leaves the tree untouched, so no other rung fires and the round would pass with `tool: "skill:auto-task-code-review"` recorded for a review the skill never performed — the precise lie the paragraph above forbids, arriving through the one door the ladder did not watch.

**The marker is the skill's Phase-2 structured report, and ONLY that** — its scope / blast-radius / risk / review-dimensions block. A report without it is evidence the skill did not run: **treat it exactly as a malformed report** (the **report rung** below — not a round, retry once, then inline). Do NOT accept it and do NOT record the `tool` literal for it.

**EMITTED IS NOT RETURNED, and this is the half that is easy to get wrong.** The skill *prints* the Phase-2 block mid-turn and then, on a clean review, ends with the one-liner `Reviewed <scope>. No significant issues found.` Only the agent's **returned output** crosses the subagent boundary — so an agent that follows the skill faithfully can still hand back a final message that is just that one line, and a marker check would then reject a perfectly good clean review. Verifying that the skill *emits* the block proves nothing about what you *receive*. So the prompt MUST say it in those terms: **"reproduce the skill's full report — including its Phase-2 scope / blast-radius / risk / review-dimensions block — verbatim in your final message; that message is the only thing I receive."** Without that sentence the marker is unreachable on exactly the outcome you want most, and the check becomes a self-disabling feature rather than a guard.

**The discriminator is the BLOCK, never the length.** A clean review's report is legitimately *short* — that is a success, not a failure, and the **report rung** below says so. Short-with-the-block passes; missing-the-block fails, however long it is. Do not conflate the two: reading brevity as absence is the same defect in a new costume.

**Pick that marker and no other, because it is the only one the skill emits unconditionally** ("Phase 2 output: the structured report above, then continue immediately to Phase 3"). Do NOT extend the check to Phase 4 or Phase 5 content, however tempting the completeness is: the skill's own output discipline short-circuits a clean review after Phase 3 — *"If after Phase 3 there are no significant findings … otherwise stop there"* — so Prevent is skipped by instruction and Phase 5 has no findings to quote. A check demanding those would reject a **correct clean review**, discard it, burn the retry and force the round inline; the feature would disable itself on exactly the outcome you want most. That is not hypothetical — it is the defect the first version of this clause shipped, caught in review, and it is why the marker is deliberately one always-present block rather than the whole five-phase shape.

Two honest limits, stated rather than glossed: this is a *structural* signal, not proof — a determined agent could imitate the block — and the fallback is the same inline call the setting exists to move away from. It raises the cost of a silent substitution from zero to deliberate, which is the same standard every other gate flag in this pipeline is held to, since all of them are prose-trusted artifacts rather than hook-verified ones.

**Spawn shape.**
- ONE `general-purpose` Agent, **synchronously** (`run_in_background: false`, per the synchronous-spawn rule at Gate A). Prefix its `label` with `state.title`.
- **Its prompt MUST forbid edits, in those words.** `general-purpose` carries `Edit`/`Write`; `task-execution-verifier`'s declared `tools: [Read, Glob, Grep, Bash]` make an edit impossible by construction, and this agent has no such floor. An edit here changes the working-tree diff mid-review, which moves `reviewed_diff_sha` and blocks the commit. The reviewer reports; **the orchestrator applies every fix**, in the main loop, exactly as before.
- Hand it `.auto-task/<branch>/CONTEXT.md` and `TRACE.md` per the read-before-review contract, **plus the findings of every prior round this run** — see delta-scoping below for why that is load-bearing rather than courteous.
- **Hand it `PLAN.md`'s Acceptance Criteria table, and this bullet is not optional.** The reviewer's output contract requires an `ac:` on every finding — the number of the criterion it breaks, or `none`. It cannot cite a number it was never shown: the AC table lives **only** in `PLAN.md` (`STATE.json` carries `requirements[]`, not the numbered rows), so a spawn that hands over only CONTEXT/TRACE leaves `ac:` answerable exactly one way — `none` — on every finding, forever. That is worse than omitting the field, because `none` reads downstream as the positive claim "breaks no criterion", which argues *against* reopening and biases the loop toward defer/park. The measured cost of that bias is the whole reason the field exists: ~90 findings across three runs, 49 parked and never fixed. **Gate B has always done this** — its Step 1 spawn hands over "The Acceptance Criteria from `.auto-task/<branch>/PLAN.md`", which is precisely why keying its Step-2 clauses on a literal `ac:` works there. Pass the table with user-descoped rows removed, exactly as Gate A does, and say which were descoped and why.

**Three prompt clauses that protect the run's own bookkeeping. None is boilerplate; each closes a hole the edit-prohibition alone does not reach.**

1. **The reviewer writes nothing under `.auto-task/`** — not `STATE.json`, not `TRACE.md`, not `artifacts/`. Say so explicitly, because the sha check below **cannot** catch a violation here: that directory is kept out of git by the run's own exclude entry, so a write into it never moves the diff hash. This clause is the only thing standing between a helpful agent and a corrupted run record.
2. **Tell it that it is running under `/auto-task` orchestration.** That is the exact condition the review skill's read-before-review contract uses to suppress its own trace append. A fresh-context agent has no way to infer it, so an unlabelled spawn takes the standalone path and double-writes the log — one entry from the skill, one from the orchestrator, describing the same round.
3. **Tell it that it is the reviewer, not the caller.** The skill's Caller note directs *the caller* to update the `gates.*` flag and make the next tool call, and calls writing a recap instead a protocol violation. Every one of those directives is addressed to the orchestrator that spawned this agent. A read-only reviewer that tried to follow them would attempt exactly the state write clause 1 forbids. Its only output is the report.

**Rounds 2+ are DELTA-SCOPED, and this is what makes the change affordable.** Round 1 reviews the full working-tree diff. Every later round reviews only the delta since the previous round — the same *technique* Gate B's Step 1 uses, for the same reason: re-reading the whole accumulated diff means round N re-searches all N−1 rounds of fixes, so the search surface grows while the budget does not. Write the round's diff bytes to `.auto-task/<branch>/artifacts/review-<n>.diff` at **spawn** time, record that boundary as the round's **`diff_sha`** (Step C), and hand the next round `diff -u <that file> <(current diff)` plus the previous round's findings named explicitly.

**The boundary is `rounds[n-1].diff_sha` — NOT `reviewed_diff_sha`, and the distinction is load-bearing rather than pedantic.** The two fields differ on exactly the rounds delta-scoping runs on. `reviewed_diff_sha` is the **commit gate's** pinned field, written *only when a round comes back clean* (`references/state-schema.md`), so after a round that REOPENED — which is the only way a round 2 exists at all — it is still null or still points at some earlier clean round. Naming it here would leave the first delta-scoped round with no boundary, and the two ways out of that are both wrong: silently re-read the full diff, losing the cost bound this whole step is justified by, or write `reviewed_diff_sha` at spawn from a pre-fix tree and briefly pin a hook-read gate field to bytes no clean review covered. `rounds[n-1].diff_sha` has neither problem — Step C records a row on **every** exit, reopen included, so the previous round's boundary always exists — and the `artifacts/review-<n>.diff` file holds the bytes themselves, which is what makes the delta executable. (Gate B is not a counter-example: its `verified_diff_sha` is written at *spawn* and is bound by no hook, which is precisely why it can serve as a boundary and `reviewed_diff_sha` cannot.)

**The failure mode this is bounded against, stated plainly.** A reviewer with no memory of the run re-raises findings earlier rounds already considered and resolved — which is exactly the churn `0.29.0` and `0.30.0` were spent bounding, re-entering through a new door. Three things hold it: the read-before-review contract (CONTEXT.md + TRACE.md), the prior-round findings passed by name, and delta-scoping. **If rounds stop converging, that is the cause to suspect first**, and `review_in_subagent: false` restores the previous behaviour in one setting without touching the gate.

#### Step 0's degradation ladder — every way the spawn can go wrong, and where each lands

A review that runs in another context can fail in ways an inline call cannot. **None of these may deadlock the run, pass the gate, or leave `reviewed_diff_sha` pinned to bytes no review actually read.**

**Order the rungs like this, and the order is load-bearing rather than editorial.** Take the first case that applies:

1. **No agent returned at all** (the spawn itself failed). Nothing to compare and nothing to attribute — skip the sha check entirely and go straight to the retry rung. **This case must come first**, because a tree that moved during a window in which no reviewer existed did not move *because of* a reviewer: blaming it on one would discard a round, disable the subagent for the rest of the run and write a false TRACE incident, all triggered by an autosave, a formatter, or your own concurrent edit.
2. **An agent returned — then check the TREE before judging the REPORT.** The sha comparison is a fact about the world; every remaining rung is a judgement about a *report*. An agent that ignores "invoke the skill" is the same agent that ignores "do not edit", so the two failures correlate strongly — and a ladder that asked about the report first would hand that exact agent the *report* rung's handling, never run the sha check, never set `subagent_disabled`, and then let the retry capture its spawn-time baseline from the **already-edited tree**, folding a model-authored edit into `rounds[n].diff_sha` as if it were authored work.
3. **Only then, judge the report.**

Referring to these by ordinal is what went stale last time the order changed, so name them instead: the **spawn-failure** case, the **edit** rung, and the **report** rung.

- **The EDIT rung — the reviewer edited the tree despite the prohibition. Checked before the report, and only when an agent actually returned** (a failed spawn short-circuits above, per the ordering rule). Detect it: capture the diff sha at spawn (you already do, for delta-scoping), recompute it with the byte-identical pinned-flag formula the moment the agent returns, and compare. **A move means the tree changed while the review was reading it.** Then: discard that round's findings — they describe a tree that no longer exists, so acting on them is worse than losing them — **re-run the round inline against the current tree**, and **disable the subagent for the remainder of the run** so one incident cannot repeat every round. **Record both facts in state, not in your head:** the round's row gets `via: "inline-fallback"` (Step C), and `gates.code_review.subagent_disabled` is set `true`. The state write is what makes the disable survive a resume — a resumed orchestrator re-reads `review_in_subagent: true` and would otherwise re-enable the very agent that edited the tree. Note the incident in TRACE as well. **Do NOT automatically revert the reviewer's edits**: a scripted revert of model-authored changes is destructive and can take a legitimate concurrent edit with it. The commit gate stays honest without any re-pin here, and the mechanism is the hook rather than this rung: `reviewed_diff_sha` is written **only on a clean round**, so if the inline re-review reopens, nothing re-pins it and `enforce-gates.sh` keeps blocking the commit until some later clean round does — which is the correct outcome, not a gap. (Do not read the fallback as re-pinning: that would be the same `reviewed_diff_sha`-versus-`rounds[n-1].diff_sha` conflation corrected two paragraphs above.) The edit itself is left visible in the diff for the ordinary review and Gate B to judge.
- **The REPORT rung — the spawn failed; or the report came back empty, malformed, or truncated; or it lacks the skill's Phase-2 structured report** (the no-evidence-the-skill-ran case above — same rung, same handling, because the outcome is identical: no review this contract can vouch for; and per the ordering rule a bare spawn failure reaches this rung *without* the sha check having run). Note what is NOT on this list: a report that is short *because the review was clean* is a **success**, not a failure — brevity is never the test, the Phase-2 block is (see the marker rule above, including why the prompt must require that block to be **returned** and not merely emitted). No review happened, so **this is not a round**: append no `rounds[]` row, leave `gates.code_review.passed` alone, and do not touch `reviewed_diff_sha`. **Retry the spawn exactly once.** If the second attempt fails the same way, **invoke the skill inline for this round** and carry on — record `via: "inline-fallback"` on the round's row (see Step C) and note the reason in TRACE. A retry-forever loop, or a stop for the user, would both let an unavailable subagent hold a run hostage over a setting whose whole point is that either call site produces the same review.
- **Note what this detector does and does not see.** It compares the tracked working-tree diff, so it catches any edit to repository files. It is blind to `.auto-task/`, which is why the prohibition above is a prompt clause rather than a check — the two are complementary and neither substitutes for the other.

**In every degraded path `gates.code_review.tool` still reads `skill:auto-task-code-review`**, because the skill still performed the review — only its call site moved. The value tracks which reviewer ran, never which context it ran in; that is the same reason the hook needs no change when the default flips.

**`shadow_review` is skipped while this is on.** Its whole purpose is to measure what an independent reviewer catches that the main-loop review missed; with the review already independent it would be an independent review of an independent review, measuring nothing.

**The skip is recorded only when the user actually asked for the pass** — i.e. when the `shadow_review` setting is `true`. Then write `shadow_review: { status: "skipped", note: "review_in_subagent is on" }` rather than omitting the object, so the run's record answers "why is there no measurement here?" for someone who enabled it and would otherwise see silence. **When the setting is `false` — the default — the object stays absent exactly as before**, because there is nothing to explain and the no-shape-change guarantee in the schema depends on it. Getting this backwards writes the object on every stock run, which is the one thing that section promises never happens.

### Step A — grade every finding before deciding the round

**Apply the Gate B Step-2 reopen test verbatim** — do not restate or re-derive it. A Phase-4 finding costs a round if and only if at least one of **(a)** it breaks an approved Acceptance Criterion, **(b)** it is a runtime-reachable regression or bypass in the diff, or **(c)** it is a security or data-loss path. The `auto-task-code-review` skill's `Blockers` / `Required fixes` / `Follow-ups` categories are its *labels*; this test decides control flow, exactly as at Gate B, and for the same measured reason — a self-assigned `required` on README wording reopened the whole loop.

**YOU grade the finding; a reviewer-supplied field is an input, never a classification you may adopt unchecked.** This is the one place Phase 4 differs mechanically from Gate B, and getting it wrong makes the whole contract inert. Gate B's Step 2 keys clauses (a) and (b) on literal `ac:` and `reachable:` fields **because the verifier-agent prompt mandates that a Gate B finding carry them** (Step 1's "Additionally:" instruction). **`auto-task-code-review` now carries the same two fields** on every finding, by its own output contract — so a Phase-4 finding arrives with an `ac:` and a `reachable:` to read, and the deferral path no longer depends on you inferring both from scratch.

**What that does and does not change, because the distinction is the whole rule.** It changes the *starting point*: you begin from two stated facts instead of a blank. It does NOT move the decision — you still classify each finding against the two things you hold independently of the reviewer: **PLAN.md's Acceptance Criteria table** (does the finding falsify a row that is not user-descoped? → (a)) and **the diff** (is there a named input or sequence that reaches the failure at run time? → (b); does the path expose a credential, allow injection, or corrupt/lose data? → (c)). A reviewer that mislabels `reachable: docs-only` on a live regression must not be able to defer it by saying so; that is exactly why the grade stays here and why the fail-closed rule below keys on **your** uncertainty rather than on the field's absence.

**The field's absence is still handled, and it is no longer the common case.** A finding that arrives without the fields — a legacy report, a degraded round, a reviewer that ignored its contract — is graded exactly as before: from the AC table and the diff, failing closed. What changed is that the old rule could not read a field that never existed; the new rule reads it when present, trusts it for nothing, and still decides for itself.

**Fail closed on your own uncertainty, which is the operative form of Gate B's `ac:` rule.** If you cannot confidently place a finding — you cannot tell which AC row it touches, or whether a real input reaches it — **treat it as AC-breaking and reopen.** The safe direction is to do the extra work, never to defer something that might be a real breach. Record the classification and its basis alongside the finding, so a later reader can check the call rather than re-derive it.

**A finding that meets (a)/(b)/(c) is a REOPENING finding:** fix it now, re-run `/auto-task-verify` plus any affected AC bound-checks, set `gates.code_review.clean_pass_after_last_fix = false`, increment `iteration.review`, and re-invoke the review skill.

**A `blocker`/`required` finding that does NOT meet the test is DEFERRED, not parked and not round-triggering.** Append it to `gates.code_review.deferred[]` with its original label, its `file:line`, and why it did not meet the test — so the record shows what was set aside rather than hiding it. Deferral is **not** the Gate B disposition: Gate B parks such a finding permanently, while Phase 4 still **fixes** it, in the batch below. That difference is deliberate and was the user's explicit choice at the plan gate: a wrong README figure or a gutted assertion is a real defect and gets fixed; it just does not buy itself a full review cycle. **`follow-up`-labelled findings park in `state.followups` as before** — deferral applies only to the `blocker`/`required` labels.

### Step B — the deferred batch, spent once per run

**When a round returns ZERO reopening findings, `deferred[]` is non-empty, AND the batch is still unspent**, do not pass the gate yet. Apply the **whole** deferred set in ONE fix step, then run **exactly one** more review pass. Record that pass's row with `batch: true`. **The unspent condition is part of the entry test, not a footnote to it** — nothing clears `deferred[]` (the spent-marker is the `batch: true` row precisely so it cannot be inferred from the array being empty), so an entry test that omitted it would re-enter the batch on every later zero-reopening round, unbounded, on the contract's normal path.

- **The batch is spent once per run and never renews.** The spent-marker is **the existence of a `rounds[]` row with `batch: true`** — deliberately not a separate boolean, which could disagree with the record. Once a `batch: true` row exists, the batch is gone for the rest of the run.
- **Disposition of a finding raised once the batch is spent — the batch pass's own included.** A **reopening** finding re-enters Step A's graded loop and is graded, fixed and recorded like any other; the batch never exempts a real breach. **It is not exempt from Step C either** — say so plainly, because the earlier wording ("re-enters normally") read as a promise of an ordinary fix round and it is not one. The batch fires only on a `reopened: 0` round, so the batch pass's own reopening finding is compared against a predecessor of 0 and the convergence test fires. That is correct, not a defect: by then the loop has already bottomed out once, so a fresh reachable breach is exactly the evidence clause 5 exists to put in front of the user. Expect a surface here rather than another round. A **non-reopening `blocker`/`required`** does not earn a second batch — that is what stops the cure becoming the disease, since a batch that could renew is the same unbounded loop in a smaller room (the reason `lb_gate_b_regate_cap` is per-site-per-run rather than per-round). Instead it **parks in `state.followups` at every tier.** This is ONE rule covering every round after the batch, deliberately **not** scoped to the batch round: rounds continue past it, so a *later* round can raise a fresh non-reopening `blocker`/`required` with no batch left to fix it in, and a rule that named only the batch round would leave that case unhandled.

  **The LIGHT-tier limitation, now closed — and why the closure took this shape.** Parking is safe on STANDARD/HEAVY because **Gate B normally follows and re-applies the identical test** (normally, not always — Gate B can be descoped via `skipped_reason` or park-granted via `park_non_blocking`, and both are user grants that carry the same exposure knowingly), giving a mis-graded finding a second, independent look. **LIGHT used to skip Gate B**, so a park there was final and the gate passed over a `blocker`/`required` nobody re-checked. **LIGHT now runs Gate B, capped at one pass** (`lb_gate_b_cap light` → 1), so that residue is gone at every tier and parking is backed by the same independent re-grade everywhere.

  **The reasoning is kept because it is what justified the change, and because it is the wrong argument to lose.** It was tempting to call the residue cosmetic, since *non-reopening* already means the finding breaks no Acceptance Criterion, is not runtime-reachable and is not a security/data-loss path. That reasoning assumes the grade is **correct** — and the grade is the orchestrator's own, made from the same context that wrote the code. What Gate B adds is a second, independent look that catches a **mis-grade**, and a mis-graded finding is by construction not cosmetic. The exposure on LIGHT was precisely the case where the orchestrator graded wrong and nothing re-checked it. It was bounded — LIGHT is `max(D, R) <= 2` — but it was a real hole, and the run that documented it also measured its shape: Gate B's first pass found in one pass what six Phase-4 rounds had missed. That measurement is the whole case for one pass rather than none.

  **One pass, not two, and no LIGHT-only hold.** One, because LIGHT is the fast path and the measured value is in the *first* independent look, not in a loop. And no hold: **a LIGHT-only hold was implemented and then removed** during the graded-loop work, and that removal stays on the record because it is the more useful lesson — it had to be restated at every site that states the advance, and across three gates it produced more defects in its own hardening than the hole it closed could have cost. Giving LIGHT the ordinary gate is the opposite move: it deletes a special case instead of adding one, which is why it costs one table cell and a cap value rather than prose at five sites.
- **The batch lands BEFORE the gate passes, at every tier.** So a deferred finding is fixed, not shipped — at every tier, LIGHT included. Be precise about the residue, because the unqualified claim is false: this covers everything in `deferred[]` when the batch fires. A non-reopening `blocker`/`required` raised *after* the batch is spent has no batch to land in, and is handled by the rule above — parked where Gate B will re-grade it, at every tier now that LIGHT runs the gate too (see the closure note above).
- **Its edits are new authored bytes, so the staleness hash moves.** The batch's single re-review is therefore not overhead this contract invents: `enforce-gates.sh` already blocks the commit unless `gates.code_review.reviewed_diff_sha` matches the current diff, so *any* fix after a clean review requires one more pass regardless. The batch's cost over parking is exactly that one pass.

### Step C — record the round, then test for convergence

**Append to `gates.code_review.rounds[]` on EVERY exit, reopen included** — the same discipline, and the same reason, as Gate B's "record the pass FIRST": an absent `rounds[]` counts as zero rows, so a round that resolves without recording silently disarms the convergence test on the very path it exists to bound.

The row is `{ n, blockers, required, reopened, deferred, followups, batch, via, diff_sha, at, files }`, where `n` is `1 +` the number of prior rows, `blockers`/`required` are the raw **label** counts, `reopened` is the count of findings that met (a)/(b)/(c), `deferred` is the count added to `deferred[]` by this round, and `diff_sha` is the boundary this round reviewed.

**`files`** is the list of repo-relative paths this round's fixes actually edited (`[]` when the round reopened nothing and therefore edited nothing). It is **presentational and inert to control flow** — nothing in this gate, the convergence test, or the fix-loop budget reads it; those key on `reopened` and `iteration.*` respectively. It exists so Phase 5's `## Review this first` can tell a reviewer *where this run fought*, which is the one signal no generic review tool can produce. **Absent `files` is legitimate and never an error** — a row written before this key existed, or by a resumed run, simply contributes no paths, exactly as an absent `rounds[]` counts as zero rows. It is orthogonal to `via` below: `via` records *where* the round ran, `files` *what* it touched, and neither is derived from the other.

**`via` — where this round's review actually ran**, one of exactly three values, and the three are **total over every path Step 0 can take** — check that before adding a fourth:

- **`subagent`** — the review ran in the spawned agent. Only this value means the round was independent.
- **`inline`** — the review ran in the main loop. Two ways to get here and they are deliberately one value, because the record's question is *where it ran*, not *why*: `review_in_subagent` is off, **or** it is on but `gates.code_review.subagent_disabled` is `true`, so Step 0's two-condition spawn decision routed inline. The second case covers every round after an edit incident, which is the common one — the ladder disables the agent for the rest of the run.
- **`inline-fallback`** — the degradation round *itself*: the one that exhausted its retry, or the one whose sha moved. Distinct from `inline` because this round is where something went wrong, and TRACE carries the reason.

**Write it on every row, not only on a degraded one.** It is the only thing separating an independent round from a self-reviewed one after the fact, and Step 0's ladder makes that a live distinction rather than a theoretical one: a twice-failed spawn falls back inline, and a detected edit re-runs inline *and* disables the subagent, so rounds from that point on are inline by construction. Leave `via` off and a run finishes with `review_in_subagent: true`, a majority of its rounds self-reviewed, and nothing in the record saying so. An absent `via` on a legacy row reads as unknown, never as `subagent`.

**Where `via` does and does not reach, stated exactly — do not overclaim it in either direction.** Two of the three derivations read it, and the third deliberately does not:

- **`record-outcome.sh` reads it** — it derives `review_rounds_independent` into the local outcomes ledger.
- **`auto-task-stats.sh` reads it** — the same derivation, byte-identical, plus the `med_indep` / `n_indep` aggregation behind the `indep` column of the by-tier table.
- **`send-telemetry.sh` does NOT read it, and must not.** The independence count was a deliberate **local-only** decision: sending it would need a column in the hosted schema and a migration applied to a live database, which is precisely the scope that decision excluded. A negative control in `tests/gate-b-loop.test.sh` asserts this hook never reads the field, so adding it is a test failure rather than a silent widening.

`review_rounds` is unchanged by all of this — it counts rows, and `via` is a field *within* a row, so writing `via` cannot protect that count and omitting it cannot corrupt it. It keeps the same `has("rounds")` discriminator (the count when the key is present, `null` when absent; **never** a bare `rounds[] | length`, the hard-zero regression three review rounds were spent removing).

**The independence count carries the same discriminator, and one more unknown of its own.** An absent `rounds` key yields `null` (nothing about that run is measurable) exactly as `review_rounds` does. Additionally, a **row** that omits `via` is *not counted as independent* — the rule two paragraphs up says an absent `via` reads as unknown and never as `subagent`, so counting it would invent independence that was never recorded. Only `via == "subagent"` counts; `inline` and `inline-fallback` do not.

**Why the null-vs-zero distinction is stricter here than anywhere else in the ledger:** every row written before this field existed carries no value at all, so a reader that coalesced null to `0` would report "zero independent rounds" across the entire history and manufacture exactly the regression someone would be looking for. Readers EXCLUDE nulls (`med_indep` selects numbers first, and `n_indep` is what separates "no data" from a real `0`). The ledger is **append-only**, so a fabricated `0` written today cannot be repaired later.

**What this replaced, kept because it explains the shape.** This paragraph previously read: "It lives in `STATE.json` and nowhere else … If the split ever matters, the fix is a derived count in the three derivations, not a reinterpretation of `review_rounds`." The split did come to matter — measured across five local runs, `via` was absent on four of them, so "was this round independent?" could not be answered from the record for any completed run. The remedy taken is the one that sentence named: **a derived count**, not a reinterpretation. The only departure is scope — two derivations, not three, because the payload half was descoped to avoid a live migration.

**`reopened` is the declared convergence basis.** Never `blockers`/`required` — those are label counts, and a deferred `blocker` cost no round, so counting it would let a run that deferred everything look like it was still churning and never converge. This is the identical basis and the identical reasoning as the Gate B convergence test above; when the two readings could differ, this one governs.

**Convergence test (Loop-rule clause 5, applied here).** Compare this round's `reopened` against the previous round's. **If it did not DECREASE, the loop has converged — surface** (`expected_next_action: "user-approval"`), showing the per-round table from `rounds[]`. One round is enough to fire; do not wait for two. As at Gate B, surfacing is the only outcome this test has: it is reached only when the round had at least one reopening finding, since a zero-reopening round has already gone to Step B or passed the gate — so a fired test always has a live AC breach, runtime-reachable regression or security path on the table, and parking those unseen would be laxer than what the budget path does on the same evidence.

**Why no separate entry-time pass cap, unlike Gate B.** A graded Phase 4 is already bounded by construction: `reopened` is a non-negative integer that the convergence test forces to *decrease*, so a surviving sequence terminates in at most the first round's count. A count that **rises** — fixes introducing new reachable defects — is precisely what the test catches, on the very next round. Ungraded Phase 4 had no such property, which is how it reached 9. A hard cap on top would be redundant with the test, and adding a mechanism the existing test already covers is the defect-surface trade this project has measured the wrong side of before.

### Shadow second opinion (opt-in, measurement only — `shadow_review`)

**Off by default. When `shadow_review` is `true`, run this ONCE per run, immediately after Phase 4 sets `gates.code_review.passed = true`, and before advancing to Gate B.**

**Superseded while `review_in_subagent` is on** (which is the default) — see Step 0's closing rule. This pass measures what a main-loop self-review misses; once the review itself is independent, there is no self-review left to measure. Record the skip as a status rather than dropping the object.

**What it is for, stated plainly so it is not mistaken for a gate.** In the `review_in_subagent: false` configuration — the only one where this pass runs at all — Phases 2, 3 and 4 all run in the main loop, so the model that wrote the diff also self-verifies and code-reviews it, and Gate A and Gate B are the only fresh-context passes. The open question is how much that self-review actually misses — and that is a question about *this* repo and *these* runs, not one to settle by argument. This pass measures it.

**It decides nothing.** It sets no gate flag, reopens no round, blocks no commit, changes no `expected_next_action`, and never routes. A finding it surfaces is recorded, not acted on. That is the whole point: an opt-in measurement that can alter control flow is no longer a measurement, and would reintroduce the review churn `0.29.0`/`0.30.0` were spent bounding. If the data says the misses are real, the answer is to change Phase 4 deliberately in a later release — not to let a shadow pass quietly become an authority.

**How to run it.** Spawn ONE `general-purpose` Agent (prefix its `label` with `state.title`), synchronously, per the synchronous-spawn rule at Gate A. **Its prompt MUST forbid edits, in those words — it reads and reports, nothing else.** This is not boilerplate: `general-purpose` carries the full tool set including `Edit`/`Write`, unlike the `task-execution-verifier` agent whose declared `tools: [Read, Glob, Grep, Bash]` make an edit impossible by construction. A single "helpful" fix from this pass would change the working-tree diff after Phase 4 went clean, which moves `gates.code_review.reviewed_diff_sha`, blocks the commit at `enforce-gates.sh`, and breaks the single-commit rule — a measurement pass must not be able to touch the artifact it is measuring. Its prompt MUST instruct it to **invoke the `auto-task-code-review` skill** via the Skill tool on the working-tree diff, handing it `.auto-task/<branch>/CONTEXT.md`, `TRACE.md` **and `PLAN.md`'s Acceptance Criteria table** per the read-before-review contract. **The AC table is not optional here either, and the reason is sharper than at Step 0:** this pass's whole output is `missed[].would_have_reopened`, graded with Phase-4's Step-A test **by reference** — whose clause (a) is "its `ac:` names a row in PLAN.md's AC table". Hand over CONTEXT/TRACE alone and every `missed[]` entry carries `ac: none`, so clause (a) can never fire and the measurement can no longer tell a missed AC breach from a missed README nit — which is the one distinction it exists to make. **Do NOT hand it a hand-rolled review prompt** — a bespoke prompt would measure "some prompt vs the skill", which answers the wrong question and violates the same rule Phase 4 is pinned by. If the agent reports it cannot invoke the skill, record `status: "unavailable"` and move on; do NOT let it fall back to reviewing by hand.

**What to record.** Append to `state.shadow_review` (additive; absent on every run where the setting is off):

```
{ "status": "ran|unavailable|skipped", "at": "<ISO>", "diff_sha": "<the reviewed_diff_sha it ran against>",
  "self_findings": <count from the final Phase-4 round>, "shadow_findings": <count>,
  "missed": [ { "file": "<path:line>", "summary": "<one line>", "would_have_reopened": true|false } ],
  "note": "<one line; e.g. why it was unavailable>" }
```

`missed[]` is the measurement: findings the shadow pass raised that the final Phase-4 round did not. Grade each one's `would_have_reopened` with the SAME Step-A test Phase 4 uses (AC breach / runtime-reachable / security-data-loss), **taken by reference so the two cannot drift** — that field is what distinguishes "the self-review missed something that mattered" from "the self-review missed a README nit", and only the first is evidence for changing Phase 4. An empty `missed[]` is a real and useful result; record it rather than omitting the object.

**Bounded absolutely: one pass, one run, no loop.** It never re-runs after a fix, because there are no fixes — nothing it reports is acted on. If it fails or times out, record `status` and continue; it must never block the advance to Gate B.

**The per-round record is also what makes the fix-loop budget's ack ritual honest.** That ritual (see `fix-loop-budget-mechanics` below, and the spine's Fix-loop budget section) requires the surface to show "the **per-round finding severities** so the user can see for themselves whether returns have diminished." Gate B could satisfy that from `passes[]`; Phase 4 had no source at all and could only re-narrate from memory. `rounds[]` is that source.

**Legacy and resumed state.** An **absent or empty `rounds[]` counts as zero rows** — the same tolerance `gates.gate_b.passes[]` already applies to runs that predate its contract. So a resumed run has no prior round to compare (the test cannot fire on a single row) and has not spent its batch. Both defaults err toward doing the work: they grant a batch and withhold a surface, never skip a fix.

**Minimal fix.** Correct the defect in place. A fix that can only be made by introducing a new subsystem, abstraction, mode or escape hatch is itself a **signal to surface**, not a licence to build: in the measured run that motivated this section, each round's fix was a whole new subsystem — a scan mode, a merge step, a fallback fingerprint — and every one became the next round's subject, which is precisely how a fix loop feeds itself. When the minimal correction is not available, say so at the surface and let the user choose scope, rather than growing the diff and re-entering the loop.

**Trip-wire (same shape as Gate B's):** after grading a round, before ending the turn — did you (a) append the `rounds[]` row AND (b) make the next tool call (a fix Edit, the batch fix, the Gate B spawn, or the Phase 5 stage)? If not, you are about to stall. Do not end the message.

## fix-loop-budget-mechanics — relocated verbatim from SKILL.md

_The loop-count definition and the ack ritual, moved here from the spine's "Fix-loop budget" section. They live beside Gate B because Gate B's Step-0 entry check is what now invokes them: the budget is consulted at Gate-B entry, not only at commit time, since `enforce-gates.sh` sees only `git commit` and this loop never reaches one. The spine keeps the section, the two hook bullets, the effective-budget formula, and a pointer here._

**Loop count** = `max(iteration.fix, iteration.review)` — and it must be both counters, because the two track different halves of the same churn. `iteration.fix` is bumped only on the Phase-3 self-verify failure path; every Phase-4 review round and every Gate-B feedback round bumps `iteration.review` instead. **Narrowed by `phase-4-round-mechanics` above:** a Phase-4 round bumps it only when it **reopens** — a round whose findings were all deferred records a `rounds[]` row and bumps nothing — so the counter measures rounds that cost a fix, which is the volume this budget bounds. A budget keyed on `fix` alone would wave through a run at `fix: 0, review: 28` — 28 rounds of iteration, the exact volume this budget exists to bound. Both hooks measure the identical `max`, so on any well-formed state the commit block and the turn-end release agree. On a state neither can verify — a counter that is non-numeric, negative, fractional, or too wide for a 64-bit compare — they diverge *by design*, because their fail policies are opposite: the gate blocks the commit (fail-closed) while the release stays silent (fail-open) and the run surfaces the ordinary way, by setting `expected_next_action: "user-approval"`. It is a `max`, not a sum: a run is bounded by how far its longest loop has run, and one ack still clears it.

_(Only the loop-count rationale above was carved here. The user-gate ritual for acknowledging an over-budget run stays in the spine: it is an actionable procedure at a yield point, classified non-deferrable, and two spine-only assertions pin it there.)_
