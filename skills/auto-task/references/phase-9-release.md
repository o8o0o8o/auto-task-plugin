## phase9-body — relocated verbatim from SKILL.md


**On entry, set `phase: "release"`** (`expected_next_action: "auto-continue"`).

The last phase. Work that has landed can be cut as a release in the same run rather than in a second session: a version bump, a `CHANGELOG.md` entry, one `chore(release): vX.Y.Z` commit, and one annotated tag — **all local**. It runs when `release_mode` is `always`/`ask` (opt-in; **default `skip`**), after Phase 8, and it is the **last writer of `phase: "done"`** on every path that reaches it.

**This phase makes ONE additional authored commit** — the third and final exception to the Single-commit rule (see "Exception 3" there), permitted on exactly the same terms as the Phase-6 bot-fix commit: it re-passes the full gate machinery first, so `enforce-gates.sh` admits it with **no hook change**. It is also why Phase 9 sits *before* `phase: "done"` and not after: after `done` the gate hook exits 0 and `record-outcome.sh` has already fired, so a release cut there would be both ungated and unrecorded.

**Interruption is handled by SURFACING, not by auto-resume (deliberate scope choice).** Cutting a release rewrites git history, and an automated recovery that guesses wrong can re-cut a release the user unwound or re-apply a reverted bump. So this phase does **not** try to resume itself. Instead every mutating action is preceded by an `in-progress` marker, and a resumed run that finds one **stops and hands the recorded state to the user** (step 1). The invariant that matters is preserved: *an interrupted release never silently re-cuts and never reports success.* Everything past that — finish it, undo it, or leave it — is a human call, which is proportionate for an opt-in, default-off step and is why this phase needs no crash-recovery state machine.

Read the live settings (do not trust only the Phase-1 snapshot): `mode = settings.get release_mode` (default `skip`), `cmd = settings.get release_command` (default empty).

**Status-write rule (applies to EVERY status this phase sets — read it before step 1).** Whenever you write `release.status = "<value>"`, **also append a matching `state.history` entry** `{ phase: "release", result: "<the same value>", at }` (plus whatever detail that outcome carries — `version`, `step`, `files`, `value`, a reason). The resume check in step 1 reads `state.history`, so a status written only to the object is invisible to it. On a completed release set `status: "applied"` explicitly and log `result: "applied"`. **One carve-out, and only one: `accepted-partial-failure`.** When the user is shown a half-cut release and accepts it as-is (the resolution rule's fourth outcome), the `release.status` deliberately STAYS `partial-failure` — relabelling it would dress an incomplete release up as success — while the history entry records `result: "accepted-partial-failure"`. So here alone the two names diverge, by design: the status describes *what the release is*, the history entry describes *what the user decided about it*. `accepted-partial-failure` is therefore a **history-only** value and is deliberately NOT in the `release.status` enum — the "every site naming a release state must draw from that set" rule in the `release` object prose governs `status` values, and this is not one. Never write it to `release.status`. Every value in the `release.status` enum is either **terminal** (step 9 writes `done`) or **surfaced** (step 1 hands it to the user), with exactly one **transitional** exception — `resolved-re-derive`, which step 1 consumes by continuing to step 2. It **can be observed at rest**: on the non-degrading path steps 2 and 3 write no status, so it persists across step 4's `ask` prompt for as long as the user takes. That is benign (nothing was cut, and the next step-1 read consumes it and re-derives) but it is the honest description — the guarantee is *consumed on the next step-1 read*, not *overwritten on the same pass*. That split (two resting kinds + one consumed-immediately value) is what keeps the vocabulary closed: no value can sit in the state file without either finishing the run or handing it to the user.

1. **Resume check (FIRST, before anything else) — surface, never auto-resume.** Read the newest `release` entry in `state.history` and branch on its `result`. **All three surfaced states share ONE resolution rule (below), so every one of them has a route back to terminal — a surfaced state that could not be resolved would make the run permanently non-terminal, which is its own kind of dishonesty.**
   - **`in-progress`** — a mutating action was in flight when the session died, so the changelog entry, the bump, the commit or the tag may each be done, partly done, or not started. **Do not infer which from the tree, and do not re-invoke `auto-task-release`** — a `report-only` pass cannot reliably distinguish "already released" from "nothing to release", and guessing is how a release gets cut twice. Instead **STOP and hand it over:** keep `phase: "release"`, set `expected_next_action: "user-approval"`, and surface the marker's recorded detail verbatim — the `step` it died at, the approved `plan` (version + bump + entry text), the `files` touched — alongside the current observable state (`git log -1 --format=%s`, `git tag --list vX.Y.Z`, `git status --short`) and the undo commands from step 8's unwind paragraph. Say plainly: *"A release was in progress and I will not guess at resuming it. Here is the state and the commands to finish or undo it; resolve it and tell me, or re-run `/auto-task` when you are done."* Do not continue to step 2 in the same turn. **If `step` names a stage this version of the phase no longer has, treat it exactly like an unrecognized value (last bullet) — surface it, do not map it onto a current stage.**
   - **`partial-failure` / `failed`** — likewise surfaced, never re-derived. Re-surface the stored `release` record (version, commit SHA if any, what is missing, the reason) plus the unwind commands, keep `phase: "release"` / `expected_next_action: "user-approval"`, and wait. **These are the user's to resolve by hand** — auto-task does not finish, retry, or revert them.
   - **`accepted-partial-failure` — the user was shown a half-cut release and chose to leave it as-is; genuinely finished, go straight to step 9's terminal write.** Written by the resolution rule's fourth outcome, and read here for exactly one reason: the acceptance is a *decision*, and without a history entry carrying it, an interrupt between that decision and step 9's terminal write would land on the still-newest `partial-failure` marker and re-surface a release the user has already settled. Do **not** re-derive and do **not** re-ask — the half-cut state is intentional. Carry the recorded `version` and `missing` into step 9's record so it stays plain that a tag (or commit) is absent by the user's choice, not by omission.
   - **`applied` or `declined` — genuinely finished; go straight to step 9's terminal write.** These two must NOT be re-derived: an `applied` release for the current version is done and re-running step 3 could cut it twice, and a `declined` is the user's "not this run" answer, which it would be rude to re-ask. **They are two of the three protected values — `accepted-partial-failure` (the bullet above) is the third**, for the same reason: it too records a decision the user already made, so re-deriving it would re-ask. Every *other* value is safe to re-derive because nothing was cut.
   - **`nothing-to-release` / `runbook` / `deferred-pr` / any `skipped-*` — fall through to step 2 for a LIVE re-read.** On every one of these paths **nothing was ever cut**, so there is no double-release risk — and short-circuiting them to step 9 would re-introduce exactly the cross-session staleness step 2 is hardened against. Concretely: the run recorded `skipped-skill-absent` / `skipped-invalid-value` / `runbook`, the session died before step 9 wrote `phase: "done"`, and the user then did the obvious thing — ran `install.sh`, fixed the typo, set `release_command` — and resumed. Treating the stale marker as final would silently never cut the release and report `done` citing a reason that is no longer true. Step 2's skill-absent bullet spells out this hazard for the same class of value and hardens against it; step 1 must not defeat that one step earlier, where the hardening cannot run. Re-deriving here is safe *because* nothing was cut, which is the same precondition that makes the resolution rule's third outcome safe.
   - **No `release` entry** — a fresh entry; fall through to step 2.
   - **`resolved-re-derive`** — the user resolved a surfaced state, you verified nothing was cut, and a release is still warranted (written by the resolution rule below). Nothing is in flight and nothing was cut, so **fall through to step 2** and re-derive. This is the only value that routes onward rather than surfacing or terminating. It is consumed by *this* read: continue to step 2, and the run then writes a real outcome at the next status-writing branch. It may legitimately still be the newest entry while the run sits at step 4's `ask` prompt — that is expected, not a bug.
   - **Anything else — an unrecognized `result` — is SURFACED, never a fall-through (fail safe).** A value outside the enum can only come from a different plugin build (the pre-descope `applying` / `applied-pending-authorization` / `re-gating` / `committing` / `descoped` markers), a hand-edited STATE, or a truncated write — and in every one of those cases *something may already have been done*. Falling through to step 2 would re-derive and re-cut it, which is the exact invariant this phase exists to protect. So: surface it like `in-progress` (record the raw value verbatim so the user can see what it was) and wait. This mirrors the value-domain hardening step 2 applies to `release_mode` and `state.landing`; step 1 guards the *mutating* window, so it needs the fail-safe more, not less.

   **Resolution rule (how ANY surfaced state returns to terminal).** When the user says they have resolved it, do not take their word for the outcome — **verify the observable state yourself** (`git log -1 --format=%s`, `git tag --list vX.Y.Z` + `git cat-file -t`, `git status --short`, and the version sources) and record what you actually observe, choosing from exactly four honest outcomes:
   - **The release is complete — and it is the release that was planned.** Verify identity, not just existence, and **do not assume the release commit is still `HEAD`** — the user may have kept working after resolving. First *locate* the commit: `git rev-parse -q --verify "refs/tags/vX.Y.Z^{commit}"` when the tag exists, else `git log --format=%H -1 --grep="^chore(release): vX.Y.Z$"`. Then verify against **that** commit (not `git log -1`): its subject is exactly `chore(release): vX.Y.Z` **for the marker's `plan.version`**, `git rev-parse "vX.Y.Z^{commit}"` resolves to it (proving the tag points at it, which `git cat-file -t` alone does not), `git cat-file -t vX.Y.Z` is `tag`, and `git show --stat <that commit>` shows only the changelog + version manifests. Then → `status: "applied"`, go to step 9. **Whether it is still `HEAD` changes only which unwind you hand over, never whether the release counts as complete:** step 8's unwind paragraph already draws exactly that distinction (the hard-reset form only when the release commit is still `HEAD` and the tree is clean, `git revert <release-sha>` otherwise). Anchoring *completeness* to `HEAD` would strand a correct, finished release permanently non-terminal — outcome 1 would fail its subject test, outcome 2 is false because it was not undone, outcome 3 is false because something was cut — leaving only the catch-all, which is precisely the "route back to terminal" guarantee this rule exists to keep. **If the user released a DIFFERENT version than the plan** (they re-judged the bump, or rewrote the entry), do NOT record the plan's version as applied — the record would name a version that was never cut and the persisted `release.unwind` would point at a nonexistent tag. Instead re-read the version sources for what was *actually* released and record that, noting the divergence from the plan; if you cannot establish it confidently, use the catch-all below. Likewise if the commit sweeps in unrelated work, say so rather than persisting an unwind that would discard it.
   - **It was undone, and the user does not want it re-cut** → `status: "declined"`, go to step 9. **Deliberately `declined`, not `nothing-to-release`:** `declined` already means "the user decided against this release", and it is one of the three values step 1 refuses to re-derive (with `applied` and `accepted-partial-failure`). `nothing-to-release` is routed to a live re-read on the premise that *nothing was ever cut* — true of step 3's own no-op, but false here, where a release **was** cut and then unwound. Reusing it would let a resume (after an interrupt between this write and step 9's `phase: "done"`) re-derive, find the bump missing, and under `always` re-cut with no prompt the very release the user just declined. One value must not carry two producers with opposite safe routings.
   - **Nothing was cut and the release is still warranted** — e.g. the step-3 refusal, where the user fixed `release_command` to a file-only form, or a step-6 `failed` where they reverted the bump → **supersede the surfaced marker and fall through to step 2** to re-derive from scratch. This is safe *precisely because* the observable state shows nothing was cut; it is the one case where re-entering the pipeline is correct rather than a re-cut. Do NOT force this case into `applied` or `nothing-to-release` — both would be a false terminal record for a run that still owes a release.
     **Set `expected_next_action: "auto-continue"` on this outcome (REQUIRED).** It is the only one of the four that does not route to step 9 — the other three reach step 9, which sets the field as part of its terminal write — so without this clause the run would fall through to step 2 with the field still on the `"user-approval"` the surfaced state left behind, and the Stop hook would *permit* a turn-end mid-step-2. That is a stall, not a wrong release action (nothing is cut either way), but the global "set the field at EVERY state write" rule applies here like anywhere else, and this is the one branch where forgetting it has a visible cost.
     **How to supersede it (`state.history` is append-only — you cannot delete the marker).** Append a new entry `{ phase: "release", result: "resolved-re-derive", superseded: "<the surfaced result you resolved>", at }` and set `release.status = "resolved-re-derive"`. Appending — never deleting — is the same supersede-by-newest-entry idiom step 1 already reads and that step 2's skill-absent bullet relies on. Without it the surfaced marker stays newest, so an interrupt anywhere in steps 2-3 would re-surface a state the user has already resolved, pointing at a stale `plan`. `resolved-re-derive` is therefore a recognized value in its own right — see the branch for it above — and is the one status that is neither terminal nor surfaced but *transitional*: step 1 consumes it by continuing to step 2, and the run writes a real outcome at the next status-writing branch. It **can legitimately be observed at rest** while the run sits at step 4's `ask` prompt; the guarantee is *consumed on the next step-1 read*, not *overwritten on the same pass*.
   - **The release is partly cut and the user accepts it as-is** — e.g. the commit landed but the tag did not, and they decline both the continuation and the unwind. Verify what actually exists, then keep `status: "partial-failure"` — **do NOT relabel it as success** — record the acceptance and exactly what is missing, and go to step 9, which treats an *accepted* `partial-failure` as terminal. **Record the acceptance where a step-1 read can SEE it (REQUIRED).** The acceptance is a fact about the *decision*, and step 1 branches on `state.history`, not on the `release` object — so an acceptance written only to the object is invisible to it, and an interrupt between here and step 9's terminal write would re-surface a half-cut release the user has already knowingly accepted, asking them to decide it a second time. So append `{ phase: "release", result: "accepted-partial-failure", version, missing: "<tag|commit>", at }` — the same append-only supersede-by-newest-entry idiom `resolved-re-derive` uses to carry `superseded`. Step 1 recognizes that value as terminal-and-already-decided (see its branch list) and routes straight to step 9 instead of re-asking. Without this outcome a user who declines both offered options would match none of the others (outcome 1 fails because the tag does not resolve to the commit, outcome 2 is false because nothing was undone, outcome 3 is false because something *was* cut) and the run would sit surfaced forever — the same permanently-non-terminal hole this rule exists to close. An imperfect outcome the user owns is a finished one.
   If the observable state matches none of the four (it contradicts what the user reported, or is ambiguous), stay surfaced and say what you observed versus what you were told. **Never record a terminal status you did not verify.**

   **Gate honesty on the resolution path (REQUIRED).** A release commit the *user* made is not one auto-task gated: `enforce-gates.sh` only intercepts commits auto-task itself runs. So when you record `applied` on this path, also record — in `release`, in the `## Release` CONTEXT section, and in the final summary — that **the release commit was made outside auto-task and is therefore outside its gate coverage**, plus the state the gates were left in (a step-6 `failed` leaves `gates.gate_b.passed = false` and `reviewed_diff_sha` un-refreshed). **Do NOT restore or set any gate flag you did not earn** — the flags are checkable artifacts, and flipping one here would be the speculative-flag violation the pre-commit hook exists to prevent. The run-level invariant stays true as written: *every authored commit **auto-task makes** is individually gate-reviewed* — a user's own commit is theirs, and the record must say so rather than letting the run imply gate coverage it never performed.
2. **Resolve the mode (live read, fail-open) — five distinct degrades.** Locate `settings.sh` via the three-probe pattern (`CLAUDE_PLUGIN_ROOT` is empty in the Bash-tool env, and each Bash call is a fresh shell, so re-resolve it here). Then:
   - `skip` → `release = { status: "skipped-disabled", mode: "skip", at }`, and go to step 9 (terminal).
   - **Any unrecognized value** — the reader validates key *presence*, not value domains, so a hand-edited `"yes"` arrives verbatim — is read as `skip` and recorded distinctly as `status: "skipped-invalid-value"`. **Record the offending value in the `state.history` entry, NOT in `release.mode`:** `{ phase: "release", result: "skipped-invalid-value", value: "<what was found>", at }`. History entries are free-form, whereas `release.mode` is the closed enum `skip|ask|always`; set `mode: "skip"` (the value it was read as) and let the history entry carry the raw text. Settings unavailable → `skipped-disabled`.
   - **`auto-task-release` not in this session's available-skills list** → force skip with `status: "skipped-skill-absent"`. Probe for **either** registration form per the preflight's Invocation-name note (`auto-task:auto-task-release` under a marketplace install, or the bare `auto-task-release` under the `install.sh` fallback) — testing only the bare name would silently disable the step on every marketplace install. Check this **live**, not from a `define-preflight` history entry: `state.history` is append-only across sessions, so a stale `release-skill-absent` entry would keep disabling the step after the user re-ran `install.sh` to fix exactly that. Do **not** improvise the release yourself — that would escape the skill's never-push/never-publish and never-hand-edit-a-manifest rules.
   - **Anything other than an explicit `state.landing == "direct"` → defer.** A `chore(release): vX.Y.Z` commit belongs on the default branch, not on a feature branch awaiting review, where it would land inside the PR and be released only if and when that PR merges. So **test for `"direct"`, not against `"pr"`** — the check must fail *safe*: `pr` defers, and so does an **absent** `state.landing` (pre-existing runs predate the autonomy/landing fields, and the `landing_model` default is `pr` anyway) or any **off-domain** value (`"PR"`, a hand-edited string). Testing `== "pr"` instead would let every one of those cut a release onto a PR branch — the exact outcome `deferred-pr` exists to prevent — and it is the same value-domain trap `release_mode` is already hardened against two bullets above. In every deferring case: record `status: "deferred-pr"`, emit the release plan as a paste-ready runbook to run after the merge, and go to step 9 (terminal — auto-task owes no further work). Only an explicit `landing: "direct"` proceeds to cut a release commit.
3. **Resolve the release plan FIRST, before any prompt — in `report-only` mode.** Invoke the **`auto-task-release`** skill explicitly in `report-only` mode (its step-0 contract) so it derives the bump, drafts the changelog entry, and changes **nothing**. Hand it: (a) the landed range (`git log <base>..HEAD` + `git diff <base>`); (b) `.auto-task/<branch>/PLAN.md` for the Requirements + Acceptance Criteria the entry is written from; and (c) the resolved `release_command`. Its report must **surface what that command will do** — a delegated command runs under the user's authority and may itself push or publish, which the user must learn *before* it runs, not after. **Record that disclosure, do not merely display it.** On `ask` the prompt shows it; on `always` and on the autonomous/headless degrade **there is no prompt**, so a report-only line would have no reader at all. So carry it into `release.command_effects` and into the `## Release` CONTEXT section on every path, and on the no-prompt paths append a `state.assumptions[]` entry naming what the command was allowed to do unattended. A boundary the user only learns about in a prompt two of the three modes skip is not a disclosure.
   - **`release_command` unset → runbook, run nothing.** Record `status: "runbook"` with the plan, hand over the paste-ready steps, and go to step 9 (terminal). Guessing a multi-file version bump is how a repo ends up half-bumped; this is the honest fallback, not a failure.
   - **The command commits or tags by itself** (the report says so — `npm version`, `standard-version`, `semantic-release` and `cargo-release` all do by default) → **do not run it.** Its internal commit never passes through a Bash-tool git commit, so `enforce-gates.sh` would never see it, and it wedges step 8's commit precondition. Record `status: "failed"` with the reason ("`release_command` commits/tags by itself; this step needs a file-only command") and the fix (`--no-git-tag-version` / `--skip.commit --skip.tag` / `--no-commit --no-tag`, or a wrapper that only writes manifests), surface it, and stop. Nothing was run, so nothing needs undoing — which is why this is caught here, in `report-only`, rather than after the fact.
   - **Nothing to release** (no user-observable change since the last tag, or the version is already released) → `status: "nothing-to-release"`, go to step 9. **This holds in `ask` mode too:** because the plan is resolved before the prompt, `ask` never interrupts about a release that isn't warranted.
   - **The report lists ANY other blocker → `status: "failed"` here, before touching anything.** The skill's `report-only` report is required to carry a **Blockers** line for everything from its edge list that is already true — a pre-existing `vX.Y.Z` tag, an absent or unparseable `CHANGELOG.md`, a dirty tree carrying unrelated work — and its own edge table says a pre-existing tag means STOP before applying. So act on it *at the earliest point it is knowable*: record `status: "failed"` with the blocker and what would clear it, surface, and stop. **Do not fall through to step 4.** Falling through would write the in-flight marker, invoke `apply` (which correctly refuses), then run step 5 and a full step-6 re-gate — a re-verify, a re-`auto-task-code-review` and on STANDARD/HEAVY a whole Gate B pass — against a diff nothing changed, only to fail at step 8 with nothing staged or a tag command that cannot succeed. Step 8's `failed` bullet names these same blockers, but reaching them there means the work was done and the tree touched first; this branch is what makes the naming honest.
4. **Decide whether to release.**
   **What `apply` does here — it does NOT commit.** Under orchestration the skill's `apply` performs only its substeps 4.1-4.3 (write the changelog entry → run the `release_command` → verify the bump landed) and then returns; the commit and the tag are **this phase's** job, at step 8. That split is mandatory, not stylistic: the bump is new authored bytes, so committing before step 6 refreshes `gates.code_review.reviewed_diff_sha` is hard-blocked by `enforce-gates.sh` — the release would fail with a bump on disk and nothing cut. It also keeps the run's one-commit rule intact (every commit goes through `auto-task-commit`).
   - `always` → re-invoke the skill in **`apply`** mode with the report verbatim as the approved plan, no prompt.
   - `ask` → **degrade to `always`, without yielding, when the run cannot legitimately stop**: `state.autonomy == "autonomous"`, or `AskUserQuestion` is unavailable (headless). Re-invoke the skill in **`apply`** mode and append a `state.assumptions[]` entry `{ kind: "auto-approved-ambiguity", note: "release_mode=ask degraded to always (<autonomous|headless>); cut vX.Y.Z (<bump>) unattended", at }` so the merge gate (or the PR body) surfaces the call. Otherwise set `expected_next_action: "user-approval"`, present the release plan prefixed with the run banner — **the version, the derived bump AND the signal that decided it, the changelog entry, and what the release command will do** — and ask once: cut this release, cut it at a different bump level, or skip it this run. Write back `expected_next_action: "auto-continue"` and honor the answer. A **different bump level** is a binding amendment: re-invoke `report-only` for the corrected version, then re-invoke the skill in **`apply`** mode with that corrected plan — **and if the corrected report carries a Blockers line, act on its Blockers line exactly as step 3 does** (record `status: "failed"` with the blocker and what would clear it, surface, and stop; do not proceed to `apply`). The corrected version is a *different* version, so it can trip a blocker the original did not — most obviously a pre-existing `vX.Y.Z` tag for the level the user just picked. Without this the outcome still stays honest (`apply` refuses, and the "Read what `apply` RETURNED" branch below records `failed` and surfaces), but the run spends a whole wasted skill invocation to learn what the report already said. **Skip** → `status: "declined"`, park the plan in `state.followups` (`source: "release"`), go to step 9; nothing was changed, so there is nothing to unwind.
   - **Mark the in-flight window immediately BEFORE the `apply` call (REQUIRED).** Log `{ phase: "release", result: "in-progress", step: "apply", plan: { version, bump, entry: "<the approved entry text VERBATIM>" }, at }` *before* invoking `apply`, and set `release.status = "in-progress"`. **On the amendment path there are two skill invocations — write the marker before the `apply` one, never before the corrected `report-only`.** A marker written before the re-derivation would pin the superseded `plan.version`, so a later step-1 resume would compare the observable release against a version the user had already replaced and take the "released a DIFFERENT version than the plan" branch for a release that in fact matched the approval — and would surface the pre-amendment `entry` text as "what the user approved". The marker must always carry the *final* approved plan. The `plan` payload is the durable copy of what the user approved — a resumed session cannot see the dead session's conversation, and step 1 surfaces this payload rather than re-deriving it. **Marker-continuity rule (REQUIRED): every later `in-progress` refresh (steps 6 and 8) MUST carry `version` and `plan` forward unchanged.** Step 1 reads only the *newest* `release` entry, so a refresh that dropped them would leave the highest-stakes interrupt — a death inside step 6's long re-gate — with a marker that cannot produce the handover step 1 mandates (the approved entry text, and the version the `git tag -d vX.Y.Z` undo is parameterised on), while step 1 simultaneously forbids re-deriving them. Carrying them forward keeps every marker self-sufficient; `state.history` being append-only means the original is still there, but nothing should require a reader to walk backwards past the newest entry. The marker must precede the call: an interrupt across the sub-agent return boundary would otherwise leave a bump on disk with no record that anything was attempted.
   - **Read what `apply` RETURNED before going anywhere near step 5 (REQUIRED).** The skill hard-stops on a non-zero `release_command` (its substep 4.2) and returns a failed report — and a legitimate release command *does* fail: this repo's own generator refuses to write when the version has no changelog entry. **If `apply` did not complete, record `status: "failed"` with the command transcript and the partial state, surface it, and STOP here.** Do NOT continue to step 5. Continuing would authorize the release paths and then spend a full re-verify + re-`auto-task-code-review` + Gate-B pass on a tree carrying a changelog entry for a version that was never bumped, and arrive at step 8 with nothing distinguishing it from success. The tree may hold a partial write the command made before failing — say so explicitly and hand over `git checkout -- <the changelog + manifest paths>` for files that already existed, and, for anything the command *created*, **simply deleting the untracked file**. Note the difference from step 6's otherwise-identical undo: that one also names `git rm --cached <path>` because step 5's `git add -N` has run by then, whereas step 5 runs *after* this branch — nothing is intent-added here, so `git rm --cached` would only error on an unstaged path. This is the branch the `failed` status was defined for; without it the skill's hard stop has no reader.

5. **Authorize the release paths for staging — BEFORE the re-gate (REQUIRED; ordering is load-bearing).** `CHANGELOG.md` and the version manifests are not in a Blast Radius authored in Phase 1 for the *code* change, so append them to PLAN.md's **Blast radius** list with a one-line note that Phase 9 added them, and log `{ phase: "execute-checkpoint", result: "adjacent", files: [<release paths>], summary: "release step Phase 9 — changelog + version manifests authorized for staging", at }`. If the release created a file, `git add -N <path>` it **now, before step 6 pins the sha** — an untracked file is invisible to `git diff <base>` and so to `reviewed_diff_sha`, and intent-to-adding it *after* the pin would make it enter the diff only after the hash was fixed, hard-blocking the commit. This is a *recorded* authorization, not a bypass: the paths stay restricted to the skill's scope contract.
6. **Re-pass the gates (MANDATORY).** The bump + changelog are new authored bytes added after the review went clean, so the review is stale by exactly the mechanism `enforce-gates.sh` blocks on. Append a refreshed in-flight marker `{ phase: "release", result: "in-progress", step: "re-gate", version, plan, files: [...], at }` BEFORE clearing any gate flag — **carry `version` and `plan` forward on every refresh** (see the marker-continuity rule at step 4), then re-run `/auto-task-verify` (current tier scope), re-invoke the **`auto-task-code-review`** skill on the new diff and drive it to a clean pass, then refresh `gates.code_review.reviewed_diff_sha` (Phase 4's pinned-flags formula) and `clean_pass_after_last_fix`. On **STANDARD/HEAVY** also set `gates.gate_b.passed = false` and **re-run Gate B** against the release diff, restoring `true` only on a clean adversarial pass; LIGHT skips Gate B by design.
   - **If either re-gate does not come back clean, SURFACE — do not loop and do not auto-revert.** A Blocker/Required from the re-review or from the re-run Gate B means the release diff itself is not shippable. Record `status: "failed"` with the findings, and hand the user both the state (the bump is on disk, uncommitted; `gates.gate_b.passed` may be `false`) and the undo: `git checkout -- <the changelog + manifest paths>` for files that already existed, **plus `git rm --cached <path>` and deleting the file** for anything the release *created* and step 5 intent-added — `git checkout --` alone restores an intent-added path from the empty index blob, leaving a 0-byte staged addition rather than removing it. Then stop. Auto-task does not revert the tree for you here: an automated revert on a tree that also holds the run's own reviewed work is riskier than a clear handover.
7. **Loop-counter accounting (do NOT silently spend the fix-loop budget).** A **clean** release re-review does **not** increment `iteration.review`: no finding drove it, it is a gate refresh, and `enforce-gates.sh` measures the budget against `max(iteration.fix, iteration.review)` — charging it would consume rounds meant for real fixes and could block the commit on a run that never iterated. A re-review that *does* produce a Blocker/Required is not looped either (step 6): it surfaces.
8. **Commit, tag, and verify — THIS phase does both, now that the gates are refreshed.** Append a refreshed in-flight marker `{ phase: "release", result: "in-progress", step: "commit-tag", version, plan, at }` BEFORE staging anything — again **carrying `version` and `plan` forward**, so an interrupt here is visible to step 1. Then stage the release paths only (`git restore --staged .auto-task/` defensively first) and commit via the **`auto-task-commit`** skill with the message exactly `chore(release): vX.Y.Z` and **no** AI-attribution trailer; the pre-commit hook validates the refreshed gates. Then create the annotated tag: `git tag -a vX.Y.Z -m "vX.Y.Z"`. The `auto-task-release` skill has already returned by this point — it stopped after verifying the bump (step 4) and never commits under orchestration. Then confirm: the commit subject is exactly that string, the tag exists and `git cat-file -t vX.Y.Z` is `tag` (annotated, not lightweight), the commit touches only the changelog + version manifests, and **nothing was pushed**. **Never push and never publish** — surface the exact commands the user would run (`git push origin HEAD && git push origin vX.Y.Z`, plus any publish step) and hand them over. **Establish the push state by looking for positive evidence that the release DID reach the remote — never by looking for evidence that it did not (REQUIRED; the check must fail safe toward "local").** A delegated `release_command` can push on its own, so this is the one place the never-push boundary can be broken by something auto-task does not control, and it must be *detected and reported* rather than assumed away — but a detector that guesses "pushed" from a negative signal is worse than none, because it withholds the very unwind the release needs. Concretely: **treat the release as local unless** `git ls-remote --tags origin "refs/tags/vX.Y.Z"` returns a ref, **or** the branch has an upstream (`git rev-parse --abbrev-ref "@{upstream}"` succeeds) that already contains the release commit (`git merge-base --is-ancestor <release-sha> "@{upstream}"`). Do **not** key off `git status -sb` showing the branch "in sync": a branch with no upstream at all — the normal state of an auto-task worktree branch, and of any `direct` run whose push was held at the Phase-5 prompt — prints no tracking segment and so satisfies "not ahead of upstream" while nothing whatsoever has been pushed. Reading that as a push would record `pushed_by_command` for a purely local release and hand the user `git push --delete origin vX.Y.Z` instead of the local unwind that is its only actual recovery path — the exact inverse of the dishonesty this branch exists to prevent. **Name the discriminator, because the probe itself cannot tell two of these apart:** `git ls-remote --tags origin "refs/tags/vX.Y.Z"` prints **empty stdout in both the "tag is absent" and the "remote is unreachable" case** — absent from the remote and an unreachable remote are indistinguishable by stdout alone, so **use the exit status, not the emptiness, to tell them apart** (`ls-remote` exits non-zero when it cannot reach the remote, and zero-with-no-output when it reached it and found nothing). This is fail-safe either way — **the action is identical** on both readings (treat the release as local, hand over the local unwind), so a mistaken reading never produces a wrong command; only the *caveat* differs, which is why it must still be got right. Concretely there are three outcomes: **pushed** (a ref came back), **local** (exit 0, no ref — the remote was reached and does not have it), and **unverified** (non-zero exit — the remote could not be checked at all). **If the remote cannot be reached** (no network, no `origin` — this run's own Phase 1 hit exactly that), the push state is *unverified*: record it as unverified with what you observed, print the push commands as still-owed but say the remote could not be checked, and do not set `pushed_by_command`.
   - **When the evidence IS positive → `status: "applied"` (the release is complete — it is only *also* public).** **Precondition: this bullet applies only when the commit AND the tag both exist** (the confirmations above passed). State it explicitly so this bullet and the `partial-failure` bullet below cannot both match the same state on paper — without it, a run where the tag failed but the push probe came back positive would textually satisfy both. That combination is unreachable in practice (`release_command` runs at substep 4.2, *before* the commit and tag exist, and a pre-existing remote tag is already a step-3 blocker), but an enum whose two bullets overlap in text is a defect regardless of whether the overlapping state is reachable — a reader cannot tell which branch governs. Record `release.pushed_by_command = true` plus what you observed, and do not print the push commands as though they were still owed: that summary would be false. Say plainly in the final summary that the release was pushed by the configured command and is therefore already public, so the local unwind no longer applies — a published tag needs `git push --delete origin vX.Y.Z`, which is the user's call. Then go to step 9, which writes `done` and (per its `## Release` field list) mandates that disclosure. **This status is deliberately `applied` and not `partial-failure`/`failed`:** nothing failed and nothing is half-done, so surfacing it as a failure would misdescribe it — the honesty owed here is about *what happened to the boundary*, which the disclosure carries, not about the release's completeness.
   - **`partial-failure`** (the commit landed, the tag did not) → `status: "partial-failure"`, `phase: "release"`, `expected_next_action: "user-approval"`. Surface it as a partial failure — naming the commit SHA and handing over **both** the continuation (`git tag -a vX.Y.Z -m "vX.Y.Z" <sha>`) and the unwind — and never describe it as done. This is the state most likely to be misread as success. Auto-task does not finish or undo it for you; the user resolves it, and step 1 re-surfaces it on any later run.
   - **`failed`** (a blocker such as a pre-existing tag pointing elsewhere, or an absent `CHANGELOG.md`) → `status: "failed"`, surfaced the same way, with the reason and whatever state exists. Never move or delete an existing tag to make room. **This bullet covers only blockers raised *here*, at the commit/tag step — it is NOT where a `release_command` failure is raised.** The command runs earlier, in the skill's apply **substep 4.2** (step 4), and a non-zero exit is caught by step 4's own "Read what `apply` RETURNED" branch, which records `failed` and stops **before** step 5 authorizes any path and before this step is ever reached. Attributing a command failure to the commit step would misdescribe both *when* it happened and *what state the tree is in* — at substep 4.2 nothing is staged, nothing is intent-added, and no gate has been refreshed.
   - **Unwind, surfaced whenever anything was applied.** Because nothing is pushed, the release is fully reversible locally: `git tag -d vX.Y.Z` and `git reset --hard HEAD~1`. **"Fully reversible locally" is conditional on nothing having reached the remote — check before you claim it.** One narrow case escapes the probe above: a `release_command` that **pushes the commit without the tag**, on a branch with no upstream configured. `ls-remote --tags` misses it (no tag was pushed) and the ancestor probe is inconclusive (`@{upstream}` is unset), so the release reads as local while a commit is in fact public. `--follow-tags` pushes both and so is caught, which is why this needs a command that pushes commits but not tags — narrow, but the unwind claim is exactly what it would falsify. So when `command_effects` says the command pushes at all, say the local unwind covers only what stayed local and name `git push --delete` / a revert-and-push as the remote half. **State the precondition every time:** `git reset --hard HEAD~1` is only safe while the release commit is still `HEAD` and the tree is clean — it discards uncommitted work and is the wrong command if anything landed after; when either is untrue, hand over `git revert <release-sha>` instead. Persist what you handed over to `release.unwind`. **Auto-task never runs these itself** — they are handed to the user, which is precisely why an interrupted unwind is not a state this phase has to recover from.
9. **Record + terminal state.** Always: write `release` to state — including the terminal status, which on a completed release is `status: "applied"` — **mirror it to `state.history` per the status-write rule above** (so a completed release logs `result: "applied"`), and append a TRACE entry (`operation: auto-task:phase-9-release`) naming the outcome. **One exception to that mirror — the *accepted* `partial-failure` path, where you mirror NOTHING.** The acceptance already appended `{ result: "accepted-partial-failure" }`, and `release.status` deliberately stays `partial-failure`, so mirroring the status here would append a *newer* bare `partial-failure` entry that buries the discriminator: an interrupt before the `phase: "done"` write would then let step 1 read the newest entry as an unresolved half-cut release and re-surface a decision the user already made — the exact hole outcome 4 closes, relocated one step later. On that path the acceptance entry must remain the newest `release` entry. (The TRACE entry above is still written, on every path.) **Everything else is conditional on having actually produced it — never write a record of something that did not happen:**
   - **A `skipped-*` outcome** (`skipped-disabled` / `skipped-invalid-value` / `skipped-skill-absent`) — nothing ran, so there is no version, entry, commit, tag, or transcript. Record the status and the reason and **stop there**: do NOT add a `## Release` section beyond a single line naming why the step was skipped, do NOT append `state.checks[]` rows for checks that never ran, and above all do NOT create an `artifacts/release-*.txt` for a command that was never executed (a fabricated artifact is worse than a missing one — artifacts are read as proof).
   - **`nothing-to-release` / `deferred-pr` / `runbook`, and either step-3 `failed`** (the command was refused before running, or a report-only blocker stopped it before it ran) — no release command ran, so no transcript. A `## Release` section IS warranted here and is the point: record the plan that was *not* cut and why (and, for `runbook`/`deferred-pr`, the paste-ready steps handed over).
   - **`declined`** — which producer it came from decides what to record, because the two differ on whether anything ever ran. From the **step-4 ask** (the user said "skip it this run"): nothing ran, so treat it exactly like the bullet above. From the **resolution rule's undone outcome**: a release command *did* run in an earlier session, a bump was written, a commit and possibly a tag existed, and the user then unwound it — so do NOT write "the plan that was not cut". Record what actually happened: the version that was cut, that it was unwound at the user's direction, and the state you verified. That cut-and-reversed fact is the most audit-relevant thing about such a run and it must not be lost. This session has no transcript to save (the command ran in the dead session) — say so and save nothing, per this step's own no-fabrication rule.
   - **`applied` / `in-progress` / `partial-failure` / a `failed` raised at step 4, 6 or 8** — the release command ran **in this session**, so save its transcript under `artifacts/release-*.txt` — **but verify that premise before acting on it, because ALL FOUR of these statuses can be recorded with no transcript in *this* session** (per this step's own rule a fabricated artifact is worse than a missing one, and an `artifacts/release-*.txt` invented to satisfy this bullet is precisely that). The four: **`applied`** recorded on step 1's **resolution path** (outcome 1) — the command ran in a dead session, so this one has no transcript; **`partial-failure`** recorded on that same resolution path (outcome 4, the *accepted* half-cut release) — likewise a dead-session command; a step-4 **`failed`** raised **before** substep 4.2 ever ran the command — the skill also hard-stops on its earlier substeps, e.g. a `CHANGELOG.md` whose insertion point it will not guess at; and an **`in-progress` at `step: "apply"`**, written *before* the `apply` call by design (step 4's marker rule), so the command may not have started. (An `in-progress` run does not itself reach step 9 — step 1 hard-stops it — but it is listed because the status appears in this bullet's set and a later session must still not invent a transcript for it.) Count the *statuses*, not the producers: every status this bullet lists has at least one no-transcript route, which is why the premise must be checked rather than assumed. In all four cases say so and save nothing; everything else in this bullet still applies, append the `state.checks[]` rows (tagged `gate: "release"`), and write the full `## Release` section to `.auto-task/<branch>/CONTEXT.md`: version, bump + signal, entry, commit, tag, the files touched, **`command_effects` — what the `release_command` was determined to do** (step 3 records this on every path precisely because the `ask` prompt is the only place it is *displayed*; omitting it here would leave the disclosure with no home a human reads), the push/publish commands NOT run — **or, when `pushed_by_command` is set, that the command pushed on its own and the release is already public, since "commands NOT run" would be false there** — and the unwind.
   Then, subject to the **run-metrics terminal guard** (Phase 5 step 4 — confirm the `handover-metrics` entry exists and run the metrics step first if it does not, since a run resumed straight into Phase 9 can reach `done` without Phase 5's metrics step having run in this session): **terminal statuses** — `applied` / `nothing-to-release` / `declined` / `runbook` / `deferred-pr` / any `skipped-*` → `phase: "done"`, `expected_next_action: null`, and give the final summary (PR URL if any + the release version/commit/tag or the reason none was cut + the push commands not run + where artifacts live). **Transitional status** — `resolved-re-derive` should never reach step 9: step 1 consumes it by falling through to step 2, and the run writes a real outcome before any terminal write. If it *is* the status here, something skipped a status write — do not record it as an outcome; surface it instead. **Surfaced statuses** — `in-progress` / `partial-failure` / `failed` → stay `phase: "release"` (**except an *accepted* `partial-failure`** — the user was shown the half-cut release and chose to leave it, so it is finished and terminal; record the acceptance and write `done`. **Read the acceptance from the newest `release` entry in `state.history`, not from the conversation:** it is accepted iff that entry's `result` is `accepted-partial-failure`. `release.status` is `partial-failure` in BOTH cases by design — the carve-out in the status-write rule mandates it stays that value — so the history entry is the only discriminator, and a resumed session that cannot see the original exchange has exactly this to go on. Without keying on it, step 9 would re-surface a decision the user already made, which is the hole outcome 4 was added to close. **This exception writes `phase: "done"` AND `expected_next_action: null`** — the terminal pair from the yield table's Phase-9 row, NOT the `"user-approval"` named after this parenthesis, which governs only the three genuinely-surfaced statuses. Stated explicitly because the parenthetical is long: a `done` phase carrying `"user-approval"` is a combination the yield table never lists, and the Stop hook would read a finished run as still owing the user a turn.) with `expected_next_action: "user-approval"`; the run is NOT `done`, and it is the user who resolves it (step 1 re-surfaces the state on any later run rather than guessing).

**Release step off?** The default (`release_mode: "skip"`). Phase 9 is never entered, `release` stays `null`, and the run reaches `done` exactly as it did before this phase existed. (Phase 9 *is* entered — and writes `skipped-disabled` — only if the guard read `always`/`ask` and step 2's live re-read then returned `skip`.)
